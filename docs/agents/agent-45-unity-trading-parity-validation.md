# Agent 45: Unity Trading Parity Validation Agent

**Creation order:** Third in Migration Phase 2, Sub-Phase B. Created alongside Agent 44 and runs continuously against it, same pattern as Agent 32/33 and Agent 39/40's own relationships.

## Responsibility

Prove Agent 44's C# port produces numerically identical output to the current TypeScript implementation for the same inputs, across every Sub-Phase B function — the same "the C# code agrees with the TypeScript code" standard Agent 33/40 already established, restated for Trading's scope.

## Inputs

- `docs/agents/agent-40-unity-galaxy-planet-parity-validation.md` — the harness/comparison pattern extended, not re-invented.
- The real content catalog (`content/resources.json`, `content/tradingBasePrices.json`, `content/planetMarketPreferences.json`) — real items (`igneous-ore`, `autunite-crystal`, `hydrogen-gas`, `ion-forged-hull-plate`) used throughout, not synthetic fixtures.
- Agent 44's own output.

## Outputs

### 1. Extended `scripts/parityHarness.ts`

Ten new corpus sections, each generated by running the REAL TypeScript function once and recording its actual output:

- `createListingCases` (3) — global and planet listings across three real resources at three different tiers.
- `applyDriftCases` (4) — including two cases deliberately sized to hit the floor/ceiling clamp, not just an unclamped interior value.
- `applyRecoveryCases` (4) — including elapsed-hours 0 (no-op) and a very large elapsed time (effectively fully recovered).
- `seasonCases` (3) — `getCurrentSeason`/`getSeasonalEffect`/`getSeasonalPriceMultiplier` together, including an empty-categories case (`null` effect).
- `emergencyCases` (5) — four arbitrary (planetId, now) pairs (all landed on "no emergency," ~85% the expected outcome) plus **one found by a small brute-force search over candidate planet ids** specifically so the corpus also exercises the triggered branch's `category`/`endsAt` fields, not just the far more common null result. The search itself isn't part of the harness's committed output — only the one planetId it found (`emergency-search-3`) is, documented as found-by-search rather than hand-picked to "look right."
- `globalPriceCases` (2) — buy and sell directions against the same three-planet market-state set.
- `purchaseListingCases` (5) — successful planet purchase, successful global purchase that exactly closes the listing, self-trade rejection, insufficient-quantity rejection, non-positive-quantity rejection.
- `sellToMarketCases` (2), `sellToGlobalMarketCases` (1) — straightforward successful sells.
- `expireListingsCases` (1) — a 4-listing batch mixing expired/not-yet-expired and global/planet-location, including a sold-out (quantity 0) expired listing that must produce no `ReturnAction`.

Error/rejection paths unreachable with real content (the global-listable tier-5 ceiling — nothing in the current catalog exceeds tier 4) are deliberately not in this corpus; Agent 44's own direct unit tests cover those instead (this agent's own Must-Not-Do).

### 2. Extended `ProfitableCore.Tests/Parity/ParityCorpus.cs`

New DTOs for every section above. `MarketLocation`'s JSON shape (`"global"` or `{ planetId }`) has no natural strongly-typed field, so it's carried as a raw `JsonElement` and converted at the point of use (`TradingParityTests.ParseLocation`) rather than via a custom `JsonConverter` — consistent with this test suite's existing "manual reconstruction from DTO into real domain object" convention (`GalaxyPlanetParityTests.AssertPlanetMatches`).

### 3. `ProfitableCore.Tests/Parity/TradingParityTests.cs`

Ten `[Theory]`/`[MemberData]` test methods, one per corpus section, each reconstructing real domain objects from the DTOs and asserting field-for-field equality against the C# port's actual output.

## Must NOT Do

- Must not accept Agent 44's own unit tests passing as a substitute for this comparison — same restated rule as every prior parity agent in this migration.
- Must not generate the corpus against a synthetic/toy resource catalog — real `content/*.json` throughout (`igneous-ore`/`autunite-crystal`/`hydrogen-gas`/`ion-forged-hull-plate`).
- Must not hand-pick the triggered-emergency case's `(planetId, now)` pair to "look plausible" — found by an actual small search over the real function's own output, documented as such, since a hand-typed pair with no verification could easily encode a wrong assumption about the trigger window's boundaries.
- Must not record error/rejection cases the real content catalog structurally cannot reach (e.g. the global tier-5 ceiling) — those belong in Agent 44's own direct unit tests, which construct a hand-built tier-6 fixture explicitly for that purpose.

## Testing Requirements

- All 30 new corpus cases pass, and regenerating the corpus (`npm run parity`) and re-running `dotnet test` reproduces the same pass result.
- Every Sub-Phase B Simulation Core function (Agent 44) has at least one real-content parity case exercising it.

## Definition of Done

- `dotnet test` passes with zero failures across all 591 tests (541 through Sub-Phase A + 30 parity + 20 direct unit tests: 11 `TradingSimulationTests` + 5 `TradingContentLoaderTests` + 4 `TradingContentLoaderRealFilesTests`).
- A reviewer can regenerate the corpus and re-run to reproduce the same result independently.
- No later Sub-Phase B agent (Presentation/Integration) should discover a numeric disagreement between the C# and TypeScript implementations this agent's corpus should have already caught.
