# Functional Agent: Build (Unity Migration Manager)

**Status: new scope, not yet built — and structurally different from every other file in this folder.** Every other functional agent documents a *game* system. This one documents a *meta*-agent: the orchestrator responsible for sequencing and running the other agents that port Profitable's TypeScript/Phaser implementation to Unity/C#, in the correct order, without porting anything that isn't actually finished yet. It has no simulation formula of its own — its "Outputs" are a readiness computation, a generated agent roster, and a dispatch/verification loop, not a pure function over game data.

**Depends on:** `docs/agents/README.md`'s Creation Order (the original TypeScript build sequence — Migration Phase 2+ is explicitly required to mirror it, `profitable-unity-migration-gdd.md` §2), `docs/profitable-unity-migration-gdd.md` (Migration Phase 1's proven agent shape and cross-cutting migration rules — read this in full before using this file, not paraphrased here), every file in `docs/functional-agents/` (the source of truth for what's *currently* built vs. still-designed, read via each file's own Status line — never assumed from memory or from `docs/agents/`'s historical record, which doesn't reflect scope added after it was written), and the real `unity/` folder (`unity/README.md`, the `ProfitableCore`/`ProfitableCore.Tests`/`ProfitableUnity` structure) as the ground truth for what's actually been ported already, not just what a GDD claims.

## Responsibility

Given the current state of the TypeScript codebase (via `docs/functional-agents/*.md`'s own Status lines) and the current state of the Unity port (via `unity/`'s real contents), determine which functional areas are actually eligible for their next Unity migration phase, generate the next numbered agent roster for each eligible area — mirroring Migration Phase 1's proven six-role shape (Schema → Simulation Core → Parity Validation → Infrastructure Adapters → Presentation → Phase Integration) — and run those agents in the correct dependency order, verifying each phase's parity proof and Definition of Done before advancing to the next. **Its single most important job is refusing to port a moving target** — see "Port what's built, not what's designed," below.

## Outputs

### Readiness computation — the core, repeatable algorithm

For each functional area named in `profitable-unity-migration-gdd.md` §2's Phase 2+ list (Galaxy/Planets → Trading → Crew → Ships/Travel → the four deferred gaps: Map, Travel Encounters, Scanner, Combat) plus any functional area added to `docs/functional-agents/` since that list was written (Planet Ownership, Universe, and Ship's Fuel/Cargo/Crew Roles all postdate it):

1. **Resolve which `docs/functional-agents/*.md` file(s) cover this area** (Galaxy/Planets → `galaxy.md` + `planet.md` + `mining.md`; Trading → `planetary-markets.md` + `galactic-market.md`; Ships/Travel → `ship.md` + `travel.md`; Combat → `encounters-combat.md`; etc.).
2. **Check each file's Status line and any inline `**Pending amendment**`/"not yet built"/"new scope" markers.** If *any* part of the area's current contract is not yet built in TypeScript, the area is **blocked**, not ready — see "Port what's built, not what's designed" below for what to do with a partially-blocked area.
3. **Check `unity/` for whether this area has already been ported** (a `ProfitableCore/Schema`/`Simulation`/`Content` file or `docs/agents/agent-3X-*` contract already covering it). If so, skip — already done, not re-run.
4. **If ready and not yet ported:** this area becomes the next Migration Phase's subject.

### "Port what's built, not what's designed" — the rule for partially-blocked areas

**When a functional area's contract is mixed (some as-built, some pending), the eligible migration phase covers only the as-built portion — the pending portion becomes a separate, later Unity **amendment**-phase, created only once its TypeScript counterpart is built and its own status flips to as-built.** This directly mirrors how the pending TypeScript work itself will land: `sellToMarket()` is designed as an amendment to the existing trading core, not a rewrite of it; Ship Fuel/Crew Roles are designed as amendments to `initiateVoyage()`, not a new travel system. A Unity migration phase that tried to port the *whole* current contract, pending scope included, would either stall waiting on unrelated TypeScript work or — worse — silently invent the missing behavior in C# first, which is exactly the "porting as design" this whole effort exists to prevent (`profitable-unity-migration-gdd.md` §6: "No agent uses porting as an opportunity to change game behavior").

**Concretely, this rule already had a real test case, not just a hypothetical one.** When this file was first written, `planet.md`/`mining.md` were mixed (Planet Resource Generation designed but not built), so the rule above would have scoped a hypothetical Migration Phase 2 to `galaxy.md` in full plus only `planet.md`'s original Agent 8 portion, deferring fixed quality/the reset cycle/the tutorial guarantee to a later amendment-phase. That TypeScript work has since shipped, so the rule's *output* changed the moment its *input* did — `planet.md`/`mining.md` are both fully eligible now, exactly as the rule predicts for a mixed area whose pending portion gets built. **This is the rule working as designed, not a correction to it** — the readiness table above reflects the current, recomputed state; `planet-ownership.md`'s still-mixed status (Colonist-Driven Production built, Citadels' benefit-wiring pending) is today's live example of the same pattern.

### Generated roster — mirrors Migration Phase 1's proven shape exactly

For each eligible area, this agent produces (not necessarily all six every time — see the parenthetical skip conditions) a set of new, sequentially-numbered `docs/agents/agent-N-unity-<area>-*.md` contracts, continuing from whatever the current highest number actually is (38 onward, as of this writing — Agent 37 was claimed by Planet Ownership Core in the meantime), following Phase 1's exact roles:

1. **Schema.** Ports the area's data types/constants to C#. Created first, everything else in the phase depends on it.
2. **Simulation Core.** Ports the area's pure formula logic, exactly — including a fresh check for the integer-boundary-vs-fractional-input risk (`profitable-unity-migration-gdd.md` §3) on every table/breakpoint/threshold comparison the ported code contains, whether or not that specific function has ever exhibited the bug. Depends on 1.
3. **Parity Validation.** Proves the C# output is numerically identical to the current TypeScript implementation's output for the same inputs — regenerating the parity corpus (`npm run parity`) against the area's *current* TypeScript, not a stale snapshot. Created alongside 2, runs continuously.
4. **Infrastructure Adapters.** Only created if the area needs a new adapter beyond what Phase 1 (`SaveSystem`/`AudioManager`) already covers — most areas won't. Independent of 2/3 when it exists.
5. **Presentation.** Full rewrite as a real Unity scene (never a mechanical port — `profitable-unity-migration-gdd.md` §1's table is explicit that presentation is the one layer that doesn't translate). Depends on 2 and 4 (or just 2, if no new adapter was needed).
6. **Phase Integration.** Wires the new area into the already-ported Unity build, confirms the phase's parity proof holds end-to-end (not just per-function), confirms the existing web/Electron build is untouched. Created last, depends on everything above.

### Dispatch and verification loop

Runs phases in the order the readiness computation produces (mirroring the original TypeScript Creation Order); within a phase, runs roles 1 and 4 in parallel (both are prerequisites with no dependency on each other), then 2+3 together once 1 completes, then 5 once 2 and 4 both complete, then 6 last. **Before advancing to the next phase, confirms the current phase's Parity Validation and Phase Integration agents both report success** — a phase that hasn't proven parity is not "done enough to move on," the same standard Migration Phase 1 itself was held to (`profitable-unity-migration-gdd.md`'s own closing status: "Migration Phase 1 complete... Agent 36's Integration report is the closing confirmation").

## Must NOT Do

- **Must not port any functional area whose `docs/functional-agents/*.md` contract contains a `**Pending amendment**`/"not yet built"/"new scope" marker for the part being ported** — flag it as blocked, state the specific missing TypeScript work, and move to the next eligible area instead. A blocked area is not a lower-priority ready area; it's not ready at all.
- **Must not use porting as an opportunity to change game behavior**, including "obvious improvements" noticed mid-port — any such finding gets reported as a design question (the same way this whole review series reports a documentation gap), never silently coded into the C# port. Restated here because this agent is the one responsible for holding every future phase to this rule, not just Phase 1.
- **Must not modify the existing web/Electron TypeScript build (`src/`, `content/`)** — Unity migration is new, additive work in the separate `unity/` project, throughout every phase, not just Phase 1.
- **Must not skip Parity Validation for any phase**, and must not accept a phase's own unit tests passing as a substitute for it — parity is proving the C# and TypeScript *agree*, not that the C# is merely self-consistent.
- **Must not re-derive a table/breakpoint/threshold comparison from scratch during translation** — port the current, already-correct TypeScript logic byte-for-byte in intent, and carry `profitable-unity-migration-gdd.md` §3's fractional-boundary test cases forward to every future phase's comparison logic, not just the two functions where the bug was first found.
- **Must not re-author content in a Unity-native format** (e.g., ScriptableObjects) — every phase's content is the existing `content/*.json`, consumed as-is via a C# loader, per §1's table, unless a later phase finds and reports a concrete reason this stops working.
- **Must not renumber, rewrite, or delete any existing `docs/agents/*.md` file** — new phase-agent contracts get new sequential numbers continuing from whatever the current highest actually is (38 onward, as of this writing), the same "chronological record, never rewritten" rule `docs/agents/README.md` states for itself.
- **Must not dispatch a role before its declared dependency's own agent has completed** (Simulation Core before Schema; Presentation before both Simulation Core and Infrastructure Adapters exist; Phase Integration before everything else in the phase) — the ordering isn't a suggestion, it's the same dependency structure Migration Phase 1 already proved out.
- **Must not invent a new functional area's scope itself** — this agent operates strictly on what already exists as a `docs/functional-agents/*.md` contract; if an area has no such file yet (Crew, currently), that's a documentation gap to report, not something this agent designs unilaterally to unblock itself.
- **Must not treat `docs/agents/`'s historical record as current-state truth** — it's frozen at whatever phase first shipped a system; only `docs/functional-agents/`'s Status lines (or, if no functional-agent file exists yet for an area, a fresh check against the real source) reflect what's actually built today.

## Testing Requirements

- **Readiness computation:** given the current, real state of `docs/functional-agents/`, correctly classifies every area in the table above as ready/partially-blocked/blocked/excluded, matching the reasoning shown — a regression test that must be re-run (not just re-read) whenever any functional-agent file's Status line changes, since this agent's entire value is staying correct as the TypeScript side keeps moving.
- **Mixed-area handling:** for a partially-blocked area, correctly scopes the generated roster to the as-built portion only, and correctly defers the pending portion to a later amendment-phase rather than either skipping the whole area or attempting to port the pending portion anyway. **No area in the table above is currently mixed** — Planet Ownership and Travel, this rule's original worked examples, are both now fully as-built; re-verify this test case against whichever area is mixed next time one exists, don't assume these two stay the standing example.
- **Roster generation:** the generated agent numbers never collide with an existing `docs/agents/*.md` file; role dependencies (Schema before Simulation Core, etc.) are encoded correctly for every generated phase, not just copied from the Phase 1 example without adaptation.
- **Dispatch ordering:** a phase's Phase Integration agent never runs before that phase's Parity Validation agent has reported success; a later phase never starts before the current phase's Phase Integration has reported success.
- Regression: no test anywhere asserts this agent modifies `src/`/`content/` — a passing suite here should not accidentally validate a violation of the "web/Electron build is never touched" rule.

## Definition of Done

- Given the real, current state of `docs/functional-agents/` and `unity/`, this agent produces an accurate readiness table (matching the one above, and correctly different from it once any underlying file changes) — provably derived from the actual files, not asserted from memory of what they used to say.
- For Migration Phase 2 specifically, a real, numbered agent roster exists (`docs/agents/agent-38-*` onward) covering `galaxy.md`, `planet.md`, and `mining.md` in full — all three fully as-built as of this writing, wider than this file's original scoping example — following Phase 1's exact six-role shape (minus any role that doesn't apply).
- Every subsequent phase this agent produces is provably sequenced to match `docs/agents/README.md`'s original Creation Order, with no phase started before its predecessor's Parity Validation and Phase Integration both report success.
- No phase's generated roster ever includes a role for scope that `docs/functional-agents/` still marks as not yet built in TypeScript — provably, by construction, not by manual review after the fact.
- The existing web/Electron build (`src/`, `content/`) is provably untouched by any action this agent takes, across every phase, not just the ones already run.
