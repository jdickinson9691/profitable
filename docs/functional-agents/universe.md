# Functional Agent: Universe

**Status: fully designed, zero code exists.** Unlike `galaxy.md`/`planet.md` (existing systems) and closer to `ship.md`'s original state (new scope), this file has **no implementation to document at all** — confirmed by a direct search (`grep -rli "universe|leaderboard" src/`, zero matches). What it does have is a complete, locked design (`profitable-design-questions.md`, Multiplayer section) — this file is that design's consolidated forward-looking contract, and the place future Universe/leaderboard development should be tracked, per this folder's own purpose. **Deliberately not scheduled** — Multiplayer's own design entry ties its build timing to "when the project moves toward being an app," not to any milestone currently active.

**Revision history:** the original version of this file left two real gaps (net worth's valuation formula, the universal modifier's floor/ceiling values) and never specified how the Universe would know how many galaxies exist for its own per-capita math — closed in an earlier pass. A second pass, done as part of a systematic agent-by-agent review, found four more: net worth and trading volume both predated (and never got updated for) Trading Counterparty/Planet Ownership, the registry had no decay/staleness concept, and missed daily reports had no catch-up behavior, unlike every other timed system in this project. All closed below, per the corresponding entries in `profitable-design-questions.md`'s Multiplayer section.

## Responsibility

Register each new galaxy at game start, aggregate anonymized per-player trading activity into a universal per-item price modifier feeding `galactic-market.md`'s `getGlobalPrice()`, and separately compute identity-attached leaderboards — without ever letting the registry/pricing pipeline and the leaderboard pipeline share data, and without introducing any shared real-time presence between players.

## Inputs (once built)

- `getGlobalPrice()` (`galactic-market.md`) — gains exactly one new input, a universal modifier, on top of what it already reads live from `PlanetMarketState[]`. Nothing about its existing signature/guarantees changes.
- `applyDrift()` (`planetary-markets.md`) — the universal modifier's own formula shape, and its `PRICE_FLOOR_PERCENT`/`PRICE_CEILING_PERCENT` constants, are reused as the starting values for this layer's own bounds (see Outputs).
- `PLANET_COUNT` / `galaxy.md`'s `loadOrCreateGalaxy()` — the registry reports a galaxy's own planet count once, at the same moment a galaxy is first created; this file never influences what that count is.
- `content.tradingBasePrices` (`planetary-markets.md`) and `SHIP_PURCHASE_COST_BY_TIER` (`travel.md`) — the valuation sources net worth is computed from (see Leaderboards).
- `transportColonists()`/`buildCitadel()`'s own recorded costs (`planet-ownership.md`) — net worth's planet-ownership component reads these directly, never re-derives a citadel's "value" independently.
- `sellToMarket()`'s return value (`planetary-markets.md`) — trading volume sums this alongside `purchaseListing()`'s, so the newer instant-sell path counts too.
- Existing player-attribution fields, already built for exactly this moment and confirmed still valid: `Listing.createdByPlayerId` + self-trade prevention (`planetary-markets.md`), `Wallet.playerId`, `Ship.ownerId`, `Scanner.ownerId` (`ship.md`/`travel.md`), `CrewMember.hiredByPlayerId` (a `crew` functional file doesn't exist yet in this folder — crew is currently only documented in `docs/agents/agent-16-crew-core.md` and siblings; out of scope for this pass).
- The timestamp-not-duration pattern (`lastCheckedAt`, elapsed time derived rather than trusted) — the precedent this file's own daily-report cadence reuses.

## Outputs (once built)

### Scope: asynchronous, market-and-leaderboard-only
No shared real-time presence, no live shared galaxy, no conflict resolution — players never directly encounter each other on the map or in a shared simulation tick. Exactly two interaction channels: a shared influence on market pricing (below), and leaderboards. Deliberately the cheapest real multiplayer shape available, reusing this project's existing asynchronous/catch-up architecture pattern throughout rather than inventing live sync.

### Galaxy registry
A **one-time event at game start** (when `galaxy.md`'s `loadOrCreateGalaxy()` generates a fresh seed, not on every subsequent load of an existing game): the client generates a local, random `galaxyToken` — never derived from or linked to `playerId`, never displayed anywhere in the UI — and registers it with the Universe alongside that galaxy's own `PLANET_COUNT`. This closes a real gap the pricing layer always had: the universal modifier's per-capita formula needs to divide by "how many galaxies exist," and nothing before this specified how the Universe would know that number, or tell one galaxy's periodic report apart from another's, given the pricing report itself carries no identifier of any kind (below). A `galaxyToken` doesn't weaken that anonymity guarantee — it can never be traced to a *player* — it only gives the registry a stable way to count distinct galaxies and de-duplicate a retried report. **The Universe never assigns or varies a galaxy's planet count** — `PLANET_COUNT` stays exactly the locally-decided, currently-uniform constant `galaxy.md` already owns; the registry only records what each galaxy independently decided, useful for an aggregate stat ("average planets per galaxy across the playerbase") and as the pricing formula's real denominator (below) — nothing more. Registration never blocks or gates local play — a galaxy is fully generated and playable before (or even if) registration ever succeeds, consistent with "each galaxy stays fully private/local, playable with zero Universe dependency." **Registration is permanent** (a `galaxyToken` is never deleted — the correct source for a "total galaxies ever" census stat) **but the pricing formula's denominator only counts recently-active ones** (below) — the two numbers serve different purposes and are computed differently from the same registry.

### Universe pricing layer
Each player keeps their own private, single-player-shaped `galaxy.md` instance, completely unchanged by this feature. Periodically (**daily**, reusing the same 24h cadence already established for emergency checks and encounter windows), each registered galaxy (keyed by its own `galaxyToken`) reports **anonymized** aggregate activity: `{ itemId: string, quantitySold: number, quantityBought: number }[]`, covering **everything tradeable, tiers 1-7** — deliberately not restricted to the tier 1-5 global-listing ceiling (`galactic-market.md`'s restriction is about the *listing* mechanism specifically; this is a read-only signal, and excluding tier 6-7 activity would blind the layer to the very items whose exclusivity matters most). **Structurally anonymous as to player identity** — the report payload has no field to put a `playerId` into, nothing to leak because it was never there; the `galaxyToken` is a separate, registry-only concept (above), not part of this report's own item-keyed shape.

**Reports catch up rather than covering a fixed prior-24h window.** A galaxy's report covers activity accumulated since its own `lastReportedAt` — a galaxy offline for 3 days reports 3 days of accumulated activity the next time it checks in, never silently losing signal, the same always-catch-up discipline `resolveBackgroundCrafting()`/voyage resolution/market recovery already use. `lastReportedAt` doubles as the registry's own activity signal (below) — no separate active/inactive flag anywhere.

**Universal modifier formula** (new function, e.g. `computeUniversalModifier(reports: GalaxyReport[], activeGalaxyCount: number): Record<itemId, number>`): `netVolume = quantityBought − quantitySold`, summed across all reporting galaxies for an item, divided by the count of galaxies whose `lastReportedAt` falls within a new `GALAXY_ACTIVE_WINDOW_DAYS` (originated default, tunable) of the current report cycle — **not the total-ever-registered count**, and **not a count of galaxies that happened to report that period** either: a quiet-but-recently-active galaxy still belongs in the denominator, while a long-abandoned one shouldn't permanently dilute the modifier toward inert as the game's real-world lifetime accumulates dead saves. "Active" is never a stored flag — always derived from how recently `lastReportedAt` was updated, the same "derive from a timestamp, never a stored boolean" discipline crew attrition/upkeep already use. That per-capita figure scales a **percentage** adjustment, bounded by `UNIVERSAL_MODIFIER_FLOOR_PERCENT` / `UNIVERSAL_MODIFIER_CEILING_PERCENT` — **new, independently-tunable constants, defaulted to the same 0.5 / 1.5 values `PRICE_FLOOR_PERCENT`/`PRICE_CEILING_PERCENT` already use** (`planetary-markets.md`) rather than the literal same constants, since a backend-scoped modifier and a per-listing local bound are different enough in scope to deserve independent tuning later even though they start identical — the same "reuse the shape, not necessarily the literal value" discipline Scanner's own tier-scaling already applied. **Before any real data exists, the modifier is a neutral 1.0× (no effect)** — `getGlobalPrice()`'s existing guarantees must hold identically on day one and after a year of real data. Feeds into `getGlobalPrice()` as one additional multiplier on top of what it already computes.

### Leaderboards
Identity-attached by design (the opposite privacy model from the registry/pricing layer above — worth keeping structurally separate, not just conceptually). Launch set:
- **Net worth** — `Wallet.credits` + Σ(each owned resource/component inventory batch's quantity × its `content.tradingBasePrices` base price) + Σ(each owned ship's `SHIP_PURCHASE_COST_BY_TIER[ship.tier]`) + Σ(colonist transport credits actually spent per owned planet) + Σ(citadel construction credits actually spent per owned planet, `planet-ownership.md`). Base price / sunk-cost throughout, never a live lookup or a re-derived "current value" — the latter throws for any held item not currently traded anywhere and would make net worth swing on a single distant transaction; a citadel has no market anywhere pricing it, so its recorded construction cost is the only real number available. A ship's own purchase-cost-by-tier already reflects its installed components' quality, so component value isn't separately double-counted for installed components — only uninstalled ones sitting in inventory are valued via the base-price sum above. **Scoped to resources, components, ships, and (added in this pass) planet-ownership investment** — scanners and crew are still deliberately not included; extending to them remains new scope.
- **Trading volume** — total credits transacted through listings (`purchaseListing()`) **and** instant sell-to-market transactions (`sellToMarket()`, `planetary-markets.md`) — both summed the same way, so a player using either or both trading paths accumulates volume identically. (The original version of this bullet only counted listings, written before `sellToMarket()` existed — closed in this pass.)
- **Highest crafted tier achieved** — best single crafted item ever produced, tracked via a max() over crafting history.
- Second wave, not required at launch: fleet strength, combat record, exploration (planets discovered), crew empire.

A separate, identity-attached report from the same daily cadence: `{ playerId, netWorth, tradingVolume, highestCraftedTier, ... }`. **One backend, three genuinely separate report types and pipelines** (registry, pricing, leaderboard) — sharing infrastructure (all three need something outside any single browser client) without sharing data; contaminating the anonymous pricing pipeline with the leaderboard's identity-attached data would break its one real guarantee. The registry's `galaxyToken` is not itself identity-attached (it can't be traced to a player), but it's still kept out of the pricing report's own item-keyed payload — a deliberate belt-and-suspenders separation, not a strict necessity.

### New infrastructure, named honestly
This is **the first thing in the entire project that requires an actual backend** — every system before this milestone is a self-contained browser client. Exact hosting/technology and whether a report fires because the player's client is running vs. server-side regardless are explicitly left open, tied to the eventual app-conversion timing, not to this contract. (Report *frequency* itself — daily — is decided, not open; only the trigger mechanism is.)

## Must NOT Do

- Must not include a `playerId` anywhere in the pricing-layer report payload, under any framing — structural anonymity as to player identity is the whole guarantee; a "just for debugging" field would break it.
- Must not let `galaxyToken` be derived from, combined with, or made reversible to `playerId` — it exists solely for galaxy-counting/de-duplication, never as a backdoor identity link.
- Must not let the Universe assign, suggest, or vary a galaxy's `PLANET_COUNT` — registry-only, recorded after the fact, never a precondition for local generation.
- Must not compute the per-capita denominator from a period's report count, or from the total-ever-registered count — the correct source is the recently-active subset (`lastReportedAt` within `GALAXY_ACTIVE_WINDOW_DAYS`); each of the other two has its own failure mode (report-count undercounts quiet-but-real galaxies, total-ever-registered dilutes toward inert as abandoned saves accumulate).
- Must not delete or expire a `galaxyToken` from the registry itself — registration is permanent (the "total ever" census stat depends on it); only the *per-capita formula's* denominator filters to an active subset, the registry itself never forgets a galaxy.
- Must not report a fixed prior-24h window — always accumulate since the galaxy's own `lastReportedAt`, so an offline gap never silently drops signal.
- Must not merge the registry, pricing-layer, and leaderboard data flows into one report or one pipeline.
- Must not implement any shared real-time presence, live position sync, or conflict resolution.
- Must not implement market manipulation *detection* — still deferred (`planetary-markets.md` restates the same boundary); this file computes an aggregate modifier, it does not police individual player behavior.
- Must not restrict the pricing-layer report to tier 1-5 — that ceiling is `galactic-market.md`'s listing-mechanism-specific rule, not a universal data-scope rule.
- Must not value net worth's inventory component via a live `getGlobalPrice()` call, must not re-derive a "current value" for an owned planet/citadel (sunk-cost only), and must not include scanners or crew in net worth without a new, explicit decision to extend that scope.
- Must not let trading volume count only `purchaseListing()` — `sellToMarket()` transactions count identically.
- Must not change `getGlobalPrice()`'s existing guarantees (global buy never beats best planet sell, and vice versa) — the universal modifier is one more multiplicative input on top of the existing computation, never a replacement for it, and must default to a neutral 1.0× before any real report data exists.
- Must not begin implementation before the app-conversion timing decision is actually made — this file documents a locked *design*, not authorization to start building.

## Testing Requirements (once built)

- Registry: a fresh game generates exactly one `galaxyToken`, never regenerated on subsequent loads of the same game; the total-ever-registered count increments exactly once per genuinely new galaxy, never per report, and never decrements.
- Active-window filtering: a galaxy with `lastReportedAt` older than `GALAXY_ACTIVE_WINDOW_DAYS` is excluded from the per-capita denominator but still present in the total-ever-registered count; a galaxy that reports again after a long gap is immediately counted active again, with no separate re-activation step.
- Catch-up reporting: a galaxy offline for N days reports N days of accumulated activity in its next report, verified against a case where a fixed-24h-window implementation would have silently dropped the earlier days.
- `computeUniversalModifier()`: per-capita normalization uses the active-galaxy count, not report count or total-ever-registered; floor/ceiling bounds hold under extreme input, mirroring `applyDrift()`'s own floor/ceiling tests exactly; returns a neutral 1.0× with zero reports.
- Net worth: matches a hand-calculated sum across a known inventory + ship roster + planet-ownership investment, using base prices, per-tier ship costs, and recorded colonist/citadel spend exactly as specified — no live-price or re-derived-value dependency anywhere.
- Trading volume: a player using only `sellToMarket()` (never `purchaseListing()`) accumulates non-zero volume, verified directly — the exact regression case this pass's fix targets.
- A negative test proving the pricing-layer report shape has no field capable of carrying a `playerId`, and that `galaxyToken` never appears alongside identity-attached leaderboard data in the same payload.
- Regression: `getGlobalPrice()`'s existing invariants (buy/sell never beating the best planet price) still hold with a universal modifier applied.

## Definition of Done (once built)

- Every player's local galaxy experience is provably unchanged by this feature's existence, including registration — read-only signal aggregation and a one-time registry write, never a live shared state or a generation-time dependency.
- `getGlobalPrice()`'s pre-existing guarantees are provably intact with the universal modifier active, on day one (neutral 1.0×) and after real report data accumulates.
- The pricing-layer report contains no player-identifying data, verified structurally, not by policy; the registry's `galaxyToken` is provably never linkable to a player.
- The per-capita denominator is provably immune to long-term dilution from abandoned galaxies — an active-window test spanning a simulated long game lifetime shows the modifier stays meaningful, not inert.
- A missed report is provably never lost signal — a catch-up report after an offline gap covers the full accumulated period.
- Net worth, trading volume, and highest crafted tier are each computed by an exact, specified formula — including planet-ownership investment and `sellToMarket()` activity — no leaderboard category ships with an undefined or incomplete valuation method.
- Leaderboards are computed from a genuinely separate report/pipeline than the registry/pricing layer, with zero data crossover.
