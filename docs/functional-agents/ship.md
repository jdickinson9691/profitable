## Responsibility

Give a player one screen showing everything about their current ship — name, tier, location, all 4 component slots and each one's real gameplay effect, fuel level/capacity, cargo hold capacity, and (new) its crew roster and role slots — and implement the mechanics that currently have no code behind them at all: fuel, cargo capacity, and ship-assigned crew roles. Must not duplicate or reimplement anything `deriveShipTier()`, `assembleShip()`, `calculateTravelTime()`, or the existing crew system already do; this agent adds new stats/slots and one new screen, not a parallel ship or crew model.

The existing 4-slot `components` shape (`weapon`/`engine`/`shield`/`cargoHold`, each `ShipComponent | null`) is unchanged — Cargo Hold Capacity's own design entry confirmed a single `cargoHold` slot stays a single slot.

## Outputs

### Schema amendment (Agent 1 style — new fields and constants)

Two new fields on `Ship` (`src/data/types/ship.ts`):
```ts
export interface Ship {
  // ...existing fields unchanged...
  fuelCapacity: number;   // derived from ship.tier, recomputed same moment deriveShipTier() is
  currentFuel: number;    // mutated by initiateVoyage() and refuelShip() only
}
```
One new field on the `Voyage`-adjacent cargo path is **not** added here — `VoyageCargoItem`/`Voyage.cargo` already exist (`src/data/types/voyage.ts`); Cargo Hold Capacity is a *check* against the existing shape, not a new field.

New constants (`src/data/constants/shipsAndTravelConfig.ts`, same file every other ship/travel constant already lives in):
- **`FUEL_CAPACITY_BY_TIER: readonly { tier: TierColor; capacity: number }[]` — retuned on a later review pass: Grey 50, White 65, Green 80, Blue 100, Purple 125, Orange 155, Gold 190** (was 150→500; see `profitable-design-questions.md`'s Ship Fuel section, "Amendment — Fuel Management," for the full reasoning). Chosen so a low/mid-tier ship (Grey/White/Green) cannot always reach the galaxy's single worst-case route in one hop, while Blue and above always can (100 > the ~85-fuel worst case) — the numeric line where fuel becomes a genuine routing constraint rather than a non-factor at every tier.
- `FUEL_COST_PER_DISTANCE_UNIT: number = 0.03` (mutable `let` + setter, same pattern as `DISTANCE_TO_TRAVEL_HOURS_PER_UNIT`) — **unchanged**; only capacity was retuned, not the cost formula, to avoid also disturbing refuel-cost economics.
- `REFUEL_COST_PER_UNIT: number = 2` (mutable `let` + setter) — unchanged; a full Grey tank from empty now costs at most 100cr (50 × 2), down from 300cr, consistent with the smaller tank rather than a repricing.
- **`STARTING_SHIP_FUEL_CAPACITY: number = 100`** — a flat, narrowly-scoped exception: the very first, pre-assigned starting ship's `fuelCapacity`/`currentFuel` are set to this value instead of `FUEL_CAPACITY_BY_TIER[Grey]`'s new, tighter 50, so a bad-seed roll can never make `secondaryDiscoveredPlanet` (`galaxy.md`) structurally unreachable from `startingPlanet` before the player has any way to afford repeated refueling. Expires naturally on the ship's first component change, once `deriveFuelCapacity()` starts reading the normal tier table again (`assembleShip()`'s existing "recompute on change" behavior) — not a permanent Grey-tier buff, only a one-time bootstrap headroom. Same shape as `galaxy.md`'s `discovered: true` override and `planet-ownership.md`'s colonist pre-population: a bootstrap exception, not a change to the general rule.
- `CARGO_HOLD_CAPACITY_BY_TIER: readonly { tier: TierColor; capacity: number }[]` — Grey 5, White 8, Green 12, Blue 18, Purple 25, Orange 35, Gold 50 (originated defaults).

All five follow the existing tunable-constant convention (`export let` + a same-name `setXxx()` function) so the Debug/Tuning panel (`src/presentation/debugTuningRegistry.ts`) can expose them the same way every other balance constant already is — adding the corresponding `TuningSection` rows is this agent's job too, not a separate one.

### Core amendment (Agent 20 style — new pure functions)

- **`calculateFuelCost(origin: Planet, destination: Planet): number`** (new file, `src/ships/calculateFuelCost.ts`, same directory/shape as `calculateTravelTime.ts`) — `calculateDistance(origin.position, destination.position) * FUEL_COST_PER_DISTANCE_UNIT`. Pure, no `Ship` parameter (fuel cost is not tier-modified — see design entry for why).
- **`deriveFuelCapacity(tier: TierColor): number`** (new file or co-located with `deriveShipTier.ts`) — looks up `FUEL_CAPACITY_BY_TIER`, same shape as `tierMidpoint()`. Called by `assembleShip()` (or a thin wrapper around it) so `ship.fuelCapacity` recomputes at the same moment `ship.tier` does, on every component change — never left stale. **Never called for the starting ship's initial values** — those are set directly to `STARTING_SHIP_FUEL_CAPACITY`, bypassing this lookup entirely; the very next `assembleShip()` call (the ship's first component change) is what first routes the ship through `deriveFuelCapacity()`'s normal tier table, ending the bootstrap exception naturally.
- **`initiateVoyage()` amendment** (`src/ships/initiateVoyage.ts`) — two new precondition checks added before the existing logic, both hard rejections (throw, same pattern as `assembleShip()`'s category-mismatch check), never a partial/silent success:
  - Fuel: reject if `ship.currentFuel < calculateFuelCost(originPlanet, destinationPlanet)`. On success, deduct the cost from `ship.currentFuel` in the same call.
  - Cargo: reject if the sum of the supplied `cargo: VoyageCargoItem[]`'s `quantity` fields exceeds the ship's `cargoHold`-tier capacity (`CARGO_HOLD_CAPACITY_BY_TIER`; a ship with no `cargoHold` component installed gets Grey-tier capacity, same "no components → Grey" rule `deriveShipTier()` already uses for consistency, not a separate zero-capacity special case).
  - Existing `arrivesAt`/travel-time computation is otherwise **completely unchanged** — both new checks run before it, neither touches it.
- **`refuelShip(ship: Ship, wallet: Wallet, amount: number): RefuelShipResult`** (new file, `src/ships/refuelShip.ts`) — same shape as `purchaseScanner()`: checks `wallet.credits >= amount * REFUEL_COST_PER_UNIT`, checks `ship.currentFuel + amount <= ship.fuelCapacity` (rejects an over-fill, doesn't silently clamp), deducts credits, adds fuel, returns a typed success/failure result. No pool, no tier-rolled candidate, no refresh interval — a flat-rate resupply available at any planet with a shipyard, per the design entry.

- `REPAIR_ELAPSED_TIME_CAP_HOURS: number` — a new, independent cap constant for `resolveComponentRepair()`'s elapsed-time window, not a reuse of crew's `ELAPSED_TIME_CAP_HOURS` — same "reuse the shape, not the literal constant" discipline this project follows whenever a pattern crosses a system boundary (crew's background-crafting cap and this repair cap can be tuned independently even though they share a shape).

**Core amendment:**
- **`getCrewSlotsForShip(ship: Ship): CrewSlotsByTierEntry`** (built, `src/ships/getCrewSlotsForShip.ts`) — looks up `CREW_SLOTS_BY_TIER[deriveShipTier(ship)]`. Pure lookup, no side effects, same shape as `deriveFuelCapacity()`. As built, returns the existing `CrewSlotsByTierEntry` type directly (Agent 1 amendment) rather than a separately-named `CrewSlotAllocation` type.
- **`assignToShipRole(crewMember: CrewMember, ship: Ship, role: ShipCrewRole, currentRoster: readonly CrewMember[]): AssignShipRoleResult`** (new file, `src/ships/assignToShipRole.ts`) — mirrors `assignToCraft()`'s shape (operates on an already-hired, idle `CrewMember`; never touches hiring/pool/wage code). Rejects if: the role isn't one of the ship's currently-allocated slots per `getCrewSlotsForShip()`; the slot is already full (checked against `currentRoster` filtered to this ship+role); `role === "Crafter"` and `crewMember.profession === null`. On success, sets `shipRole`/`assignedShipId`; does **not** change `status`/`assignedCraftId` — a ship-role assignment and a craft assignment are independent, per the "must not gate the other 4 roles" decision, though a `Crafter`-role assignment and simultaneously being `assignToCraft()`'d elsewhere would be a real conflict worth a follow-up decision if it comes up in implementation (not resolved here).
- **`Pilot` effect**: a new tier-keyed table (e.g. `PILOT_SPEED_BONUS_BY_TIER`) read by `calculateTravelTime()` when the ship has a crew member with `shipRole === "Pilot"` assigned — multiplies on top of `SHIP_TIER_SPEED_MODIFIER`, never replaces it.
- **`Combat Engineer` effect**: read by `resolveCombatChoice()` when present — reduces `COMBAT_COMPONENT_DURABILITY_DAMAGE_PERCENT`/`COMBAT_CREW_UNAVAILABLE_DURATION_HOURS` by a tier-scaled percentage on a loss. Never affects the win/lose roll itself.
- **`Science Officer` effect**: read by `performScan()` when present — an additional radius bonus stacking with `SCANNER_TIER_RADIUS_BONUS`.
- **`Systems Engineer` effect, and the resolved 3-way repair interaction (Systems Engineer / Citadel Level 3 / Crafter) — previously left open in three places, resolved together on this review pass, not incrementally.** `resolveComponentRepair(ship, ownedCrew, activeVoyage, dockedPlanet, currentTime)` (new file, `src/ships/resolveComponentRepair.ts`) — same "derive from elapsed hours since a stored timestamp, capped, no background job" shape `resolveBackgroundCrafting()` already established, applied to a new `Ship.lastRepairedAt: number` field (mutated only by this function, same "own field, own writer" pattern `currentFuel`/`ship.tier` already follow). `activeVoyage: Voyage | null` and `dockedPlanet: Planet | null` are explicit parameters, never looked up internally — `Ship.currentPlanetId` alone can't distinguish "docked here" from "mid-voyage, origin still shown" (`ship.ts`'s own comment: "the Voyage record itself is what represents 'currently in transit'"), so the caller must resolve and pass which state currently applies, matching this codebase's "no hidden lookups in a pure function" convention everywhere else.
  - **Three independent rate sources, summed into one combined per-category rate, each gated by its own availability condition — not a single shared rate:**
    - **Systems Engineer** (`SYSTEMS_ENGINEER_REPAIR_RATE_BY_TIER`, new tier-keyed constant) — **unconditional**, applies to *any* damaged category regardless of `activeVoyage`/`dockedPlanet`, exactly mirroring `resolveBackgroundCrafting()`'s own location-independence (a crew member's ongoing work isn't gated by where the ship physically is).
    - **Citadel Level 3** (`CITADEL_LEVEL_3_REPAIR_RATE`, new flat constant — a level, not a tier, so no tier table) — **only when `activeVoyage === null` and `dockedPlanet.citadelLevel >= 3` and `dockedPlanet.ownedByPlayerId === ship.ownerId`** (`planet-ownership.md`). Applies to *any* damaged category while that condition holds.
    - **Crafter (Weaponsmith/Engineer/Shield Technician/Cargo Specialist)** (`CRAFTER_REPAIR_RATE_BY_TIER`, below) — **only when `activeVoyage !== null`** (the design entry's own literal wording, "while traveling"), and only to the *one* category matching the assigned crew member's profession.
  - **Citadel and Crafter-role repair structurally never overlap with each other** — a ship is either traveling (`activeVoyage !== null`) or docked (`dockedPlanet` meaningful), never both, per `Ship.currentPlanetId`'s own documented semantics. Each independently stacks additively with Systems Engineer (whose unconditional rate applies in both states), but the three-way case the original "left open" notes worried about never actually occurs simultaneously — it's two separate two-way combinations, not one three-way one.
  - **No sub-interval blending across a mixed elapsed window** — if a ship was traveling for part of the time since `lastRepairedAt` and docked for the rest (e.g., the player was offline across a voyage and a subsequent dock), the rate is determined **once**, by whichever state is true *at the moment `resolveComponentRepair()` is called*, and applied to the **entire** capped elapsed window — not reconstructed per sub-interval. This matches every other elapsed-time function in this codebase (`resolveBackgroundCrafting()`, `applyRecovery()`, the resource reset cycle): a single rate/state resolved once per check, never a historical replay. Less precise than a true segmented calculation, but consistent with the one pattern this whole codebase already uses everywhere else for "time passed while the game wasn't being watched."
  - The first mechanic anywhere that restores component durability after combat damage.
- **`Crafter` effect**: **corrected on review — the previous wording here ("applies a small bonus to the matching component category") didn't match what the design entry actually decided**, and read as a `craft()`-formula bonus, which it isn't. The real decision is two structurally different effects depending on profession:
  - **Weaponsmith/Engineer/Shield Technician/Cargo Specialist → a repair effect on their own ship's matching-category component**, reusing `resolveComponentRepair()` (Systems Engineer, above) — **gated to only accrue while `activeVoyage !== null`** (the design entry's literal "while traveling" wording), and scoped to *only* the one component category matching the crew member's profession, rather than any damaged component. Stacks additively with Systems Engineer's unconditional rate when both are assigned; see `resolveComponentRepair()` above for the full resolved 3-way (Systems Engineer / Citadel / Crafter) combination rule, including why Citadel and this effect never actually overlap with each other. **Honesty note, matching this file's own Citadel-Level-1-style disclosure elsewhere**: today, only the weapon component's `qualities.durability` is ever reduced by anything (`resolveCombatChoice()`'s Lose outcome) — engine/shield/cargoHold have no current damage source, so Engineer/Shield Technician/Cargo Specialist's repair effect is real but presently inert for most ships until/unless a non-combat damage source exists for those categories.
  - **`Artisan` → a material-quantity discount on general (non-component) recipes, applied entirely upstream of `craft()`, in `CraftScene`, before `craft()` is ever called** — reduces the recipe's required input quantity for a matching recipe when an assigned Artisan is aboard the active ship. **`craft()` itself is never touched** — no new parameter, no crew read anywhere inside `src/simulation/craft.ts` — keeping `crafting.md`'s existing crew-agnostic contract exactly true, with zero exception. **Chosen over a `craft()`-formula bonus** (which would have required amending `craft()`'s signature and crafting.md's own "free UI selection, crew-agnostic" contract) specifically to keep this the one Crafter sub-effect that adds no new dimension to the crafting formula itself — cheaper to make, never better/more-consistent quality, a genuinely different axis from `crafterTier`/`schematicTier`.
  - See also `docs/functional-agents/crafting.md`'s own cross-reference note confirming `craft()` remains fully crew-agnostic after this change.

**Presentation:** the new `ShipStatusScene` (above) gains a "Crew" section listing each of the ship's currently-allocated slots (per `getCrewSlotsForShip()`), showing the assigned crew member (name/tier) or "(empty)", with an **`> Assign`** action per empty slot (picking from the player's idle roster) and an **`> Unassign`** action per filled one. `CrewScene.ts` gains a per-member indicator when `assignedShipId` is set, so a ship-assigned crew member doesn't silently disappear from the crew roster view.

## Must NOT Do

- **Must not add a 5th `ComponentCategory` or fold fuel/cargo capacity into an existing component's `qualities`.** Fuel and cargo capacity are `Ship`-level stats derived from tier, not component-level stats — the same "ship tier vs. component tier" boundary Combat's weapon-specific departure already drew a hard line around; this agent does not blur it back.
- **Must not let a voyage fail, strand, or recompute `arrivesAt` mid-flight for fuel or cargo reasons** — both are precondition checks at `initiateVoyage()` only, per the design entries' explicit rejection of a mid-voyage failure state (same reasoning Hazard's design already used to keep `arrivesAt` locked).
- **Must not scope cargo hold capacity to general inventory (Mine/Refine/Craft/Market)** — `Voyage.cargo` only, per Cargo Hold Capacity's explicit scope decision. Must not add a size cap to `src/presentation/inventory.ts`.
- **Must not consume an inventory item as fuel** — fuel is an abstract `Ship`-level number (`currentFuel`), never a draw against `fuel-canister`/`enriched-fuel-rod`/`high-yield-fuel-core` or any other resource batch. That was a real option, explicitly rejected in the design entry — reopening it here would contradict a decision already made, not extend it.
- **Must not touch `refine()`/`craft()` internals, galaxy/planet generation, trading logic, or crew logic** — same hard boundary every phase since Phase 2 has restated; this agent only adds to `Ship`/travel/crew *assignment*, never the crew system's own hire/wage/upkeep/attrition formulas.
- **Must not implement rendering, input, save/load, or audio inside the core amendment files** (`calculateFuelCost.ts`, `refuelShip.ts`, `assignToShipRole.ts`, `getCrewSlotsForShip.ts`, the `initiateVoyage()` changes) — pure, framework-agnostic TypeScript only, same as every existing file in `src/ships/`.
- **Must not hardcode any new constant outside `shipsAndTravelConfig.ts`** — the same "one place a value changes" rule every prior amendment has followed.
- **Must not add a 5th `ComponentCategory` for crew capacity** — `CREW_SLOTS_BY_TIER` is keyed by the ship's derived tier, exactly like `FUEL_CAPACITY_BY_TIER`, never by a component.
- **Must not let `assignToShipRole()` create, hire, pay, or dismiss a `CrewMember`** — it only mutates `shipRole`/`assignedShipId` on an already-existing, already-hired crew member.
- **Must not let a `Crafter`-role assignment succeed for a crew member with `profession === null`** — tier 1-5 crew are eligible for the other 4 roles, never this one.
- **Must not let a crew member hold two ship-role assignments simultaneously** — `assignToShipRole()` must clear any prior assignment for that crew member first.
- **Must not let any of the 5 role effects (Pilot/Combat Engineer/Science Officer/Systems Engineer/Crafter) replace an existing formula's primary driver** — each stacks as an additional modifier (Pilot alongside `SHIP_TIER_SPEED_MODIFIER`, Science Officer alongside `SCANNER_TIER_RADIUS_BONUS`, Combat Engineer as mitigation only, never touching the win/lose roll itself) rather than substituting for it.
- **Must not let a Weaponsmith/Engineer/Shield Technician/Cargo Specialist Crafter-role repair effect touch any component category other than the one matching their profession** — a Weaponsmith aboard repairs weapon durability only, never engine/shield/cargoHold, even if those happen to be damaged by some future mechanic; cross-category repair is Systems Engineer's job exclusively.
- **Must not let Artisan's crafting discount add a parameter to `craft()`, read any crew data inside `src/simulation/craft.ts`, or otherwise compromise `crafting.md`'s crew-agnostic contract** — the discount is computed and applied to the recipe's required input quantity entirely in `CraftScene`, before `craft()` is invoked; `craft()` must remain provably unaware any crew system exists.
- **Must not let `resolveComponentRepair()` look up `activeVoyage`/`dockedPlanet` internally** — both are required, explicit parameters; the function must not query `SaveSystem`, a voyage store, or any other hidden state to determine whether the ship is currently traveling or docked.
- **Must not let the Crafter repair effect and the Citadel Level 3 repair effect both apply to the same `resolveComponentRepair()` call** — structurally enforced by their mutually-exclusive gates (`activeVoyage !== null` vs. `activeVoyage === null && dockedPlanet` meaningful), never by an explicit `if` guarding one against the other; if a future change ever made "traveling" and "docked" not mutually exclusive, this would need revisiting, not silently left to coincidentally still work.
- **Must not reconstruct a mixed elapsed window by state (part-traveling, part-docked) into separate segments** — one rate, resolved once from the state true at call time, applied to the whole capped elapsed window, matching `resolveBackgroundCrafting()`'s own precedent exactly.
- **Must not reuse `ELAPSED_TIME_CAP_HOURS` (crew's background-crafting cap) for `resolveComponentRepair()`** — a new, independent `REPAIR_ELAPSED_TIME_CAP_HOURS` constant, even though both share the same "cap the catch-up window" shape.
- **Must not initialize a new game's starting ship via `deriveFuelCapacity(tier)`** — it must be set directly to `STARTING_SHIP_FUEL_CAPACITY`, bypassing the normal tier lookup entirely; calling `deriveFuelCapacity()` for the starting ship would silently reintroduce the softlock risk this constant exists to prevent.
- **Must not let `STARTING_SHIP_FUEL_CAPACITY` persist past the starting ship's first component change** — `assembleShip()`'s existing recompute-on-change behavior must overwrite it with the normal `FUEL_CAPACITY_BY_TIER` value at that point; a bootstrap exception that never expires would be a permanent, undocumented Grey-tier buff, not a one-time grace.

## Testing Requirements

- `calculateFuelCost()` matches a hand-calculated value for a known origin/destination pair (same style as `calculateTravelTime()`'s own hand-calculated test).
- `deriveFuelCapacity()` returns the exact **retuned** `FUEL_CAPACITY_BY_TIER` value for every tier, including the "no components installed → Grey" case.
- **The retuned capacity table's actual constraint, verified numerically, not just asserted:** the galaxy's worst-case single-trip fuel cost (`calculateDistance()` at the max possible diagonal × `FUEL_COST_PER_DISTANCE_UNIT`) exceeds Grey/White/Green's capacity and is at or under Blue/Purple/Orange/Gold's — a real regression test locking in "Blue is the first always-reachable-in-one-hop tier," not a claim that could silently drift if either constant changes independently.
- **`STARTING_SHIP_FUEL_CAPACITY`**: a freshly-created starting ship's `fuelCapacity`/`currentFuel` both equal this constant, not `FUEL_CAPACITY_BY_TIER[Grey]`; the value comfortably exceeds the worst-case single-trip cost computed above (the actual softlock-prevention guarantee, verified numerically); after the starting ship's first `assembleShip()` call (any component swap), `fuelCapacity` matches the normal Grey-tier value from the table instead — the bootstrap exception is provably temporary, not a standing rule.
- `initiateVoyage()`: rejects when `currentFuel` is below cost (and does **not** mutate `currentFuel` on rejection); succeeds and deducts exactly the computed cost when sufficient; rejects when supplied cargo quantity exceeds `cargoHold` capacity; a ship with no `cargoHold` component gets Grey-tier cargo capacity, not zero.
- `refuelShip()`: rejects on insufficient funds (no state mutated); rejects on over-fill past `fuelCapacity` (no partial/clamped refuel); succeeds and mutates both `wallet.credits` and `ship.currentFuel` correctly together.
- `getCrewSlotsForShip()`: returns the exact `CREW_SLOTS_BY_TIER` allocation for every tier, including the Blue-tier "both Combat Engineer and Science Officer at once" case.
- `assignToShipRole()`: rejects when the role isn't currently allocated for the ship's tier; rejects when the target slot is already full; rejects a `Crafter` assignment for a `profession === null` crew member; succeeds and correctly clears any prior assignment for that crew member; never mutates `status`/`assignedCraftId`.
- Each role effect (Pilot/Combat Engineer/Science Officer/Systems Engineer/Crafter): present vs. absent produces a measurably different, correctly-directioned result in the function it modifies, with the underlying formula's own existing tests still passing unmodified when no role-holder is assigned (the "stacks, never replaces" guarantee, verified not just asserted).
- **Crafter (Weaponsmith/Engineer/Shield Technician/Cargo Specialist)**: repairs only the matching component category, verified by asserting the other 3 categories are unaffected even when damaged; stacks additively with a simultaneously-assigned Systems Engineer; zero effect when `activeVoyage === null` (docked), even if otherwise eligible.
- **Crafter (Artisan)**: `CraftScene`'s required-input-quantity for a general recipe is reduced when an Artisan is assigned to the active ship, unchanged otherwise; `craft()`'s own test suite (`crafting.md`) passes completely unmodified — a real regression check that this effect never reaches `craft()` itself, not just a documentation claim.
- **`resolveComponentRepair()` — the resolved 3-way interaction:**
  - Systems Engineer alone (docked or traveling): repairs any damaged category at `SYSTEMS_ENGINEER_REPAIR_RATE_BY_TIER`.
  - Docked at an owned Level 3 Citadel, no Systems Engineer: repairs any damaged category at `CITADEL_LEVEL_3_REPAIR_RATE` alone.
  - Docked at an owned Level 3 Citadel, with a Systems Engineer assigned: combined rate is the **sum** of both, verified as strictly greater than either alone (the "repairs faster with one" guarantee, `planet-ownership.md`).
  - Traveling, Systems Engineer + a category-matching Crafter both assigned: that one category's combined rate is the sum of both; every other damaged category gets Systems Engineer's rate only.
  - Traveling, Citadel condition unreachable (not docked) even if the ship happens to be at a planet with an owned Level 3 Citadel mid-voyage in some edge case — `dockedPlanet` must be `null` whenever `activeVoyage !== null`, enforced by the caller, verified by a test that passing both non-null simultaneously is never a supported input.
  - A mixed-window case (docked when last checked, traveling now, or vice versa): the rate is resolved once from the **current** state and applied to the **whole** capped elapsed window — verified by constructing a scenario where the two possible rates would produce different output, and asserting only the current-state rate's result appears, never a blend.
  - `Ship.lastRepairedAt` updates to `currentTime` on every call, whether or not any repair actually occurred (no eligible crew/Citadel) — matching `resolveBackgroundCrafting()`'s own `updatedCrewMember`/`lastCheckedAt` unconditional-update behavior.
- Regression: `deriveShipTier()`, `assembleShip()`'s existing 4-category behavior, `calculateTravelTime()`, `resolveArrival()`, `resolveCombatChoice()`, `performScan()`, and the full existing crew suite (`hireCrew`/`assignToCraft`/`payUpkeep`/`checkAttrition`) are provably unchanged when no ship-role assignment exists — zero deviation across their full existing test suites.
- Presentation: `ShipStatusScene` reads every displayed value directly from Core's outputs — never recalculates any of them independently.

## Definition of Done

- A player can open a new **Ship** screen and see their active ship's name, tier, location, all 4 components with an honest description of each one's real effect, current/max fuel, cargo hold capacity, and its crew roster with each currently-allocated role slot filled or empty.
- A voyage cannot be initiated without enough fuel, verified against an insufficient-fuel attempt; a voyage cannot be initiated with more cargo than the ship's `cargoHold` tier allows. Neither ever produces a partial or stranded state.
- A player can refuel at a shipyard, paying the exact `REFUEL_COST_PER_UNIT`-derived cost, and cannot overfill past capacity or refuel without sufficient credits.
- A player can assign an idle, already-hired crew member to any of their ship's currently-allocated role slots (including the Crafter slot, only for crew with a profession), see that role's effect reflected the next time the relevant system is used, and unassign them again — with the assigned crew member still drawing wages and still subject to attrition throughout, exactly like any other hired crew member.
- `Ship.fuelCapacity` and the ship's crew-slot allocation are both provably always current after any component change, same as `Ship.tier` — never stale.
- Every pre-existing function this file's scope touches (Agent 2/8/11/16/20's functions, `refine`/`craft`, galaxy generation, trading, crew, ship/travel/combat/scanner) is provably unchanged when none of this file's new mechanics are in play — zero deviation across their full existing test suites.
- `craft()` (`crafting.md`) remains provably crew-agnostic after the Crafter role effect exists — zero new parameters, zero crew reads inside `src/simulation/craft.ts`, verified by its own unmodified test suite, not just asserted in prose.
- A combat-damaged component recovers durability over elapsed time whenever a Systems Engineer is assigned (anywhere), a category-matching Crafter is assigned (while traveling), and/or the ship is docked at an owned Level 3 Citadel — with multiple simultaneously-applicable sources provably summing rather than only the best one applying, and the Citadel/Crafter pairing provably never both active on the same check.
- Fuel capacity is a real routing constraint at low/mid ship tiers, provably not just a formality: at least one real route exists that a Grey-tier ship cannot complete in a single hop without refueling en route, while a Blue-tier-or-higher ship can always reach any discovered planet directly regardless of distance.
- A brand-new game's starting ship can always reach both `startingPlanet` and `secondaryDiscoveredPlanet` in a single hop each, regardless of how far apart the seed happened to place them — verified across many seeds, not assumed safe from the `STARTING_SHIP_FUEL_CAPACITY` value alone.
- Zero imports from any rendering, DOM, or browser-API library in any of this file's new core files.
