# Profitable — Open Design Questions

Derived from the executive summary draft. Organized by subsystem since answers in one area constrain the others.

**MVP Scope (decided):** the first vertical slice is a hardcoded single planet with 2-3 resource types, validating the quality-roll system, one refining recipe end-to-end, and one crafting recipe + schematic end-to-end. Galaxy/planet generation, the trading loop, crew crafters, travel, and the galactic map are all explicitly **post-MVP**, per the decided development order: galaxy generation → planet generation → resource generation → crafting recipes/schematics → trading loop → crafters → travel → map.

## Resources & the 5 Qualities

**Decided:**
- The 5 qualities are: **purity, density, potency, durability, rarity**.
- Qualities are universal (every resource type has all 5 defined), but not every quality is *applicable* to every resource type — e.g., gases would not have durability. Non-applicable qualities are represented as **null/NA in data, not zero** (zero would misleadingly imply "worst possible quality" rather than "doesn't apply"). If a recipe references a quality that's null/NA on one of its inputs, that reference **does not influence the crafting formula or output at all** — it's excluded from the calculation entirely, not treated as zero and not invalidating the input.
- Each quality is a **numeric value from 1-100**, mapped to a **7-tier color structure**: grey, white, green, blue, purple, orange, gold.
- Tier breakpoints (gradual curve):

| Tier | Range | Width |
|---|---|---|
| Grey | 1-40 | 40 |
| White | 41-60 | 20 |
| Green | 61-75 | 15 |
| Blue | 76-85 | 10 |
| Purple | 86-91 | 6 |
| Orange | 92-96 | 5 |
| Gold | 97-100 | 4 |

- Qualities roll **randomly** on gathering. Roll is further **modified by the planet** the resource is gathered from (set at planet generation) — full mechanics deferred to a future **Planets** section.
- All 5 qualities matter, but not every recipe requires all 5 — recipes will have **quality score requirements** per input (full mechanics defined under Crafting & Recipes/Schematics).
- The 5 qualities **persist for all items at every tier** — raw, refined, and crafted (tiers 1-7) all carry the same 5 qualities. No conversion into a separate stat system; no relabeling.
- **Color tier display differs by tier band:**
  - **Tiers 1-2 (raw/refined):** each of the 5 qualities gets its **own individual color tier**.
  - **Tiers 3-7 (crafted):** the 5 qualities are **aggregated into a single overall color tier**, used to represent the item's rarity/quality at a glance and to help determine its sell value in the market.
- Sell value for crafted items is intended to be driven by this same quality data (via the aggregate color tier), rather than a separate parallel value system.
- **Locked (2026-07-29): the crafted-item aggregate tier formula is a straight average of the 5 qualities, mapped through the same tier breakpoint table.** This was implemented as a "stub, exact aggregation formula is post-MVP" placeholder from the original MVP build (`src/simulation/aggregateTier.ts`), and two later sections (market listing tier, below; ship tier, in the Ships section) already explicitly reused it as "the same straight-average-to-tier formula already used for crafted items' aggregate color" — but this bullet itself never formally closed the "post-MVP" placeholder framing, leaving the stub language and the two sections that assumed it settled talking past each other. Formally locked now, during alpha content authoring, per `docs/profitable-alpha-content-roster.md`'s own recommendation ("no reason to treat this one differently" from ship tier / market listing tier, which already use straight average) — no formula change, since the code has done this since the MVP; this closes the documentation gap, not a design change.

## Refining

**Decided:**
- Refining is **n:1** — multiple units of a resource combine into one refined output (e.g., 2 iron ore → 1 iron bar). This also extends to **multiple different resources** as inputs to one refined output (e.g., 2 iron bars + 1 coal → 1 steel bar).
- Output quality is influenced by input quality: **higher-tier input resources increase the potential for higher-tier output**, rather than guaranteeing a 1:1 pass-through.
- Working formula: **Option A — Weighted average with variance.** Output quality = average of input qualities (weighted by quantity if inputs differ), then a random +/- variance is applied. **Mixed-quality/mixed-resource inputs combine via straight average** (weighted only by quantity, not skewed toward best/worst input) — chosen because the already-decided threshold penalty separately handles punishing weak individual inputs, so weighting toward worst would duplicate that mechanism; straight average also keeps the first step of an already multi-stage formula simple. If a single standout input should matter more later, that's better handled via schematic bonus or crafter tier rather than the base combination math. **Variance is percentage-based: ±10% of the input average** (not a flat point range) — this scales naturally with the uneven tier-band widths (grey is 40 points wide, gold is only 4), so variance doesn't feel irrelevant at the bottom or disproportionately punishing at the top. This base ±10% is then narrowed by refiner tier (per the variance-reduction mechanic already decided) — e.g., a grey-tier refiner keeps close to the full ±10%, a gold-tier refiner narrows it substantially, making top-tier crafting more reliable in skilled hands.
- Refiners **have a skill/level system**, using the **same 7-tier color scale as resource quality**, and higher-tier refiners get bonuses to output via **variance reduction / ceiling raise**: refiner tier narrows the negative side of the variance roll and/or raises the achievable ceiling above what inputs alone would allow.
- **Working refiner/crafter tier variance table** (applies to both Refining and Crafting — an asymmetric adjustment to the base ±10% variance, narrowing the downside more than it extends the upside, so bad luck becomes rare at high tiers while good luck becomes more possible, not just more likely):

| Tier | Negative side | Positive side |
|---|---|---|
| Grey | -10% | +10% |
| White | -8% | +10% |
| Green | -6% | +10% |
| Blue | -4.5% | +11% |
| Purple | -3% | +12% |
| Orange | -1.5% | +13% |
| Gold | -0.5% | +15% |

This same table applies to **crafter tier** in the unified crafting formula as well, keeping the two production roles mechanically consistent.
- **No loss/waste** — refining yield is 100%, with one exception: **quality can increase effective yield via a chance of material refund**. Above a quality threshold, each refining action has a chance to refund 1 (or more) of the consumed input units, scaling with input/refiner quality tier. **Working refund chance curve**, keyed to the tier the refining formula's *output* actually lands on (post-variance, post-refiner-tier) rather than the raw input tier — so a skilled refiner consistently landing near gold output gets rewarded even from mediocre inputs:

| Tier | Refund chance (per consumed unit) |
|---|---|
| Grey | 0% |
| White | 0% |
| Green | 5% |
| Blue | 10% |
| Purple | 15% |
| Orange | 20% |
| Gold | 25% (plus a secondary ~20% chance the refund is 2 units instead of 1) |
- Refining **cannot fail** — no failure chance, no degraded/salvage outcome. Given the inputs, refining always succeeds.

## Crafting & Recipes/Schematics

**Decided:**
- Recipes are **not fixed to specific materials**. Instead, a recipe specifies a **category + recommended quality threshold** per input (e.g., "metal bar, durability 60+"). Inputs below the recommended threshold are still usable, but reduce the quality of the crafted output, via **scaled penalty below threshold** (penalty multiplier scaling with how far below threshold an input falls). **Working penalty curve** (escalating, with a hard floor):

| Points below threshold | Output penalty multiplier |
|---|---|
| 0 (at/above threshold) | 1.0 (no penalty) |
| 1–10 | 0.95 |
| 11–20 | 0.85 |
| 21–30 | 0.70 |
| 31–40 | 0.50 |
| 41+ | **Hard floor — input rejected**, craft cannot proceed with this input |

The penalty steepens the further below threshold an input falls (5% → 10% → 15% → 20% per 10-point band), rather than a flat linear slope, and a hard rejection past 40 points below threshold keeps the recipe's category+threshold system meaningful rather than letting the penalty asymptote toward zero. This penalty is applied **last** in the crafting formula (see unified formula below), after crafter/schematic influence, and can be softened but not bypassed by the schematic's forgiveness bonus.
- Schematics are **unique items in their own right** — discoverable and purchasable from planetary markets, not just permanent unlocks.
- Schematic rarity mechanic: **bonus modifier**. The base recipe/output ceiling is the same regardless of schematic tier, but higher-tier schematics grant a bonus to the crafting formula (reducing the threshold penalty, or improving the variance roll). Rewards owning a higher-tier copy of the same schematic without changing its ceiling. **Working schematic tier contribution** (additive, stacking on top of crafter tier's shared asymmetric variance table, but deliberately smaller in scale — a schematic is closer to equipment than to a skill investment):

| Tier | Ceiling raise (+ to positive side) | Variance narrowing (- to negative side) | Threshold-penalty forgiveness |
|---|---|---|---|
| Grey | +0% | -0% | 0% |
| White | +1% | -0.5% | 5% |
| Green | +2% | -1% | 10% |
| Blue | +3% | -1.5% | 15% |
| Purple | +4% | -2% | 20% |
| Orange | +5% | -2.5% | 25% |
| Gold | +6% | -3% | 35% |

**Forgiveness mechanic:** reduces the effective "points below threshold" before the penalty curve table is applied (e.g., a gold schematic's 35% forgiveness turns a 20-points-under input into an effective ~13-points-under) — softens but never fully erases the penalty, consistent with the earlier decision that great crafters/schematics can't fully compensate for bad inputs.

**Combined cap:** total combined ceiling raise from crafter tier (up to +15% at gold) plus schematic tier (up to +6% at gold) is **capped at +18% combined**, not +21% — keeps a maxed crafter + maxed schematic best-in-class without making input quality nearly irrelevant at the top of the game.
- Crafting **has randomness**, influenced by both **input resource quality** and **crafter skill** — not fully deterministic.
- **Working unified crafting formula** (combines input quality, threshold penalty, schematic bonus, and crafter skill into one pass):
  1. **Base average:** `base_avg` = weighted average of input qualities (Option A, same as Refining).
  2. **Ceiling raise:** crafter skill tier and schematic tier **both raise the achievable ceiling above `base_avg`, additively**. Crafter tier's contribution uses the **same asymmetric variance table as Refining** (see Refining section — narrows the downside, extends the upside by tier); schematic tier's contribution is a separate additive bonus on top of that.
  3. **Variance roll:** a random +/- variance is rolled around the raised ceiling; the *width* of that variance is narrowed by crafter skill tier (via the shared table) and schematic tier, also additively.
  4. **Threshold penalty (applied last):** *after* the roll from steps 1-3 produces a raw output value, apply the scaled penalty for under-threshold inputs — reduced by the schematic's forgiveness bonus. A great crafter and great schematic **cannot fully compensate for under-threshold inputs**, since the penalty is applied after their influence.
  5. `output = clamp(final penalized value, 1, 100)`
- Crafter skill is **not** a single universal skill — there will be **defined crafting skills/professions specifically for tier 6 and 7 crafters**. Lower tiers (3-5) may use a more general/shared skill, with specialization kicking in at the higher tiers.
- **Locked (2026-07-29): crafting a recipe with no owned schematic resolves `schematicTier` to Grey — not an error state, and not a separate bonus-free code path.** Gap found during the alpha content roster's craftability spot-check: `craft()` requires a `schematicTier` input (`agent-02-simulation-core.md`), but `docs/profitable-alpha-content-roster.md` §5 deliberately designates 5 recipes as known-by-default with **no** `Schematic` entity in `content/schematics.json` at all, and nothing before now specified what value to pass in that case. Resolved by observing that Grey's own row in the schematic tier contribution table above is already "+0% ceiling raise, -0% variance narrowing, 0% penalty forgiveness" — i.e., no bonus — so "no schematic owned" and "an owned Grey-tier schematic" are already mechanically identical outcomes. This requires no new formula or table, only a one-line resolution step (`resolveSchematicTier()`, `src/simulation/schematicTier.ts`: `schematic?.tier ?? "Grey"`), applied wherever a recipe's schematic is looked up before calling `craft()` (`CraftScene.ts`, `CrewScene.ts`). **Explicitly out of scope for this decision:** `ShipAssemblyScene.ts`'s existing, separate simplification for ship component recipes — schematicTier there is always player-selected directly via its own tier selector regardless of whether a real `Schematic` entity exists for that recipe (documented in that file's own comment since Phase 5) — is a different, pre-existing gap (schematic *ownership* is never actually checked/tracked for any of the 16 component recipes, not just the 5 known-by-default ones) and is not resolved by this note.

**Ideas for unique/special schematics (beyond the standard tiered set), kept for reference:**
- Unique/named schematics with fixed bonus properties, found via rare events/exploration.
- Planet-locked schematics (ties to Planets section).
- Degrading/limited-use schematics, consumed after N uses.
- Schematic fragments that must be combined to unlock the full recipe.
- Player-discovered variants from unusual crafting quality combinations.

## Galaxy & Planet Generation

**Status: MVP complete, this is the active phase.** The MVP used one hardcoded planet (Delta Rigelus) with no modifiers, seasons, or tier — deliberately thin, per Agent 1's minimal `Planet` type. This section is where that gets replaced with real generation.

**Carried over from Resources & Qualities:** qualities roll randomly on gathering, further modified by the planet the resource is gathered from — full mechanics were deferred to here.

**Carried over from Trading Market:** seasons (for the eventual galactic trade map) are determined at planet generation, based on the planet's tier — planet tier itself is now resolved (see Decided below).

### Decided

- **Planet tier quality roll modifier:** a flat additive modifier applied to the base 1-100 roll before clamping, tied to the same 7-tier structure used everywhere else:

| Planet Tier | Quality Roll Modifier |
|---|---|
| Grey | -15 |
| White | -8 |
| Green | +0 |
| Blue | +8 |
| Purple | +15 |
| Orange | +22 |
| Gold | +30 |

`rollQuality()` rolls 1-100 as normal, then this modifier is added before the final clamp to 1-100. Unlike the refiner/crafter/schematic tables (where Grey = no bonus, since those represent skill/equipment investment with a real zero state), **Green is the neutral point here** — a planet isn't something you level up, it's just a place, and most places should be unremarkable. Grey planets carry a genuine penalty, making Gold-tier planets real destinations worth traveling for (ties into the same exploration/exclusivity theme as tier 6-7 crafted goods and unique schematics). The scale is roughly double the refiner/crafter tables' spread since it stacks with (not replaces) those modifiers — a flatter planet modifier would barely register once refiner/crafter/schematic bonuses are also in play.
- **Planet tier determination:** planet tier is assigned via a **random roll (1-100) at generation time, mapped through the existing tier breakpoint table** (Grey 1-40 / White 41-60 / Green 61-75 / Blue 76-85 / Purple 86-91 / Orange 92-96 / Gold 97-100) — the same mechanism already used everywhere else (`getTierColor()`), rather than inventing a separate planet-rarity system. Because the tier bands are unequal width, this naturally produces mostly Grey/White/Green planets with rare Gold ones, without needing a separately designed distribution curve. Also keeps the color-tier mental model consistent for players across resource quality, refiner/crafter skill, and now planet quality.
- **Resource distribution across planets:** each planet has a **subset** of producible resources (matches the MVP's `Planet.producibleResourceIds` list shape — a list, not a "produces everything" flag), not a universal "every planet produces everything" model. This creates real reasons to explore/trade, consistent with the exclusivity theme already used for tier 6-7 crafted goods and unique schematics.
- **Planet type system (governs which resource categories are eligible on a given planet):** adapted from **NASA's real exoplanet classification system** (public-domain science, not fictional IP) rather than an invented or franchise-borrowed system. NASA groups exoplanets into four types — Gas Giant, Neptunian, Super-Earth, and Terrestrial — which map cleanly onto composition, and therefore onto which of the game's resource categories (solid/gas/crystal) a planet can produce:

| Planet Type (NASA-based) | Eligible Resource Categories |
|---|---|
| Terrestrial | Solid, Crystal |
| Super-Earth | Solid, Crystal, (occasionally Gas) |
| Neptunian | Gas, Crystal (icy) |
| Gas Giant | Gas |

  Planet Type is a **hard filter** on eligible categories, not a bias — a Gas Giant cannot roll a solid resource. Within the eligible categories for a given planet, a **random subset** of actual resources is drawn to populate that planet's `producibleResourceIds` list, and **the size of that subset scales with planet tier** (a Grey-tier Terrestrial world might get 1-2 solid/crystal resources; a Gold-tier one might get most or all of them) — giving tier a second axis of value (selection, not just quality roll) and reinforcing "Gold planets are real destinations" without a separate mechanic. Planet Type also sets up "specialties" (still open below) as a natural next layer rather than a competing system.
- **Resource subset selection rule:** subset size is **percentage-based (not a flat count)**, scaled by planet tier, applied against the number of resources eligible for that planet's type — consistent with the ±10% percentage-based approach already used for refining/crafting variance, so the rule doesn't need re-tuning as the resource roster grows:

| Planet Tier | % of eligible resources available |
|---|---|
| Grey | 20% |
| White | 35% |
| Green | 50% |
| Blue | 65% |
| Purple | 80% |
| Orange | 90% |
| Gold | 100% (all eligible) |

  `count = max(1, ceil(percentage × number_of_eligible_resources_for_this_planet_type))` — the `max(1, ...)` floor guarantees no planet ever has zero producible resources, and Gold at 100% means a Gold-tier planet of a given type is guaranteed to have every eligible resource for that type. **Selection within that count is a uniform random draw, no weighting** — there's no "common vs. rare resource" flag in the data model yet (only category and quality qualities), so weighting isn't possible without adding one; that would be a separate, smaller decision on the `Resource` type itself if wanted later.
- **Galaxy structure:** a **fixed, finite set of planets generated once** (not an infinitely expandable/streaming procedural system) — a fixed count is far simpler to test and balance, and nothing in the current design requires live/on-demand generation. Each planet gets a **simple position (e.g., x/y coordinate) at generation time**, even though travel is still post-MVP — cheap to add now, expensive to retrofit later, same reasoning as building the `NetworkAdapter` stub before multiplayer was in scope. **No formal "region" data structure yet** — a flat list of planets, each with a coordinate, is sufficient; regions/sectors (if wanted later, e.g. for trade map flavor) can be derived from coordinates after the fact rather than requiring a hierarchy to be designed now.
- **Planet specialties (Option A — per-resource specialty):** planets **tier White or higher** get exactly **one** specialty resource, randomly selected from their eligible pool, which receives a **flat +15 quality modifier** on top of the planet's regular tier modifier — roughly one full planet-tier step, so a specialty feels like "this planet is effectively one tier better, but only for this one resource." **Grey-tier planets never get a specialty**, keeping Grey genuinely unremarkable (consistent with Grey also having no refund chance and a quality penalty elsewhere in the design). Solves the "does the specialty always make it into the random subset" problem via a **reserved-slot rule** rather than inflating the subset count: the specialty is selected first, occupies one of the slots the existing percentage-based count formula already produces (unchanged), and the remaining `count - 1` slots are filled via the normal uniform random draw from the eligible pool minus the already-placed specialty. This keeps subset size a pure function of tier — a specialty planet doesn't quietly produce more resources overall than a non-specialty planet of the same tier, only a better version of one.
- **Planet tier scope: gathering only.** Planet tier's mechanical effect (the quality roll modifier, and the specialty bonus) applies **exclusively to the gather roll** — the refining and crafting formulas remain planet-agnostic, with no additional planet-tier stacking on top of the already-capped crafter tier + schematic tier (+18% combined). This keeps each tier system scoped to one job (planet tier → resource generation, refiner tier → refining, crafter/schematic tier → crafting), avoiding a fourth stacking modifier that would complicate an already carefully-tuned cap. Planet tier still drives real strategic decisions — better planets produce better raw inputs, which then flow through the unchanged downstream formulas — it just doesn't get re-applied at every step. Where to build refining/crafting operations becomes a logistics/convenience question (proximity, travel time, market modifiers) rather than a formula question.
- **Generation seed and naming:** galaxy/planet generation is **seeded by default**, consistent with Agent 2's existing contract requirement that every random function (`rollQuality`, `refine`, `craft`) be seedable/deterministic for testing — treating galaxy generation as an exception to that rule would be an inconsistency, not a stylistic choice. If no seed is supplied, one is generated randomly and **stored** (not discarded) so the resulting galaxy can be reproduced later — this also gives deterministic testing and debugging for free, and leaves room for a future "share this galaxy" or "new game with code" feature without re-architecting. **Name generation is explicitly deferred** — unlike the seed, it's pure content/flavor with zero mechanical dependencies (nothing else in the design reads or reasons about a planet's name), so building a real procedural name generator now would be scope creep. Use placeholder-style names for now (e.g., `"Planet-{id}"` or a short hardcoded list) to unblock generation logic; a real name generator can be its own isolated task later.
- **Discovery state:** a simple `discovered: boolean` field is added to the `Planet` type now, defaulting to `false` for every planet except the starting planet — same reasoning as the position/seed fields: cheap to add at generation time, more disruptive to retrofit onto every existing planet record once the trade map actually needs it later. The field carries **no behavior yet** — nothing reads or acts on it until travel/map features exist — it's just present and ready for when they do.
- **Planet generation attributes needed beyond the MVP's minimal type:** with tier, Planet Type, quality-modifier data, position/coordinate, and discovery state now decided above, the `Planet` type's full MVP-of-this-phase shape is settled — no remaining open attribute questions.

**Section status: all open questions resolved.** Galaxy & Planet Generation is ready to move from design into agent contracts.

## Trading Market

**Decided:**
- Markets are **per-planet**, not a single global/unified market. Each planet's market has **modifiers for what that planet wants/buys and what it sells**.
- The market will **expand beyond the four item tiers to also include crafters themselves** — specifically, **hiring an NPC crafter to join your crew** (not a one-off service listing or schematic/skill access sale). Full mechanics deferred.
- **Two-tier market model:** a **global/overall market** accessible everywhere (no travel required) exists alongside per-planet markets, but does **not** offer the best buy or sell prices.
  - **Global market scope:** players can only **list/sell tiers 1-5** on the global market, but can **buy any tier 1-7** there. Tiers 6-7 are **sell-restricted to planet markets** as an intentional exclusivity design choice.
  - **Global market pricing:** prices are **live**, and are **influenced by planet market activity** — **now given a concrete mechanism**, see "Global price mechanism" under Newly Decided (Trading Loop phase) below.
  - **Buy/sell model:** for players, markets (both global and planet) are a **direct buy/sell option**, not an auction/bid system (unless refined further later).
  - **No AI NPC merchants (for now):** no auto-buy mechanism — items listed need an actual buyer. Explicitly a **post-launch feature**.
- To address the challenges tier 6-7 exclusivity raises (discoverability, dead inventory, market saturation, new-player accessibility), the working solution is a **galactic trade map**:
  - Each discovered planet shows what it **sells cheap** and what it **buys at a premium**.
  - **Three layers of change drive the map's data:**
    1. **Baseline drift (continuous):** fluctuations from actual player buy/sell activity — **now given concrete shape**, see "Baseline drift / soft-cap pricing" under Newly Decided (Trading Loop phase) below.
    2. **Seasons (slow, predictable):** each planet has a recurring cycle, **determined at planet generation based on the planet's tier**, that swings its buy/sell lists on a schedule.
    3. **Emergencies (rare, sudden):** randomly-triggered events announced on the map, **purely random** — not caused by simulation/economy state.
  - Undiscovered planets are fogged until visited/scouted; a scanner/map upgrade could extend range or data freshness.

### Newly Decided (Trading Loop phase)

- **Currency: single, universal currency** (e.g., "Credits") across all markets — global and per-planet, all tiers 1-7. This is the only option compatible with the already-decided "live pricing, influenced by planet activity" mechanic, which requires one shared price axis to track drift/seasons/emergencies against; a barter/resource-backed model would need its own separate exchange-rate system layered on top, effectively reinventing currency without calling it that. **Regional price variance is already covered by the per-planet market modifiers** (already decided) rather than needing a second, separate currency-exchange mechanism — a planet-specific buy/sell modifier on a single currency achieves the same "prices differ by location" effect without the added complexity of multiple currencies.
- **Listing lifecycle (Option B — expire and return, not indefinite or auto-discounting):** a listing that finds no buyer **expires after a set duration** (a tunable number, e.g. ~72 in-game hours — not locked, just a reasonable starting point) rather than sitting forever (which would worsen the dead-inventory problem already flagged for tier 6-7 exclusivity) or auto-discounting toward a sale (which would functionally reintroduce an auction/price-discovery mechanic, undoing the already-decided direct buy/sell model). **Where the item goes on expiry depends on market type:** a **planet market** listing is **held at that planet for pickup** — consistent with the physical-presence theme already built into planet markets, so a player has to return to collect what didn't sell, same as they had to be there to list it. A **global market** listing returns **straight to inventory**, since the global market is accessible everywhere and there's no physical "there" to hold it at.
- **Remote tier 6-7 sales (Option C — remote allowed, but only to discovered planets, item travels):** a player can remotely initiate a tier 6-7 sale to any planet they've already **discovered** (reusing the `discovered` boolean already on the `Planet` type from Phase 2 — no new field needed), rather than requiring physical presence for every sale (which would worsen dead-inventory risk) or allowing fully remote/instant sale anywhere (which would undermine the tier 6-7 exclusivity design entirely). The item **travels rather than teleporting** — it isn't listed/sellable at the destination until it arrives. **Exact travel time mechanics are deferred to the Travel milestone**, per the decided development order; this decision only establishes that a delay exists and that discovery is the gating requirement, not the specific duration or any in-transit risk (e.g., piracy). Once the item arrives, it becomes a normal planet-market listing subject to the listing lifecycle rule above (72-hour expiry, pickup at that planet).
- **Baseline drift / soft-cap pricing:** rather than building a separate soft-cap mechanism alongside "baseline drift," **baseline drift itself is defined as the soft cap** — same reasoning as rejecting "weighted toward worst" for refining because the threshold penalty already covered that job; doubling up on one problem with two mechanisms is avoided here too. Concretely: each unit sold into a planet's market drops that item's price by a **percentage of its current price** (e.g., -2% per unit, within a rolling window), and each unit bought raises it similarly — percentage-based, consistent with the ±10% variance and tier percentage tables used elsewhere, so the effect is naturally diminishing (each successive unit moves the price less in absolute terms than the last, since the drop compounds against an already-lower number). A **floor and ceiling** (e.g., 50%–150% of the planet's base price for that item) directly prevents both "one seller crashes the price to zero" and "one planet becomes an infinite sink" — the curve flattens as it approaches either bound rather than needing a separate hard cutoff rule. Prices **drift back toward base over time** when untraded, so a temporarily crashed/inflated price doesn't stay that way forever — also gives the market-news-ticker idea (already logged above) something concrete to report on ("prices at [Planet] are recovering"). Exact percentage, window, and floor/ceiling values are left as tunable numbers, not locked.
- **Multiple planets can buy the same tier 6-7 category** — demand is not one-planet-per-item-type. This directly avoids the single-point-of-failure risk already flagged for tier 6-7 exclusivity (one planet's price crash being the only outlet for an entire category), and costs nothing new to build since each planet already tracks independent price/drift state — multiple planets wanting the same category is just more instances of a mechanism that already exists, not a new one. Consistent with the trade map's per-planet buy list already implying planets differ in what they want, which naturally allows overlap rather than a strict galaxy-wide partition. **Follow-on idea, not yet decided:** which planets buy which tier 6-7 categories could reasonably be driven by **Planet Type** (the same lever already used for raw resource eligibility in Phase 2) — e.g., a mining-flavored planet buying weapons/tools at a premium — worth revisiting once the trade map's specific buy/sell lists are fleshed out.
- **Global price mechanism:** the global price for any item is **derived directly from live planet prices, not tracked as a separate rolling average or independent feed.** Global buy price = the **lowest current sell price** across all planets currently selling that item, **plus a fixed markup** (e.g., +10%). Global sell price = the **highest current buy price** across all planets currently buying that item, **minus a fixed discount** (e.g., -10%). This **structurally guarantees** the already-decided "global never offers the best price" rule by construction — there's no way for the global price to accidentally beat a planet's price, since it's defined as that price plus a penalty. It also **reuses existing pricing data** rather than needing new state: baseline drift, seasons, and emergencies already move individual planet prices live, so the global price just reads the current best planet price at query time (a filter over existing per-planet market data, not a new data structure), meaning any of those three change-layers automatically and correctly propagates to the global market with no extra mechanism needed. Exact markup/discount percentages are left as tunable numbers, not locked.
- **Listing quality representation:** market listings are **bucketed by a single derived "market tier"** — a straight average of the item's 5 qualities, mapped through the existing tier table — rather than exact-match stacking (nearly every unit rolls a unique 5-axis combination, which would flood the market with unbrowsable singleton listings) or bucketing across all 5 axes independently (up to 7⁵ buckets, defeating the purpose of bucketing at all). This reuses the same straight-average-to-tier formula already used for crafted items' tiers 3-7 aggregate color, just applied one step earlier for market display/stacking purposes only. **The underlying item instance keeps its full, real 5-quality data** — the market tier is a display/stacking convenience, not a data transformation; when an item is actually refined or crafted, the formulas read its true per-quality values, not the market bucket it happened to list under. **Known tradeoff:** two listings in the same bucket (e.g., both "Blue") can have meaningfully different individual quality profiles that average to the same tier — a buyer optimizing for one specific quality axis won't see that difference from the listing alone; this is an accepted cost of keeping listings simple and browsable.
- **Listing model confirmed: direct fixed-price listings**, not an order book or NPC price-discovery system — this was effectively already implied by two prior decisions ("markets are a direct buy/sell option, not an auction/bid system" and "no AI NPC merchants, items need an actual buyer"), now stated explicitly. A player creates a fixed-price listing (sell X units at price Y); any other player can accept it at that listed price — no bidding, no negotiation. This is what makes the listing lifecycle (72-hour expiry, pickup/return) and market tier bucketing meaningful mechanics, rather than a different model (an order book) that wouldn't need either. **Partial purchases are allowed** — a buyer can purchase part of a listing's quantity (e.g., 5 of a stack of 12); the listing stays active with the remainder until it hits zero or expires, rather than being all-or-nothing.
- **Price history:** tracked now — a timestamped log of price points per item per planet, generated as a natural byproduct of the baseline drift/seasons/emergencies mechanisms already computing live prices. Costs almost nothing to store, and directly feeds the price-history-graph idea already logged under market-driver flavor/communication.
- **Market manipulation — partially resolved now, detection logic deferred to multiplayer:** three cheap structural choices made now rather than deferred entirely, since retrofitting them once multiplayer exists would be far more disruptive than building them in from the start (same reasoning as the seed/position/discovered-flag decisions):
  1. **Self-trade prevention:** a listing's creator cannot purchase their own listing — a no-op in single-player, but the rule already exists in the formula layer for when multiplayer arrives.
  2. **Trade attribution:** every listing records which player entity created it — trivial in single-player (always "the player"), but this is the field that makes manipulation *detectable* later (repeated trades between the same accounts, coordinated pumping) without needing a data migration once multiplayer ships.
  3. **The already-decided soft-cap/floor-ceiling baseline drift mechanism is the primary defense against price-cycling exploits** — stated explicitly here as covering this concern, since each successive trade already moves the price less, not more, directly limiting the profitability of "buy low, sell high, repeat." No new mechanism needed for this part.
  **Genuinely deferred:** cross-player detection logic (flagging suspicious trade patterns, rate-limiting, account-level intervention) — this is real multiplayer-specific work with no single-player equivalent to design against yet, so there's nothing concrete to build until multiplayer is in scope.
- **Taxes/fees:** a **flat transaction fee on sales** (e.g., 5%, taken by "the market" itself, not any player), functioning as a **currency sink**. This addresses a gap created by the single-universal-currency decision — without a sink, currency only accumulates in the economy over time (a slow inflation problem), and a small flat sale fee is a standard, low-complexity fix.
- **Regional market nuances beyond what's already decided:** **closed out as already covered**, not left open — per-planet modifiers, baseline drift, seasons, and emergencies already constitute the regional-nuance system; there's no concrete gap remaining to design against without a specific new idea driving it.
- **Market-driver flavor/communication (idea, not yet a locked mechanic):** genuine potential here, and it layers naturally on top of the trade map's existing three change-layers (baseline drift, seasons, emergencies) rather than requiring new systems. Ideas kept for reference:
  - A **market news ticker/feed** on the trade map or a planet's market screen, generating short in-universe headlines tied to whichever layer is actually driving a price change (e.g., "Harvest season begins on [Planet] — grain prices falling" for a season shift, "[Planet] declares mining emergency — ore prices spiking" for an emergency).
  - **NPC merchant flavor text/dialogue** at a planet's market that reacts to current conditions (a merchant complaining about a shortage, bragging about a surplus) — cheap to add once the underlying price-driver data exists, since it's just reading the same state the ticker would read.
  - **A simple price history graph** per item per planet, so players can see *that* something changed even before they know *why* — pairs well with the ticker rather than replacing it.
  - None of this changes the underlying pricing mechanics — it's a presentation-layer feature reading from data the three change-layers already produce, so it can be deferred independently and added whenever, without touching the trading formulas themselves.

## Crew Crafters

**Status: Phase 3 (Trading Loop) complete — this is the active phase next.** Per the decided development order: galaxy generation → planet generation → resource generation → crafting recipes/schematics → trading loop → **[Phase 3 boundary]** → **crafters (NPC crew)** → travel → map.

**Carried over from Trading Market:** the market expands beyond the four item tiers to also include crafters themselves — specifically, **hiring an NPC crafter to join your crew** (not a one-off service listing or schematic/skill access sale). That was the only decision made on this system so far; full mechanics were explicitly deferred to here.

**Decided:**
- **Crew mechanics (Option C — both active and passive, with a real distinction):** a crew member can be **actively assigned** to a specific craft action (the player picks them, using their exact tier/profession, same as choosing which crafter to use), **or left idle**, in which case they can passively work on **queued/background crafts** at a reduced rate or capacity while the player is elsewhere. This is deliberately the more complex option over passive-only or active-only, because it's the only one that makes "crew" mean something beyond a reskinned crafter-tier stat — a passive-only system turns hiring into a shopping trip for stat boosts, and an active-only system barely differs from the existing player-crafter mechanic. The active/idle split creates a real management decision (bring this crafter to actively work, or leave them running background production) and gives multiple crew members distinct roles.
- **Background/idle crafting simulation (Option B — catch-up calculation on return, timestamp-based):** no continuous ticking. A `lastCheckedAt` timestamp is stored (via the existing `SaveSystem`, same pattern as other persisted state) rather than the client computing and passing in an elapsed duration directly — elapsed time is derived as `now - lastCheckedAt` at resolution time, not asserted by the caller. When the player checks on a crew member, the system resolves all background production in one deterministic pass: `(elapsedTime, crewMemberTier, recipe) → output`, the same pure-function shape already used for `refine()`, `craft()`, and `applyDrift()` — fits the established architecture rather than introducing a new pattern. Chosen over true real-time ticking (nothing to keep alive in a browser tab with no server — would need a catch-up path anyway for the "tab closed" case, making live-ticking mostly redundant) and fixed player-triggered increments (doesn't track real elapsed time at all, undercutting the entire point of idle/background crafting rewarding time away). **An elapsed-time cap** (tunable, e.g. 24-48 hours max credited) prevents both an honest edge case (leaving the game running for a week) and a future dishonest one (a manipulated timestamp claiming an impossible duration) — see the multiplayer note below for why the cap matters beyond just the honest case.
  - **Multiplayer-forward note (re-examined per the standing single-player-first decision, same reasoning as the seed/position/discovered-flag/trade-attribution fields):** a client-computed elapsed duration would be a real exploit vector under a shared economy — a player could manipulate their local clock or the value itself to claim inflated background production, directly affecting a market other players trade in. Storing a timestamp and deriving elapsed time at resolution time (rather than trusting an asserted duration) keeps the same pure function portable to a future server-authoritative caller with zero formula rewrite — only *where* elapsed time gets computed changes, not the function itself.
- **NPC Crafter Skill Representation:** hired NPC crafters use the **same 7-tier color scale** already used for refiner tier, crafter tier, schematic tier, and planet tier — no separate system. A hired NPC's **profession is locked at hire time, not freely reassignable**, for tiers 6-7 (the tier band where profession specialization already exists per the general crafting design; tiers 3-5 remain general/unspecialized, same as the existing player-crafter rule). This keeps hiring a real, non-fungible decision (you found a Gold-tier weaponsmith, not a generic Gold-tier slot you can reskin), consistent with the exclusivity theme already used for tier 6-7 schematics and crafted goods, and preserves the existing tiers-3-5-general/tiers-6-7-specialized split rather than undermining it.
- **Acquisition:** NPC crafters are found in a **small, refreshing pool of available hires at each planet's market** (reuses the "planet markets have their own state that changes over time" pattern already built for goods pricing) — not a global list, and not player-generated from scratch. When a new hire candidate appears, their tier is rolled through the **same 7-tier breakpoint table** used everywhere else; if it lands tier 6-7, a profession is also rolled (per the skill representation decision above). **Cost scales with tier**, paid in the single existing currency, consistent with how every other tier system (refiners, schematics, planets) treats "better = more valuable/harder to get." **Follow-on idea, not required to launch:** certain professions could be more likely to appear on certain Planet Types (e.g., a mining-flavored planet more likely to produce weaponsmiths for hire) — the same lever already used for raw-resource eligibility (Phase 2) and tier 6-7 trade demand (Phase 3). Exact refresh interval, pool size, and cost numbers are left as tunables, not locked.
- **Crew capacity (Option C — starts small, expandable via purchasable upgrade):** a player begins with a small base capacity for hired crew, expandable by purchasing additional slots with Credits. Chosen over unlimited capacity (which would undercut the exclusivity/scarcity theme built into every other system — tier 6-7 goods, unique schematics, planet quality, non-fungible crew hires — by removing the "who do I keep" decision entirely) and a flat fixed cap (doesn't reward progression, feels arbitrary). Capacity expansion doubles as **another currency sink**, consistent with the reasoning already used for the transaction fee. Doesn't depend on the not-yet-designed Travel/ships milestone to function now, but leaves an obvious future hook — if ships/crew quarters get designed later, capacity could naturally scale with ship size too, without needing a redesign. Base capacity and the expansion cost curve are left as tunables, not locked.
- **Interaction with the player's own crafting (in addition to, not instead of):** crew members are **parallel crafting capacity**, not a substitute for the player's own crafting. This follows directly from the Section 2.1 decision — an actively-assigned crew member works on a specific craft action, and an idle one works on background production; both framings already imply each crew member is an independent actor with their own craft in progress, running alongside the player's own. Chosen over "instead of" (would mean hiring trades away the player's own crafting capability, undermining the "crew is a real investment" framing) and "player chooses per-craft, one at a time" (makes crew members functionally identical to just picking a different crafter tier for a single action — the same "active-only barely differs from the existing mechanic" trap already avoided in 2.1; if only one craft can happen at a time regardless of crew size, having 3 crew members isn't meaningfully different from having 1). **Concretely:** multiple crafts can be in progress simultaneously — the player's own active craft, each actively-assigned crew member's craft, and background production ticking for idle crew members — each independently calling the existing unified crafting formula with its own crafter (player skill, or that specific NPC's tier/profession). No new formula needed.
- **Ongoing cost (upkeep/wage, not one-time):** hired crew members cost a **recurring wage**, not a single upfront payment. Chosen for consistency with the currency-sink pattern used throughout this phase (crew capacity expansion and the trading transaction fee are both already sinks; a one-time cost doesn't keep pulling currency out of the economy the way an upkeep wage does, and crew crafters represent genuine ongoing production capacity per the decision above, so a matching ongoing cost fits). Makes crew composition a continuous strategic decision rather than a one-time purchase, and creates real tension with the idle/background choice from 2.1 — an idle crew member still costs upkeep while producing at a reduced rate, giving a concrete reason to actually manage a crew rather than hire-and-forget. **Wage scales with tier**, reusing the same "tier = more valuable, costs more" pattern already used for acquisition (2.3). Paid automatically at a regular interval; exact wage curve and interval left as tunables.
- **Loss/attrition (two mechanisms, no random loss):** a crew member leaves via **automatic departure from unpaid upkeep** (past some grace period, per the ongoing-cost decision above) — the primary trigger, reusing an already-decided mechanism rather than inventing a new one. A player can also **voluntarily dismiss** a crew member directly, which matters practically since capacity is limited/purchasable (2.4) and hires are non-fungible/locked-profession (2.2) — a player will want to swap a lower-tier hire for a better one without having to deliberately stop paying upkeep as an indirect workaround. **Explicitly ruled out for now: random/permadeath-style loss** (death, poaching, etc.) — there's no combat, risk, or travel-hazard system yet for that to hang off of; adding it now would be speculative work against systems that don't exist, same reasoning as deferring market manipulation detection until multiplayer exists. A future travel/danger system could add risk-based crew loss later as a natural extension, but it isn't designed now.
- **Background/idle crafting rate: flat 50%, not tier-scaled.** Idle crew members produce at half the rate/yield they would if actively assigned, using the exact same `craft()` output otherwise (same quality, same tier effects on the crafting formula) — just fewer completed crafts over the elapsed time window. Chosen flat rather than tier-scaled to avoid stacking a second tier-based modifier onto the same crew member's output: crew tier already affects quality via the shared variance table inside `craft()` itself, and layering a separate tier-scaled idle-rate on top would mean tier influences background production in two places at once — the same kind of redundant stacking already avoided elsewhere (rejecting a fourth planet-tier modifier, rejecting weighted-worst refining). 50% is a real, noticeable penalty — enough to make the active/idle choice from Section 2.1 a genuine tradeoff without making idle crafting pointless.

### Open questions

- **(Multiplayer-forward, tracked now rather than assumed away, genuinely deferred — not required to resolve now):** should `lastCheckedAt` be stored now, even though single-player has no immediate tamper-resistance need — same "build it in now, costs nothing" reasoning as the generation seed and trade attribution fields? If multiplayer eventually means a persistent shared world, does background crafting need genuine server-side ticking (not just catch-up-on-check-in), since other players might want to observe/interact with a crew's production without the crew owner triggering resolution? Does a hired crew member remain strictly private to the hiring player under any future multiplayer model, or could crew members eventually be shared/tradeable/poachable — this affects whether crew data needs a `createdByPlayerId`-style attribution field now, the same pattern already used for trade attribution.

**Section status: all Crew Crafters questions resolved, except the multiplayer-forward item above, which is intentionally tracked and deliberately deferred, not an accidental gap** (same treatment as Trading Market's cross-player manipulation detection, Travel's encounters, and the Galactic Map's scanner/probe idea).

## Ships

**Status: Phase 4 (Crew Crafters) complete — this is now the active phase.** Nothing else below is decided yet; ship upgrades is the first question resolved.

**Carried over:** nothing formally decided prior to this pass, though ships are implied as the eventual vehicle for travel (next section) and as the thing crew capacity may eventually scale with (per the Crew Crafters "capacity could naturally scale with ship size" follow-on note).

**Decided:**
- **Ship upgrades (Option A — individual component swaps, each independently tiered):** a ship's capability comes from its installed components — weapons, engines, shields, cargo holds — each rated on the **same 7-tier color scale** used everywhere else (resources, refiner/crafter, schematics, planets, NPC crew), rather than one single "ship level" number. Chosen because it honors the four component types as real, distinct subsystems (a scout ship and a cargo hauler can meaningfully differ — fast engine/weak cargo vs. huge cargo/minimal weapons — rather than every same-tier ship being identical), and it costs nothing new architecturally: same tier scale, same "components are items with quality" pattern already used for schematics and crew. A hybrid "base hull tier + components" option was considered and set aside as likely redundant once components already carry their own tiers.
- **Components craftable + tradeable; whole ships purchased from a market (Option C):** ship components (weapons, engines, shields, cargo holds) are **craftable**, extending the existing crafting system with a new recipe category — same unified crafting formula, category+threshold inputs, schematic tier, and crafter tier, no new mechanic. Once crafted, components are ordinary crafted items and **automatically flow into the existing trading market** — nothing new needed there either. **Whole ships**, by contrast, are a **discoverable/purchasable unique item from a market**, reusing the same shape already built for schematics (unique, tiered, purchasable from planetary markets) and NPC crew (a small refreshing pool at a planet's market, tier-rolled) — e.g., a "shipwright" pool at planet markets offering ships at various tiers.
- **Ship tier is derived from its components:** a ship's overall tier is a **straight average of its installed component tiers**, mapped through the existing 7-tier breakpoint table — the same aggregation formula already used for crafted items' tiers 3-7 display color, and consistent with the already-decided rule of combining multiple tiered inputs via straight average rather than weighting toward the worst (same reasoning as refining's input combination and market listing tier bucketing). The derived ship tier is what feeds into performance-relevant formulas (e.g., travel speed — see Travel section), while individual components still drive their specific effects (engine → speed, cargo hold → capacity) underneath, the same way a crafted item's aggregate tier drives market value while its 5 individual qualities still exist and matter underneath.
- **Ship tier → travel speed:** derived ship tier feeds into travel time as a **percentage-based speed modifier**, the same shape as the refiner/crafter tier tables — a Grey-tier ship travels close to baseline speed, a Gold-tier ship travels meaningfully faster, applied on top of whatever base travel-time formula the Travel section defines (distance between planet coordinates). Uses the **derived ship tier**, not the engine component alone — using the engine specifically would bypass the reason the aggregate tier was built (to avoid "which component matters for what" complexity); if engines should matter more than other components for speed specifically, that's a future refinement rather than abandoning the aggregate on its first use. This resolves both "ships and travel time" and "how ship tier feeds into performance" at once, since they were the same question from opposite ends. **What stays open:** the base travel-time formula itself (distance/coordinate math) is a Travel-section question — this decision only establishes that ship tier modifies it proportionally, not what the base number is.
- **Ship component scope: four categories (weapons, engines, shields, cargo holds), no more for now.** Kept deliberately minimal, consistent with how every other system in this design has avoided speculative scope (the MVP's thin `Planet` type, unique-schematic ideas logged but not built, market manipulation detection deferred until multiplayer actually exists). The four cover the obvious bases (offense, defense, mobility, utility) without reaching further; a fifth category can be added cheaply later if a real need surfaces (e.g., once Travel's encounters feature exists and something like "sensors" becomes mechanically relevant). **Components carry the same 5-quality data** (purity, density, potency, durability, rarity) as every other crafted item — no separate stat system, consistent with the standing "5 qualities persist at every tier" rule. This means components use the exact same crafting formula, market-tier bucketing, and trading mechanics already built, with no new data pipeline. What differs is only the *mapping* from quality to gameplay effect (e.g., an engine's potency might drive speed, a shield's durability might drive damage absorption) — a balance/design detail for whenever these systems get built, not something needed now.

**Section status: all Ships questions resolved.** Ships is ready to move from design into agent contracts.

## Travel

**Status: Ships resolved, Travel is now the active section.** Captured ahead of time so nothing got lost while Phase 4 was worked through.

**Carried over from Trading Market:** remote tier 6-7 sales require the item to travel (not teleport) to a discovered planet, with exact travel-time mechanics explicitly deferred to this milestone. This is the first concrete mechanical dependency on Travel actually being designed.

**Decided:**
- **The map: same galactic trade map, extended — not a separate system.** The Phase 3 trade map already has everything travel needs (discovered planets via the Phase 2 `discovered` flag, and each planet's position via the Phase 2 x/y coordinate) — building a second, dedicated travel map would duplicate that rendering and discovery logic for no real benefit, and a player selecting a travel destination is the same mental action as a player checking trade data on the map, not a different screen's job. **Concretely:** the map screen gains a travel-relevant layer (computed travel time to each discovered planet, informed by the Ships section's ship-tier speed modifier) alongside its existing trade-data layer.
- **Coordinates stay 2D `{x, y}` — Phase 2's shape is unchanged.** Considered whether `{x, y, z}` would be worth adding for a more realistic/spatial galaxy feel, but explicitly decided against it: the only thing `position` needs to support is a distance calculation between two planets, which 2D handles fully, and there's no current plan for true 3D map navigation (rotatable camera, depth) that would justify reopening Phase 2's already-complete, tested, and committed data shape. If 3D visualization becomes a real goal later, this can be revisited then — but it's not worth the cost of touching a closed phase for a benefit that doesn't exist yet.
- **Unit of travel/distance (Option B — abstracted distance, derived from existing coordinates):** travel time is a function of the **straight-line (Euclidean) distance** between two planets' `{x, y}` positions, scaled by a tunable constant to convert raw distance into travel time, then modified by the ship-tier speed percentage already decided (Ships section). Not a real-world unit like AU — Phase 2's coordinates were never built to represent real astronomical scale, so retrofitting physical units would apply false precision. This is really the completion of the Phase 2 position decision rather than a new one — the coordinates were generated specifically so a formula like this could exist later. Exact scaling constant is left as a tunable, same treatment as every other percentage/rate value in this design.
- **Encounters during travel (Option A now, Option B logged as the intended future shape):** the initial Travel build has **no encounters** — travel is "time passes, you arrive," consistent with the same discipline already applied to crew loss/attrition (no random/combat mechanics built against a system, like combat, that doesn't exist yet). **Intended future shape, explicitly deferred, not decided as final:** lightweight, non-combat encounters resolved entirely through mechanics already built elsewhere — a trade-opportunity encounter (resolved via existing trading/currency), a discovery encounter (resource/credit reward or progress toward a new planet), and a hazard encounter resolved as a **tier check against derived ship tier** (succeed/fail against a threshold, similar in spirit to the existing threshold-penalty pattern) — no new combat-resolution system required for any of these. **Real combat is explicitly out of scope** for this milestone and any near-term follow-up: it would be the first system in this entire design with zero prior foundation to build on (ship weapons exist as a component, but no damage/combat-resolution formula exists anywhere), breaking the "reuse what's already built" pattern every other decision in this doc has followed.

**Section status: all Travel questions resolved (or explicitly deferred with a recorded intended shape, per the Encounters decision above).** Travel is ready to move from design into agent contracts.

## Galactic Map

**Status: Ships & Travel (Phase 5) complete — this is now the active phase, per the decided development order.**

**Carried over from Trading Market (Phase 3):** the trade map already exists — per-planet sell-cheap/buy-premium display, driven by three layers (baseline drift, seasons, emergencies), with undiscovered planets fogged until visited/scouted. **Carried over from Travel (Phase 5):** the map was extended with a travel layer (destination selection, computed travel time, voyage-in-progress display) — same screen, not a separate one.

**What's actually left for this phase, then, is not "build the map" (it already exists across two phases) but the specific loose threads that were explicitly deferred when the map was first designed:**

**Decided:**
- **No advance warning before an emergency starts.** The emergency's already-decided duration ("paying premium for [goods] for the next N hours") *is* the reaction window — a player who checks the map (or hears about it via the market-driver flavor ticker idea) has that window to travel there before it ends. A separate advance-warning countdown would be a second timer solving the same problem the duration already solves, the same "don't build two mechanisms for one problem" reasoning already applied elsewhere (rejecting a second soft-cap system, rejecting weighted-worst refining). It also fits "rare, sudden" better — sudden means no warning, by definition.
- **No staleness — map data for any discovered planet is always live.** Structural reason specific to single-player: the whole galaxy's state (drift, season, emergency) is already computed live and deterministically whenever queried — the same pattern already used by `getGlobalPrice()`, which reads live planet data at call time rather than a cached snapshot. There's no server, no other player, and no actual reason for the game to withhold current information it already has. Faking staleness would mean deliberately hiding data for a gameplay reason that doesn't currently exist; if an "information fog" mechanic is ever wanted, that's a deliberate future design choice, not a default staleness needs to solve now.
- **No scanner/probe mechanic — discovery stays exactly as it already works.** Discovery already has a complete, working mechanism (a planet becomes `discovered: true` when physically visited, per Phase 2/Trading Market) — a scanner wouldn't fix a gap, it would add an alternative path to something that already functions fine. Same pattern already applied twice elsewhere in this design (crew loss/attrition, encounters during travel): build nothing now, record the intended future idea explicitly, defer the real mechanic until there's an actual reason to build it. It also doesn't cleanly fit anywhere already built — not a ship component (Ships explicitly closed that list at four categories), not really a market item either — it would need its own small subsystem for no current mechanical necessity. **Recorded future idea, not built:** a scanner/probe as a purchasable item or ship upgrade that extends discovery range, letting a player discover planets within some radius without physically traveling to each one — a clean, well-scoped feature to pick up later if the game wants more strategic depth around exploration, but nothing about the current design requires it.
- **No new galaxy-wide/"zoom out" view needed now — the existing per-planet map is sufficient.** Everything the map needs to do (trade data, travel options, discovered/undiscovered state) already works on the existing screen — there's no missing function. Phase 2 already anticipated this exact question: galaxy structure deliberately has no formal region data structure, but explicitly noted visual regions "can be derived from coordinates after the fact" if ever wanted — still true, still sufficient. **The real, currently-hypothetical concern worth naming honestly:** if the galaxy ends up with dozens or hundreds of planets, a flat map showing every one at once could genuinely become cluttered — a legitimate future UX problem, but not a problem yet, since no galaxy size large enough to make it real has been set anywhere in this design. **Recorded future idea, not built:** if navigation later becomes genuinely difficult, the fix is a presentation-layer feature (visual clustering/zoom levels derived from existing coordinates) — no new data structure needed, since Phase 2 left that door open on purpose.

## Travel Encounters (Non-Combat)

**Status: active design pass.** The originally-planned development order is fully built and verified (MVP through Galactic Map). This is the first of the deliberately-deferred gaps being picked up now, per the sequencing decision: Scanner → Encounters (non-combat) → Combat → Multiplayer.

**Carried over from Travel:** the recorded future shape — lightweight, non-combat encounters resolved entirely through mechanics already built elsewhere, specifically chosen so **no combat system is required**:
- A **trade-opportunity** encounter, resolved via existing trading/currency mechanics.
- A **discovery** encounter, resulting in a resource/credit reward or progress toward discovering a new planet.
- A **hazard** encounter, resolved as a **tier check against derived ship tier** (succeed/fail against a threshold, similar in spirit to the existing threshold-penalty pattern), with a minor cost/reward outcome rather than actual combat.

This was explicitly recorded as an intended shape, not a final decision — the questions below are what's needed to actually build it.

**Decided:**
- **Trigger mechanics: roll per fixed time window during travel, same shape as the emergency system.** Reuses the exact pattern already built for emergencies (roll per 24h window, 15% trigger chance) rather than a flat per-voyage chance — a flat chance would make a short hop and a marathon trip equally likely to trigger something, which doesn't track with what travel encounters should feel like. A voyage spanning multiple windows gets multiple independent rolls, so longer trips are meaningfully more likely to have *something* happen without guaranteeing it. Exact window size (reuse 24h, or a smaller window if typical voyages run shorter once ship-tier speed is factored in) is a tunable to confirm against real voyage durations, not locked here.
- **Encounter type split: weighted random, favoring upside.** When a roll succeeds, which of the three types (trade-opportunity, discovery, hazard) occurs is a **weighted** random split, not equal odds — hazard (the only type with a downside) is the least common, while trade-opportunity and discovery (both upside-only) are more common. This makes travel feel like "usually something nice happens, occasionally something risky does" rather than a 50/50 good-or-bad coin flip every trigger. Exact weights are a tunable, not locked.
- **All three encounter types resolve automatically — no player interaction required.** Voyages resolve via a deterministic catch-up calculation (`resolveArrival()`), the same pattern as background crew crafting, not real-time ticking the player is guaranteed to be present for. An encounter that requires an interactive choice (e.g., "accept this trade offer before it expires") doesn't fit that model — there's no guarantee anyone's present when an encounter's window rolls. Decided once, for all three types, rather than separately per type. Results are **reported after the fact** when the player checks the voyage or it resolves (e.g., "Encountered a trader en route: +150 Credits"), same reporting pattern as background crafting results.
- **Trade-opportunity encounter: a direct, automatic currency grant, not a spawned listing.** When triggered, computes a small immediate currency gain (flavored as "sold surplus cargo to a passing trader" or similar) via the existing `Wallet` mechanism — no new data shape, no temporary `Listing` with its own lifecycle that would conflict with the automatic-resolution decision above (a listing implies someone needs to browse/accept it; a direct grant doesn't).
- **Discovery encounter: a found resource item (via `rollQuality()`), never a remote planet discovery.** Grants a resource item with a normal quality roll, reusing the existing `rollQuality()` function — the same mechanism already used for gathering, no new reward-generation system. Deliberately **not** currency, since trade-opportunity already covers that — a resource grant gives discovery real mechanical distinctiveness rather than two types with different flavor text and the same effect. **Explicitly does not ever set `discovered: true` on a new planet remotely.** A random encounter that discovers a planet without physical arrival would functionally *be* a scanner, just triggered by luck instead of purchase — reopening the already-closed "no scanner mechanic" decision through a different door achieves the identical outcome the design deliberately avoided, so it stays closed. (Exact source pool for the rolled resource — current/nearby planet's eligible list vs. a fixed "found in deep space" table — is a smaller implementation detail to confirm later, not a blocking design question.)
- **Hazard encounter: single roll against a fixed threshold, modified by ship tier, with a scaled currency-cost outcome on failure.** Roll a percentage-based value, apply a ship-tier modifier (same "tier shifts a roll" pattern already used for planet quality modifiers and the ship-tier speed multiplier — a higher-tier ship is more likely to pass), compare against a fixed pass threshold. On failure, apply a **scaled currency cost using the same escalating curve shape as the crafting threshold penalty** — the further below threshold, the worse the cost, not a flat fail-cost. **Currency cost was chosen over the alternatives:** cargo loss doesn't apply consistently since most voyages don't carry cargo (that field exists specifically for the Phase 3 remote-sale case); a voyage delay would mean retroactively changing `arrivesAt` after it's locked at initiation, conflicting with the existing "never recomputed mid-flight" rule; ship component degradation would need a whole new mutation path for something that currently can't change after crafting, effectively reintroducing combat-damage-by-another-name — the same thing already deferred three separate times (crew loss, real combat, and now this). A currency deduction needs none of that — it's a `Wallet` change, fits the automatic/catch-up resolution model, and reuses existing infrastructure entirely.
- **Encounter frequency stays tier-independent — ship tier's influence stops at the pass/fail roll it already has.** Extending tier into trigger frequency too would mean a second, distinct effect from the same stat on the same encounter type — the same discipline already applied to planet tier (scoped to gathering only, not extended into refining/crafting to avoid a fourth stacking modifier) and ship tier itself (scoped to travel speed, not folded into crafting just because a ship exists alongside a crafting crew member). A Grey-tier ship and a Gold-tier ship hit hazards equally often; the Gold-tier ship just handles them better once one occurs, via the pass/fail modifier already decided. One job per tier system, not several.

**Section status: all Travel Encounters questions resolved.** Travel Encounters (non-combat) is complete. Per the deferred-gaps sequencing, Scanner/probe — the item skipped in favor of tackling Encounters first — is being picked up now.

## Scanner/Probe

**Status: active design pass.** Travel Encounters (Non-Combat) is complete and verified. This is the second of the four deliberately-deferred gaps being picked up, in the order Scanner → Encounters → Combat → Multiplayer, with Scanner specifically being the item skipped the first time through and now being addressed.

**Carried over from the Galactic Map section:** the recorded future idea — *"a scanner/probe as a purchasable item or ship upgrade that extends discovery range, letting a player discover planets within some radius without physically traveling to each one"* — recorded specifically because normal discovery (physical visitation) already works fine and nothing forced this to be built immediately. That's still true; this section exists because the sequencing decision says it's this feature's turn, not because a new necessity emerged.

**Guardrail carried forward unchanged:** the Travel Encounters design pass established that a discovery encounter must never set `discovered: true` remotely, specifically to avoid duplicating what a scanner does. That constraint was written *anticipating* this section — a scanner is the one sanctioned way to discover a planet without physical visitation; nothing else should ever do that.

**Decided:**
- **Form factor: standalone item, not a fifth ship component and not folded into an existing one.** Ships already closed "four categories, no more for now" — adding a scanner as component #5 would directly reopen that decision. There's also a structural reason beyond just precedent: `deriveShipTier()` averages the four component tiers together to produce the tier that drives travel speed; a scanner has nothing to do with combat/mobility/defense/cargo, so folding it into that average would dilute what ship tier actually represents. None of the four existing components fit conceptually as a host for a "detection range" property either. A standalone item sits outside `deriveShipTier()`'s averaging entirely, keeping ship tier meaning exactly what it already means, with the scanner as a separate stat with its own separate effect — the same "one job per system" discipline already applied to planet tier (gathering only) and ship tier (speed only).
- **Acquisition: same tier-rolled, refreshing pool pattern already used for schematics/NPC crew/ships, but its own small, separate market listing type.** Reuses the exact shape you've applied three times now (a small refreshing pool at a planet's market, tier-rolled through the same 7-tier breakpoint table) rather than inventing a new acquisition mechanic — a scanner is conceptually the same kind of thing: a discoverable, tiered, purchasable item you find rather than craft. **Not merged into the existing `ShipyardPool`** — since the form factor decision established a scanner isn't a ship or a component, mixing it into that pool would blur a boundary just drawn on purpose, the same reasoning that already kept `PlanetCrewPool` and `ShipyardPool` themselves separate rather than one combined pool. Tier presumably drives the scanner's actual discovery-range effect (a Gold-tier scanner extends range further than a Grey-tier one) — this connects directly to the still-open tier-scaling question rather than fully resolving it here.
- **Discovery-range mechanic (Option b — manual "scan" action while docked, not passive/automatic):** while present at an already-discovered planet with a scanner owned, the player can trigger a scan action; planets within the scanner's radius of *that planet's* `{x, y}` coordinates become `discovered: true` — the same flag, same meaning, as physical visitation, no new discovery state invented. **Not Option a (passive/automatic based on continuous position)** — that would require tracking a real-time player position mid-voyage, which doesn't currently exist and deliberately doesn't need to: travel resolves via a deterministic catch-up calculation (`initiateVoyage()`/`resolveArrival()`) with no mid-flight coordinate, and building continuous position tracking would undo the exact thing that model was built to avoid. Option (b) reuses the Euclidean distance calculation already built for `calculateTravelTime()` — just checked against a radius instead of converted into a travel-time value — and keeps discovery deliberate, consistent with every other discovery mechanism in this design being a conscious player action rather than an ambient side effect.
- **Tier-scaling: scanner range scales with the scanner item's own tier, not ship tier — additive stacking, reusing the schematic-tier contribution table shape.** Keeping the scanner's own tier as the sole driver preserves the form-factor decision's separation cleanly (ship tier → speed, scanner tier → discovery range, no crossover either way) — deriving range from ship tier instead would quietly reintroduce the exact dilution the form factor decision was built to avoid, just from the other direction. A base value (default docked-planet interaction radius, or possibly zero without a scanner) gets a bonus added on top, scaled by the same 7-tier table shape already used for schematic contributions (Grey +0 up to Gold +6-equivalent, exact distance-unit values to be tuned) — reuses an already-designed curve rather than inventing a new one. **Smaller detail flagged, not resolved here:** whether owning multiple scanners stacks, or only the highest-tier owned scanner counts (leaning toward the latter, consistent with a ship having one derived tier rather than a sum of every component ever owned).
- **Confirmed: a scanner's effect is scoped to discovery range only — no interaction with map data staleness/freshness.** The Galactic Map decision already established staleness isn't a real problem to solve — map data for any discovered planet is always live, a structural fact about the game's single-player, no-server data model, not a limitation a scanner could meaningfully fix. The Discovery-range mechanic decision already gave the scanner a complete, self-contained job (extending the boolean `discovered` flag via the scan action), which has nothing to do with the freshness of an already-discovered planet's market data. The original recorded idea's "or data freshness" phrasing was always a maybe, written before "no staleness" was formally decided — once that door closed, there's nothing left for a scanner to act on. Not a new decision so much as confirming the scanner's scope was already complete; the "no staleness" decision needs no revisiting.
- **No connection to Travel Encounters' discovery type — both systems stay fully independent.** Unlike every prior question in this section, there's no actual collision to resolve here: a scanner (extends `discovered` at range, while docked, a deliberate action) and a Travel Encounters discovery type (grants a resource item mid-voyage, never touches `discovered`) already don't overlap in effect. Adding a connection anyway would be new scope invented for flavor, not necessity — the same category of idea already declined elsewhere (extending ship tier into encounter frequency, extending scanner into map staleness). It would also introduce a cross-system modifier pattern (owning item X changing unrelated system Y's random rolls) that doesn't exist anywhere else in this design — not a good place to establish it for the first time on a minor thematic connection.

**Section status: all Scanner/Probe questions resolved.** Scanner/Probe is ready to move from design into agent contracts. Per the deferred-gaps sequencing, Combat is the next gap to pick up, followed by Multiplayer.

## Combat

**Status: active design pass — scoping decisions made, mechanic details open.** The third of four deliberately-deferred gaps. This is the first system in the entire design with no significant prior foundation to reuse wholesale — the shallow-resolution approach below intentionally borrows as much of the existing pattern language (rolls, thresholds, tunable curves) as it can, but genuinely new mechanics (component damage, crew incapacitation, retreat) are introduced here for the first time.

**This deliberately reopens two previously-closed doors, on purpose:**
- **Ship component degradation** — explicitly avoided as a hazard-encounter outcome specifically because it "would need a whole new mutation path... effectively reintroducing combat-damage-by-another-name" and "the same thing already deferred three separate times." Combat is that deferred thing; this is where the mutation path now gets built, on purpose, not as scope creep into hazard's territory.
- **Crew loss** — the loss/attrition design explicitly ruled out random loss because "there's no combat, risk, or travel-hazard system yet for that to hang off of," while noting "a future travel/danger system could add risk-based crew loss later as a natural extension." Combat is that system. Per the scoping conversation, this stays **lightweight/non-permanent** — not the permadeath that was originally ruled out, but a real (if minor) consequence, consistent with what was actually deferred rather than reopening permadeath itself.

### Decided (scoping)

- **Trigger points: combat can occur both during travel (via the existing per-window encounter roll) and at planet arrival.** This is a genuinely new trigger context — arrival-at-planet — not just an extension of the existing mid-voyage window mechanic. Both contexts can generate a combat encounter.
- **Combat encounters are interactive — the one deliberate exception to "all encounters resolve automatically."** When a combat encounter triggers, the player is presented with an explicit choice (attack or avoid/flee) rather than an automatic outcome. This is a genuine departure from the Travel Encounters decision that all three non-combat types resolve without player interaction — worth flagging clearly rather than letting it blur into that earlier rule, since combat is deliberately the exception, not a quiet reversal of it.
- **Resolution depth: shallow — a single resolved roll, win or lose, formula TBD.** Not multi-round, not real-time, not turn-based. Consistent with the whole project's grain toward formula-driven resolution over simulated systems (matching hazard's single-roll shape, just now with player-facing stakes and an interactive trigger rather than a fully automatic one).
- **Encounter-type shape: combat is a fourth type in the travel-window roll, but arrival-triggered combat is a separate mechanism sharing the same resolution logic — hazard is not replaced.** Hazard stays exactly as it is (automatic, currency-only), specifically because it was built to resolve during a background catch-up calculation with nobody necessarily watching — replacing it with combat would force every voyage's downside encounter to require player presence, breaking the "set it and forget it" model hazard exists to preserve. Combat is additive: a fourth entry in the existing weighted type-split table (trade-opportunity, discovery, hazard, combat), presumably weighted low, likely lower than hazard since it's the only interactive type and shouldn't interrupt a background voyage too often. **Arrival-triggered combat is its own trigger point**, since arrival is a discrete docking event the window-based system was never built to check — not a second roll through the same weighted table, but a separate check feeding into the **same underlying combat-resolution mechanism** as the travel-window version. One shared resolution formula, two distinct entry points.
- **Win/lose formula: symmetric rolls using the existing tier-variance pattern — weapon component tier vs. a rolled opponent threat tier, higher roll wins.** Reuses the existing Option A (weighted average + variance) and tier-variance table shapes rather than inventing a new formula. Opponent threat is generated the same way every other tier in this design is — a random 1-100 roll mapped through the shared breakpoint table, same mechanism as planets/crew/ships/scanners. Player strength uses the **weapon component's own tier specifically, not the derived ship tier** — the one deliberate departure from the "use averaged ship tier" pattern applied everywhere else (travel speed, hazard), because combat is the one context where a specific component genuinely should matter more than the average (a cargo hold shouldn't help you fight), and it's the first time the weapon component category — inert since Ships — actually does something. Both the player's weapon-tier roll and the opponent's threat-tier roll apply the same percentage-based variance already used everywhere (±10% base, narrowed by tier); the higher roll wins. Requires no new formula design — just a new pairing (weapon vs. rolled threat) applied to the existing pattern.
- **Flee cost: no direct penalty, but the voyage is redirected to the last safe planet — same retreat mechanic as a loss, minus the damage.** Fleeing and losing both end a combat encounter the same way mechanically (forced return, encounter-free during that trip) — they differ only in whether component/crew damage occurs. This avoids inventing a second, distinct outcome path: not reaching the original destination *is* the cost of fleeing, reusing the same mechanic already decided for losing rather than adding a new one (e.g., a "chance the fight happens anyway," which would need its own new roll and formula — avoided deliberately, consistent with Combat reusing existing formulas throughout). **Net shape, three outcomes:** fight-and-win (continue to original destination, no damage), fight-and-lose (redirected to last safe planet, component/crew damage), flee (redirected to last safe planet, no damage). Fighting is what lets a player actually reach their original destination without a detour; fleeing is the safe-but-inconvenient option.
- **Component damage: on a loss, the weapon component's `durability` quality takes a percentage-based reduction; tier recomputes immediately.** Only the weapon is affected — it's the component that fought (per the win/lose formula's weapon-vs-threat pairing), so damaging it specifically is the natural, self-explaining consequence rather than an arbitrary targeting rule needing its own justification. Only `durability` is affected — the one quality with an obvious thematic fit for combat damage, chosen over a random quality or all 5 to keep the effect explainable in one sentence and avoid designing an unnecessary distribution rule. **Percentage-based, not a flat point reduction** — consistent with nearly every other numeric change in this design (drift, refund chance, variance), scaling naturally regardless of the weapon's current quality rather than being crushing at low durability and negligible at high. After the reduction, the weapon's tier recomputes via `getTierColor()` (no new tier-mapping logic), and the ship's derived tier recomputes immediately too, reusing the exact pattern `assembleShip()` already established for "a component changed, recompute the ship." **This is the first time an existing crafted item's stats mutate after creation** — every prior mutation-adjacent case either rolled a fresh value or created a new item from inputs; worth naming explicitly as genuinely new territory even though every individual piece of the mechanic reuses something already built.
- **Crew damage: on a loss, one randomly-selected owned crew member (independent of any ship/voyage) becomes temporarily unavailable — reuses the upkeep-grace-period timestamp pattern, not a stat reduction.** Surfaces and resolves a structural gap: crew members currently have no relationship to a ship or voyage at all (crew crafting is a player-level resource, independent of ship travel) — rather than inventing a new "crew aboard ship" relationship just for this, the consequence is scoped to the player's entire owned crew roster, picked at random. **Mechanic:** a new `unavailableUntil: timestamp | null` field on `CrewMember`; on a loss, one owned crew member is selected at random and `unavailableUntil` is set to a tunable duration out — same shape as `lastPaidAt` + grace period, a different field for a different purpose. While in the future, that crew member cannot be **newly** assigned to a craft (active or idle); an already-in-progress craft is not interrupted, so the block only ever applies going forward, avoiding any need to reach into and cancel existing state. No change to tier, profession, or wage — a status, not a stat reduction, since crew (unlike components) have nothing quality-based to reduce. **If the player owns no crew, this consequence simply doesn't apply** — component damage still happens regardless, so a loss is never entirely consequence-free even without crew.
- **"Last safe planet" = the current voyage's `originPlanetId` — no new field, no separately-tracked location.** Reuses data already on the `Voyage` record generating the encounter, rather than tracking a persistent "last known safe location" that would need updating on every successful dock across the game. Holds up under multi-leg travel by construction — a voyage's origin is always the most recent point the player was safely docked, so there's no scenario where a separately-tracked field would give a different (or better) answer. **Retreat trip mechanics: reuses the existing `Voyage`/travel-time system entirely, with encounter rolling suppressed for that one trip** — a retreat is just another `initiateVoyage()` call (destination = the failed/fled voyage's origin), computed via the same `calculateTravelTime()`, resolved via the same `resolveArrival()`, with a flag causing `resolveEncounters()` to be skipped for that specific voyage. No parallel travel system built just for retreats — the smallest possible way to guarantee "encounter-free."
- **Loss consequences: lightweight, not permanent, three components:**
  1. **Minor component damage** — some form of quality/tier reduction on ship components, the mutation path explicitly deferred until now.
  2. **Minor crew damage** — some lightweight consequence for crew, distinct from the existing upkeep-based loss/attrition system; resolved below as temporary unavailability via a new timestamp field.
  3. **Forced retreat to the last safe planet, guaranteed encounter-free during that trip** — a mercy mechanic ensuring a loss doesn't spiral into repeated encounters on the way back.
- **Cargo is not forfeited on a loss — it returns with the ship to the origin, same as everything else affected by the redirect.** No fourth loss consequence added on top of the three already fixed (component damage, crew unavailability, forced retreat). The redirect itself already imposes the meaningful cost for the one case `Voyage.cargo` exists for — the Phase 3 remote-sale mechanic — since the cargo simply doesn't become an active listing at the destination on schedule if the ship never arrives. Separately destroying the cargo would be piling a second penalty onto the same failure. The player retains the option to retry the voyage, or handle the cargo differently at the origin.
- **Winning grants nothing beyond reaching the original destination — already implicitly settled by the flee-cost decision.** The three-outcome shape (fight-and-win: continue, no damage; fight-and-lose: redirected, damage; flee: redirected, no damage) already makes "actually getting where you were going" the win condition's reward — no separate loot/currency bonus layered on top. Consistent with hazard's existing asymmetry (fail costs something, pass costs nothing) rather than introducing a new "combat has its own payout" mechanic.

**Section status: all Combat questions resolved.** Combat is ready to move from design into agent contracts. Per the deferred-gaps sequencing, Multiplayer is the last remaining gap.

## Multiplayer

**Status: active design pass — scoping decisions made.** The fourth and last of the deliberately-deferred gaps. Unlike Scanner/Encounters/Combat, this is the first gap that requires genuinely new infrastructure rather than a client-side amendment — every browser client in this project so far has been self-contained; Multiplayer introduces the first need for something outside the client to exist at all.

**What was already built specifically for this moment, worth confirming still holds:** `Listing.createdByPlayerId` and self-trade prevention (Phase 3); the timestamp-not-duration pattern for background crafting (`lastCheckedAt`, elapsed time derived rather than trusted — Phase 4); `CrewMember.hiredByPlayerId`, `Ship.ownerId`, `Scanner.ownerId`, `Wallet.playerId` (every owned resource already carries player attribution). All of this groundwork remains valid and directly usable.

### Decided (scoping)

- **Multiplayer scope: asynchronous, market-and-leaderboard-only — no shared real-time presence.** Players never directly encounter each other on the map or in a shared simulation tick. Interaction happens through two channels: a shared influence on market pricing (see the Universe architecture below), and leaderboards. This deliberately avoids the most expensive multiplayer shape (live shared galaxy, real-time sync, conflict resolution) in favor of something that reuses the existing asynchronous/catch-up architecture pattern used throughout this entire project.

- **Leaderboard categories.** Core three, launching first: **net worth** (`Wallet.credits` + estimated market value of owned resources/components/ships — the single best "how are you doing overall" metric), **trading volume** (total Credits transacted through listings, buy + sell — rewards active participation over hoarding), and **highest crafted tier achieved** (best single crafted item ever produced — cheap to track via a max() over crafting history). Second wave, not required for initial launch: **fleet strength** (highest derived ship tier owned, or ship count), **combat record** (win/loss ratio or total wins), **exploration** (planets discovered, physical + scanner), **crew empire** (total crew owned, or highest-tier crew hired). Leaderboards are **identity-attached by design** — this is a different sharing model from the Universe layer below, which is anonymous by design; worth keeping that distinction explicit rather than assuming one privacy model covers both.
- **Net worth's "estimated market value" is a real formula, not a placeholder phrase — closing a gap the original bullet above left open.** Owned resource/component inventory is valued at `content.tradingBasePrices`'s base price per unit — the same stable anchor every drift/recovery mechanic already reverts toward — **chosen over a live `getGlobalPrice()` lookup** specifically because that throws for any held item not currently traded anywhere (an untradeable moment shouldn't make an item vanish from someone's net worth), and would make net worth swing on a single distant transaction rather than reflect a stable estimate of what's actually held. Owned ships are valued via `SHIP_PURCHASE_COST_BY_TIER[ship.tier]` — a ship's derived tier already reflects its installed components' quality, so this doesn't separately double-count component value already folded into the ship's own price. **Scoped to exactly the three asset classes the original decision named** (resources, components, ships) — owned scanners and crew are deliberately excluded from net worth for now; both are real owned assets, but extending the formula to cover them would be new scope, not a clarification of what was already decided.
- **Net worth extended to include planet ownership — a real gap, since this bullet predates Colonist-Driven Production/Citadels.** Owned planets add Σ(colonist transport credits actually spent on that planet) + Σ(citadel construction credits actually spent, across all levels built) — a **sunk-cost basis**, the same "fixed cost-basis lookup, not a re-derived live value" shape the resource/ship valuations above already use, chosen over trying to define a "current market value" for a citadel that no market anywhere prices. Reuses `transportColonists()`/`buildCitadel()`'s own recorded costs (`planet-ownership.md`) rather than inventing a second valuation formula.
- **Trading volume extended to include `sellToMarket()` — a real gap, since this bullet also predates Trading Counterparty.** "Total credits transacted" now means every `purchaseListing()` transaction **and** every `sellToMarket()` transaction, summed the same way — a player using exclusively the newer instant-sell path must not read as having zero trading activity. No new tracking mechanism: both already return a real credits amount from a real function call: the same place total volume was always going to be tallied from.

- **Universe architecture: private per-player Galaxies report anonymized aggregate signal to a Universe layer, which computes a per-item universal price modifier feeding into the existing `getGlobalPrice()` calculation.** Each player keeps their own private, single-player-shaped galaxy exactly as built through Phase 5 — nothing changes about the core local experience. Periodically, each galaxy reports aggregate activity signal upward (e.g., "how much iron ore did this galaxy's players collectively buy/sell in this period") — anonymized, not tied to individual player identity. The Universe layer aggregates that signal **across all players' galaxies** and computes a universal modifier per item; if the aggregate signal shows heavy selling of an item across the playerbase, its universal modifier trends down, and vice versa. This modifier becomes one additional input to the **already-existing** `getGlobalPrice()` function — the same function that already reads live local planet data just gains one more number to factor in. **This reuses the "global price reads live data" pattern already built rather than inventing a new pricing mechanism**, and gives genuine multiplayer *feel* (the whole playerbase's activity affects your market) without needing real-time presence, shared listings, or conflict resolution.

- **New infrastructure requirement, named honestly:** this is the **first thing in the entire project that requires an actual backend** — something has to aggregate data across players' galaxies, which no single browser client can do alone. Even at its smallest (a scheduled aggregation job + a small database), this is a genuinely new category of infrastructure nothing before this milestone has needed.

- **Exact implementation timing and shape of the Universe backend is explicitly deferred to when the project moves toward being an app rather than purely web-driven** — i.e., roughly aligned with (though not strictly gated by) the eventual Unity migration. The *conceptual* architecture above (Galaxy → anonymized signal → Universe aggregation → universal modifier → feeds `getGlobalPrice()`) is decided now; *how* it's actually hosted and what service/database it runs on are not. (**Correction:** an earlier version of this bullet also listed "exact report frequency" as undecided — that's stale; the report-frequency bullet below locks it to daily. Left only the genuinely-still-open items here rather than leaving a contradiction standing between two bullets in the same section.)

- **Confirmed: this does not change the Unity migration decision.** The web-stack-now/Unity-later decision was about the **client** (rendering, local simulation, presentation) — a Universe aggregation backend is a separate service that any client calls via an API to fetch the current universal modifier. The client doesn't care what's on the other end of that call. Building the Universe backend and migrating the client to Unity are orthogonal decisions; neither constrains the other.
- **Report frequency: daily, reusing the same 24-hour window already used for emergency triggers and the encounter-check cadence.** One less cadence to reason about across the whole game, and already proven to feel right at this game's pace. Matches the asynchronous, no-real-time-presence shape of Multiplayer as a whole — shorter would start implying real-time responsiveness (deliberately avoided); longer would make the "your activity affects the market" feedback loop too slow to feel meaningful. Also keeps the eventual backend's load as light as possible, consistent with deferring exact hosting decisions. **Left genuinely open, since it's a backend-implementation question rather than a "what does reporting mean" question:** whether a player's local game needs to be actively running for their galaxy's report to go out, or whether this happens server-side regardless.
- **Aggregation scope: everything tradeable, tiers 1-7 — not restricted to tiers 1-5.** The global market's tier 1-5 sell restriction exists for a specific, narrow reason (protecting tier 6-7 exclusivity by keeping them off the listing mechanism) that doesn't apply here — the Universe layer is a read-only signal, not a listing mechanism, and excluding tier 6-7 activity would make the layer blind to activity in the very items whose exclusivity is most invested in feeling real. **No curated subset either** — a subset would need its own selection rule with no natural basis in the existing data model; aggregating everything means no per-item allowlist to maintain as content grows. **Concretely (revised — see the modifier formula decision below for why):** a Galaxy's daily report is `{ itemId, quantitySold, quantityBought }` per item, not a single combined "quantity traded" figure — buying and selling need to be distinguishable so they can push the universal modifier in opposite directions. No filtering on the reporting side.
- **Anonymization: structural, not policy-based — the report itself never contains a player identifier at all.** Two ways to build "anonymized" were considered: policy anonymity (raw data includes identity, but the UI/API layer chooses not to display it — fragile, since identity still exists somewhere and the non-display is just a promise that can be broken) versus structural anonymity (the report never includes an identifier in the first place — nothing to leak, because the identifying thing was never in the payload). Chosen: structural. Since the aggregation-scope decision already defines the report shape as `{ itemId, quantitySold, quantityBought }` pairs, this isn't extra work — that shape simply has no place to put a *player* identifier. Same instinct as the timestamp-not-duration pattern from Phase 4 (design the data shape so the risky thing structurally can't happen, rather than trusting a rule to be followed). The Universe layer sums reports by item across all Galaxies and never has, and never needs, any way to attribute a report back to a specific player. **Contrast with leaderboards, worth restating:** leaderboards are identity-attached by design — the Universe layer and leaderboards are two different systems with two different privacy models, not one policy applied inconsistently. (This bullet is now scoped to *player* identity specifically — see the Galaxy registry decision immediately below for why a non-player-identifying galaxy token is a distinct, later addition, not a reopening of this one.)
- **Galaxy registry: a one-time registration event at game start, carrying a stable anonymous `galaxyToken` and that galaxy's own planet count — closing a real gap the per-capita formula below always had.** That formula divides by "the number of reporting Galaxies," but nothing before now specified how the Universe would actually know that number, or tell one galaxy's report apart from another's within a period, given the anonymization decision's report payload carries no identifier of any kind. **Chosen: a stable, non-player-identifying token** — a random ID generated locally the first time a game is created, never derived from or linked to `playerId`, never surfaced anywhere in the UI, existing solely so the Universe can count distinct galaxies and de-duplicate a retried/replayed report. **This does not weaken the anonymization decision above** — that decision's actual guarantee is "a report can never be traced back to a player," which a random per-galaxy token doesn't touch; it only lets the Universe tell "100 different galaxies each reported once" apart from "1 galaxy reported 100 times," a basic data-integrity need any aggregation system has, not a new identity leak. **Rejected: zero identifiers of any kind**, which would leave galaxy/player counts as estimates inferred from report volume rather than a real count — a purer privacy guarantee in the abstract, but not chosen, since the per-capita formula's correctness directly depends on knowing the real denominator, not an inferred one.
- **Planet count is reported once, at registration, not repeated on every periodic report.** `PLANET_COUNT` (`galaxy.md`, currently locked at 50) is a locally-decided constant that never changes after a galaxy is created, so resending it daily alongside trading volume would be reporting a static fact as if it were a changing metric. **The Universe does not assign or vary planet count per galaxy** — that would mean galaxy generation depending on the backend at creation time, breaking the standing "each galaxy stays fully private/local, playable with zero Universe dependency" principle everything else in this section already respects. The Universe's only job here is recording what each already-locally-decided galaxy reports, useful for an aggregate stat (e.g., "average planets per galaxy across the playerbase") and, structurally, nothing more.
- **Registered-galaxy count — the count of distinct `galaxyToken`s ever registered — is the real source of the per-capita formula's denominator, not a period's report count.** A galaxy with zero relevant trading activity in a given day still exists and still belongs in the per-capita denominator; counting only galaxies that *reported something* that period would silently exclude quiet ones and skew the modifier. Registration (a one-time event) and periodic activity reporting (daily) are two different signals for two different purposes, both keyed by the same `galaxyToken`.
- **The denominator uses a recently-active subset, not every galaxy ever registered — a real gap the original bullet above didn't anticipate.** Registration itself stays permanent (a `galaxyToken` is never deleted — still the correct source for a "total galaxies ever" census stat), but nothing before this specified what happens as saves get abandoned and restarted over the game's real-world lifetime: every new save registers a new token with no decrement path, so an ever-growing share of the registered count would eventually be dead galaxies that never report again, permanently diluting the per-capita modifier toward inert. **Chosen: the per-capita formula's denominator counts only galaxies whose `lastReportedAt` falls within a new `GALAXY_ACTIVE_WINDOW_DAYS`** (originated default, tunable) **of the current report cycle** — an "active" galaxy isn't a separate flag to set/unset, it's simply derived from how recently that `galaxyToken` last reported, the same "derive from a timestamp, never a stored boolean" discipline this design uses everywhere (crew attrition, upkeep grace periods). A galaxy that reports again after a long gap is immediately active again, no special-case re-activation logic needed.
- **A missed daily report catches up rather than silently vanishing — matching the timestamp-not-duration, always-catch-up pattern this entire design already uses for background crafting, voyage resolution, and market recovery.** Each galaxy's report covers activity accumulated since its own `lastReportedAt`, not a fixed prior-24h window — so a galaxy offline for 3 days reports 3 days of accumulated activity in one report when it next checks in, rather than losing 2 days of signal. **Chosen over a fixed-window report** (which would silently drop any activity older than the last 24h if a client missed its exact check-in) specifically because nothing else in this project punishes a player for being offline, and there's no reason the Universe layer should be the first exception.
- **Universal modifier formula: percentage-based multiplicative modifier, bounded by a floor/ceiling, driven by per-capita net volume — reusing baseline drift's exact shape.** Computed as `netVolume = quantityBought − quantitySold`, summed across all Galaxies' reports for an item, then divided by the **registered**-Galaxy count (the Galaxy registry decision above — not a period's report count, and not previously specified before now) to get **per-capita net volume** — normalizing by galaxy count is necessary, not optional, since driving the modifier off raw summed volume would mean the same trading behavior swings prices harder purely as the playerbase grows, unrelated to actual scarcity/abundance. That per-capita figure scales a percentage adjustment to the item's `getGlobalPrice()` output — same percentage-based mechanism as baseline drift — and the result is bounded within a **floor/ceiling**, the same defensive pattern already used for local drift, preventing a runaway universal price swing the same way local drift is already prevented from running away. **Concretely, closing a gap the original version of this bullet left unspecified:** the floor/ceiling reuses local drift's exact numeric bounds (`PRICE_FLOOR_PERCENT [0.5]` / `PRICE_CEILING_PERCENT [1.5]`, `planetary-markets.md`) as starting values, but through two new, independently-tunable constants — `UNIVERSAL_MODIFIER_FLOOR_PERCENT` / `UNIVERSAL_MODIFIER_CEILING_PERCENT` — rather than literally reusing the same named constants, since a backend-scoped universal modifier and a per-listing local drift bound are different enough in scope to deserve independent tuning later even though they start identical. The same "reuse the shape, not necessarily the literal constant" discipline Scanner's tier-scaling already applied (reusing the schematic contribution table's *shape*, not its values). Originated defaults, not locked example numbers, same status as every other tunable in this document. Net effect: the Universe layer isn't a new pricing mechanism, it's one more percentage-based modifier layered onto a function already built to accept live inputs, using the exact same shape (percentage, floor/ceiling) used for every other price-affecting system in this design.
- **Leaderboard computation/hosting: same backend infrastructure as the Universe layer, but a fundamentally different data flow, not shared computation.** Standing up a second, entirely separate backend just for leaderboards — when one is already needed for the Universe layer — would be duplicated infrastructure for no benefit; both share the same underlying need (something outside any single browser client that can see data across players). **But the flows must stay genuinely separate, not merged**, because they have opposite requirements on the axis that matters most: the registry/pricing side is structurally anonymous (no player identity anywhere in the payload), while leaderboards are identity-attached by design (meaningless without knowing whose score is whose). Sharing a single data pipeline would risk contaminating that anonymity guarantee. **Concretely: one backend, three genuinely separate report types** — a Galaxy sends a one-time, non-player-identifying `{ galaxyToken, planetCount }` registration at game start, a recurring anonymous `{ itemId, quantitySold, quantityBought }` report to the Universe pricing pipeline, and separately an identity-attached `{ playerId, netWorth, tradingVolume, highestCraftedTier, ... }` report to the leaderboard pipeline — zero data crossover between any of the three. **Left as a deferred implementation detail, not a design decision:** whether leaderboard reporting reuses the same daily cadence as Universe reporting (likely, for the same reasons already established) — small enough to sit alongside the other deferred backend specifics rather than needing to be locked now.

**Section status: all Multiplayer questions resolved (except backend technology/hosting choice, explicitly and deliberately deferred to when the project moves toward being an app).** This is the fourth and final deferred gap — with this section closed, every system in the original executive summary's scope, plus all four deliberately-deferred gaps (Scanner, Travel Encounters, Combat, Multiplayer), has a complete, locked design. Multiplayer's actual implementation (agent contracts, backend build-out) remains intentionally deferred per the app-conversion timing decision — this section exists so the conceptual architecture is ready whenever that timing arrives, not so it gets built immediately.

## Ship Fuel

**Status: active design pass.** Found while building a new "Ship" status screen for alpha playtesting: no fuel mechanic exists anywhere in the codebase today. "Fuel Canister," "Enriched Fuel Rod," and "High-Yield Fuel Core" are craftable resources whose names imply fuel, but mechanically they're just crafting-flavor inputs — `high-yield-fuel-core` feeds exactly one engine recipe (`fusion-engine`), `enriched-fuel-rod` feeds a *weapon* recipe (`plasma-emitter`), and `fuel-canister` is consumed by nothing at all. Unlike Scanner/Encounters/Combat, this isn't a previously-recorded deferred idea — it's new scope, so it gets the same design-then-contract discipline as everything else rather than being invented inline in a contract doc.

**Decided:**
- **Fuel is an abstract ship resource, not a consumable inventory item (Option A — credits-based, like the scanner/ship purchase pattern).** `Ship` gains two new fields, `fuelCapacity: number` (derived from tier, the same "component tier drives a stat" shape already used for `SHIP_TIER_SPEED_MODIFIER`) and `currentFuel: number` (mutated by travel and refueling, the same shape `Wallet.credits` already uses for a mutable resource pool). **Chosen over making one of the existing "fuel"-named crafted resources the literal consumed item** (repurposing `high-yield-fuel-core` or `fuel-canister` as a per-voyage inventory draw) — that option is more thematically satisfying and would finally give `fuel-canister` a purpose, but it would require scoping fuel to the player's global, currently-uncapped inventory (the same inventory-scoping question Cargo Hold Capacity, below, deliberately avoids answering for the general case) and would tie a locked system's blocking condition to the crafting/refining economy's output, adding a second failure mode (no fuel-item on hand vs. no credits) where this design wants exactly one. Left as an explicitly recorded future idea, not built: a later "premium fuel" tier where a crafted fuel item extends range or reduces consumption beyond what credits-refueling alone provides — a clean extension if the crafting economy ever wants a reason to make these items relevant, but not required now.
- **Fuel capacity scales with the ship's derived tier, not the engine component's own tier specifically.** This was the one real fork against precedent: Combat deliberately broke from "use averaged ship tier" and paired weapon-*component* tier directly against opponent threat, reasoned as "the one context where a specific component genuinely should matter more than the average." Fuel doesn't have that same justification — capacity is a whole-ship property (a bigger, better-outfitted ship holds more fuel across the board, not just a better engine), the same framing already used for travel speed (`SHIP_TIER_SPEED_MODIFIER` reads `Ship.tier`, not the engine component specifically). Keeping fuel on the ship-tier axis avoids a second "which specific component matters here" special case with no strong reason to introduce one.
- **`FUEL_CAPACITY_BY_TIER`: reuses `SCANNER_TIER_RADIUS_BONUS`'s exact per-tier delta shape (+0/+40/+80/+130/+190/+260/+350) on top of a 150 base**, rather than a new curve: Grey 150, White 190, Green 230, Blue 280, Purple 340, Orange 410, Gold 500. Reusing an already-designed curve shape is the same discipline Scanner's own tier-scaling decision already applied ("reuses the same 7-tier table shape already used for schematic contributions"). Originated default, not a locked example number from any design doc, same status as the crew wage table when it was first written — a tunable, adjustable via the existing debug-tuning-panel pattern once implemented, not a number this document is locking in stone.
- **`FUEL_COST_PER_DISTANCE_UNIT = 0.03`, applied the same way `DISTANCE_TO_TRAVEL_HOURS_PER_UNIT` already is** (`calculateFuelCost(origin, destination) = calculateDistance(origin, destination) * FUEL_COST_PER_DISTANCE_UNIT`, mirroring `calculateTravelTime()`'s own shape) — **deliberately not tier-modified**, unlike travel time. A faster (higher-tier) ship reaching a destination sooner doesn't burn less fuel for covering the same physical distance; tier's fuel-relevant effect is capacity (how far a full tank reaches), not efficiency (cost per unit distance) — one job per tier-driven number, the same discipline already applied to keep planet tier scoped to gathering only and ship tier scoped to speed only. **Sized against the galaxy's real geometry, not picked arbitrarily:** the position range (`POSITION_RANGE = 1000`, Galaxy & Planet Generation section) bounds the maximum possible distance between any two planets at ~2,828 units; at 0.03 fuel/unit that's a ~85-fuel worst case, comfortably under even Grey tier's 150 capacity — chosen specifically so **no route is ever structurally unreachable** for a low-tier ship, only more likely to need a refuel stop along the way. A steeper cost that could exceed Grey's capacity on some real route was explicitly rejected — that would make some destinations permanently unreachable for a Grey-tier ship regardless of wallet size, a harder wall than anything else in this design imposes (every other tier gate is "worse/slower/riskier," never "impossible").
- **Consumption and the insufficient-fuel check happen once, at voyage initiation — never mid-voyage.** `initiateVoyage()` computes the fuel cost via `calculateFuelCost()`, rejects if `ship.currentFuel < cost` (same shape as `hireCrew()`'s capacity precondition check — a hard rejection before anything is created, not a partial/interrupted state), and deducts the cost from `ship.currentFuel` on success, same moment `arrivesAt` gets locked in. **A mid-voyage "ran out of fuel, stranded" failure state was considered and rejected**, for the exact reason Hazard's design already rejected a voyage-delay outcome: `arrivesAt` is locked at initiation and never recomputed mid-flight, and a stranding mechanic would need to either break that rule or invent a whole new "partial voyage" state — the same complexity Hazard's own design entry already ruled out once. Fuel is a gate on *starting* a voyage, not a risk during one.
- **Refueling: a new Shipyard action, `refuelShip(ship, wallet, amount)`, credits-per-unit — reuses the exact shape `purchaseScanner()`/`purchaseShip()` already established** (check funds, deduct credits, mutate state, return a typed result). `REFUEL_COST_PER_UNIT = 2` (originated default, same status as the capacity table above) — buying a full tank from empty costs at most 300cr at Grey tier (150 × 2), in the same ballpark as `SHIP_PURCHASE_COST_BY_TIER`'s own Grey-tier price (300cr) and `SCANNER_PURCHASE_COST_BY_TIER`'s Grey-tier price (200cr), so it reads as a comparable recurring cost rather than an outlier. Available at any planet with a shipyard (no new pool/refresh-interval mechanic needed — unlike ships/crew/schematics/scanners, fuel isn't a discoverable/tiered item with its own rarity, it's a flat-rate resupply, the same reasoning that already kept the trading market's transaction fee a flat percentage rather than a rolled/pooled value).
- **No interaction with Combat, Encounters, or Scanner.** A combat loss already damages the weapon component and benches crew — fuel is untouched by any encounter outcome, keeping this addition isolated to `initiateVoyage()`/a new Shipyard action, the same "one job per system" discipline this document applies everywhere. Explicitly **not** revisited: hazard's currency-cost-on-failure outcome does not additionally drain fuel; that would be stacking a second penalty onto the same failure, the identical reasoning Combat's own design already used to keep cargo un-forfeited on a loss.

**Amendment — Fuel Management (retuned capacity), found via `docs/profitable-tradewars-alignment.md`'s "turns" open question, resolved this pass.** TW2002's entire economy is organized around turn scarcity — a session-limited resource creating constant "what do I spend this on" tension. Confirmed as a genuinely open question, never revisited until now; explicitly **not** adopting a turns-equivalent (would contradict the real-time/catch-up architecture reaffirmed at least four separate times this project: Universe reporting, resource reset cycles, background crafting, and Fuel itself). Chosen instead: lean further into Fuel, the closest existing analog, rather than invent a second scarce resource alongside it.

- **The actual numbers above never created any real constraint — found on review, not assumed.** At `FUEL_COST_PER_DISTANCE_UNIT = 0.03` and `POSITION_RANGE = 1000`, the single most expensive possible trip (the ~2,828-unit max diagonal) costs ~85 fuel — comfortably under even Grey tier's *original* 150 capacity. **A brand-new Grey-tier ship could already reach any planet in the galaxy in one hop, at every tier, always.** Fuel gated nothing beyond "do you have credits to refuel eventually" — no route planning, no "can I make it" tension, ever.
- **This directly reopens this section's own earlier reasoning ("no route is ever structurally unreachable... a steeper cost... was explicitly rejected") — acknowledged, not silently reversed.** The original goal (no *permanently* unreachable destination) is preserved under a narrower reading: every route stays reachable *eventually* — via a shorter multi-hop route through already-discovered planets, or by upgrading ship tier — just not always in a single hop at low tiers anymore. Gold tier is deliberately retuned to still comfortably cover the single worst-case trip alone, so the top of the ship-progression ladder keeps the original "go anywhere, no fuel anxiety" guarantee — it's specifically the lower/mid tiers where real constraint now exists.
- **Two other candidate levers were considered and explicitly not adopted here, left as smaller, independent follow-ons if this doesn't create enough tension alone:** per-planet fuel price variance (reusing `planetary-markets.md`'s drift/season/emergency machinery, applied to `REFUEL_COST_PER_UNIT` instead of trade goods) and scarce refuel availability (not every planet has a shipyard). Both are real, larger design passes of their own — bundling either in now would conflate "is range a real constraint" with "is refueling itself a spatial-economic decision," two different questions.
- **`FUEL_CAPACITY_BY_TIER`, retuned**: Grey 50, White 65, Green 80, Blue 100, Purple 125, Orange 155, Gold 190 (down from the original 150→500 table, same 7-tier shape, ratio slightly widened rather than a flat rescale). Chosen so an **average** trip (the mean distance between two uniform-random points in the 2000×2000 galaxy, ~1,042 units, ~31 fuel) stays comfortably affordable even at Grey (well under the tank), while the **worst-case** trip (~85 fuel) exceeds Grey/White/Green's capacity outright and is only just barely within Green's reach — Blue is the first tier that can always reach anywhere in one hop (100 > 85), with Purple/Orange/Gold widening that margin further. Blue already reads as a meaningful mid-game threshold in this design (Ship Crew Roles' Combat-Engineer-and-Science-Officer-both-at-once unlock lands there too) — this reinforces rather than invents that reading.
- **New, narrowly-scoped exception: the starting ship's initial `fuelCapacity`/`currentFuel` are set to a flat `STARTING_SHIP_FUEL_CAPACITY = 100`, not `FUEL_CAPACITY_BY_TIER[Grey]`'s new, tighter value — the same "bootstrap exception, not a general rule change" shape `galaxy.md`'s `discovered: true` override and `planet-ownership.md`'s colonist pre-population already established.** Found necessary on review: the two bootstrap planets' *positions* are rolled on a stream fully independent of which planets they are (`galaxy.md`), so nothing guarantees `secondaryDiscoveredPlanet` is anywhere near `startingPlanet` — an unlucky seed could roll them near-max-diagonal apart, and at the new, tighter Grey capacity (50), that specific trip could be **structurally impossible** for a player who has no other ship yet and no fuel-affording credits yet, an actual softlock risk this design pass must not introduce. `100` is chosen to comfortably clear the ~85-fuel worst case with margin, matching Blue tier's own value not by coincidence but because both needed to independently satisfy "always covers the worst-case single trip." **This is a starting-ship-only value, not a Grey-tier rule** — `deriveFuelCapacity()` recomputes from the normal `FUEL_CAPACITY_BY_TIER` table on the ship's very first component change (`assembleShip()`'s existing "recompute on change" behavior), so the bootstrap headroom naturally expires the moment a new player starts actually modifying their ship, not before.

**Section status: built.** `Ship.fuelCapacity`/`currentFuel`, `deriveFuelCapacity()`, `calculateFuelCost()`, `refuelShip()`, and the `initiateVoyage()` fuel precondition (skipped for retreats) all implemented and tested. `ShipyardScene` shows a fuel readout and a `> Refuel` action per docked ship. **Known gap, honestly flagged:** `STARTING_SHIP_FUEL_CAPACITY` has no applying code path — there is no real new-game starting-ship bootstrap in this codebase (only the debug-only `devSeed.ts`), so every `Ship` is either purchased (full tank at its own tier) or produced by `assembleShip()`'s recompute; the bootstrap-exception machinery is implemented correctly but currently unreachable. Contracts: `agent-01-amendment-ship-fuel-cargo-crew-roles-schema.md`, `agent-20-amendment-ship-fuel-cargo-crew-roles-core.md`, `agent-22-amendment-ship-fuel-cargo-crew-roles-presentation.md` — see `docs/functional-agents/ship.md`/`travel.md` for the consolidated contracts.

## Cargo Hold Capacity

**Status: active design pass.** Also found while scoping the new Ship status screen. This one *is* a previously-recorded gap, not new scope: "cargo hold → capacity" was named back in the Ships section as one of the four components' intended effects, then explicitly left as "a balance/design detail for whenever these systems get built, not something needed now." Nothing built it — `Ship.components.cargoHold` has always been structurally identical to the other three slots (contributes to `deriveShipTier()`'s average, nothing else), and the one place a numeric cargo limit would matter, `Voyage.cargo` (the Phase 3 remote tier-6/7-sale mechanic), has always accepted any array with no validation against ship state at all.

**Decided:**
- **Scope: constrains `Voyage.cargo` only — general gathered/refined/crafted inventory is explicitly out of scope, not an oversight.** The player's inventory (`src/presentation/inventory.ts`) is global, unscoped to any ship, and uncapped by design everywhere else in this project — Gather, Refine, Craft, and both Market screens all read/write it with no size concept anywhere. Capping it now would mean retrofitting a capacity check into four already-built, already-locked systems to serve a feature whose only current real use case (remote tier-6/7 sale while traveling) doesn't need it. **Chosen over a whole-inventory cap** for the same reason planet tier stays scoped to gathering and ship tier stays scoped to speed: one job per system, and `Voyage.cargo` is the one place a "how much can this trip carry" question already has a natural home.
- **`CARGO_HOLD_CAPACITY_BY_TIER`: a new 7-tier table, max total item *quantity* summed across a voyage's `cargo` array (not distinct entry count)** — Grey 5, White 8, Green 12, Blue 18, Purple 25, Orange 35, Gold 50. Originated default, same status as the fuel tables above — a smaller, more modest curve than fuel's, reflecting that this constrains an occasional remote-sale trip's cargo, not a primary resource-hauling mechanic (general trading stays inventory-based, at the player's current planet, exactly as already built).
- **Enforced once, at `initiateVoyage()` — same moment and same shape as the new fuel check**, rejecting if the sum of the supplied `cargo` array's quantities exceeds the ship's `cargoHold` capacity. No partial-load/overflow-left-behind behavior — a hard precondition, consistent with fuel's own "gate at the start, never mid-voyage" decision immediately above.
- **This does not, by itself, wire `Voyage.cargo` into the UI.** `TradeMapScene.onInitiateVoyage()` has always passed `cargo: []` — no scene currently lets a player choose what to carry on a voyage at all, a pre-existing gap independent of capacity. This decision gives the field a real capacity rule to build against; actually letting a player load cargo onto a voyage (a Presentation-layer concern) is separate follow-on scope, tracked in `docs/functional-agents/travel.md`, not resolved here.

**Section status: built.** `CARGO_HOLD_CAPACITY_BY_TIER` and the `initiateVoyage()` cargo-quantity precondition (Grey-tier default with no `cargoHold` installed, skipped for retreats) implemented and tested. `ShipStatusScene` displays the active `cargoHold` tier's capacity number. Contracts: `agent-01-amendment-ship-fuel-cargo-crew-roles-schema.md`, `agent-20-amendment-ship-fuel-cargo-crew-roles-core.md` — see `docs/functional-agents/ship.md`/`travel.md` for the consolidated contracts.

## Planet Resource Generation (Fixed Quality, Reset Cycle, Tutorial Guarantee)

**Status: active design pass — deliberately reopens two previously-closed doors.** Found while reviewing what `docs/functional-agents/planet.md` should own going forward. Unlike Ship Fuel/Cargo Hold Capacity (genuinely new, additive scope), this section changes how two **already-built, already-locked** mechanics work:

- **Gathering's core premise** (Resources & the 5 Qualities section, and `rollQualityOnPlanet()`'s own contract): quality has been rolled **fresh, randomly, at the moment of gathering** since the MVP. This section replaces that with **one fixed quality per resource per planet**, rolled once at generation (and again each reset cycle, below) — gathering becomes a deterministic read, not a roll.
- **Galaxy & Planet Generation's original resource-assignment model** (`generatePlanet()`'s contract): a planet's `producibleResourceIds`/`specialtyResourceId` were rolled once, permanently, for the planet's lifetime. This section adds a periodic reset cycle that re-rolls both — plus, now, their fixed qualities — without changing tier, type, or position, which stay permanent.

Both reopenings are deliberate, not scope creep discovered mid-implementation — matching the discipline Combat's own design pass used when it knowingly reopened "no ship component degradation" and "no crew loss," rather than treating a locked decision as untouchable forever.

**Decided:**

- **Planet Types move under Planet's explicit ownership, and are confirmed to already be indicative of resource type — no new types needed.** `PlanetType` (`Terrestrial`/`SuperEarth`/`Neptunian`/`GasGiant`) and `PLANET_TYPE_ELIGIBILITY` (`docs/functional-agents/planet.md`) were always *implemented* by planet generation, but never formally called out as a concept Planet is the authority on. Reviewed against "should be indicative of the types of resources available": Terrestrial (Solid+Crystal — a rocky world, ores and crystals) → SuperEarth (Solid+Crystal+Gas — a large world with everything, the richest type by design) → Neptunian (Gas+Crystal — an ice giant, gas and crystalline ices) → GasGiant (Gas only — no solid surface at all) already reads as a coherent, self-explaining progression from "has everything" to "gas only," not an arbitrary label set. **No renaming or new types decided here** — the existing mapping already satisfies the goal; this decision formalizes ownership and confirms the review, it doesn't change the table.

- **Fixed quality per planet-resource (Option A — rolled once at generation/reset, never at gather time).** Each producible resource on a planet gets exactly **one** `QualityRoll`, computed via the existing `rollQualityOnPlanet()` formula (unchanged — same tier modifier, same specialty bonus, same clamp) but called **once per resource per generation/reset cycle**, not once per gather action. Gathering the same resource from the same planet twice now returns the identical quality both times. **Chosen over keeping gather-time variance**, because the whole point of this pass is to make a planet's resources a legible, comparable fact ("this planet reliably produces X-grade Iron Ore") rather than a per-click gamble — consistent with treating planet choice, not gather-spam, as the meaningful decision (the same instinct A3's own "is the difference in output quality obviously noticeable" playtest question was already gesturing at). Refining's and crafting's *own* variance rolls (`refine()`/`craft()`'s `tierVariance`) are completely untouched — this only removes randomness from the gather step itself, not from what a player does with the gathered material afterward.

- **The reset cycle is derived live from `(planetId, now)`, with zero persisted state — reusing `getCurrentSeason()`'s exact architecture, not inventing a new one.** A new `PLANET_RESOURCE_RESET_INTERVAL_HOURS` constant (originated default: **168 hours / 7 days** — long enough that a planet's resource identity feels stable across a normal play session, short enough that the galaxy's economy genuinely shifts over a longer campaign; a tunable, not locked in stone). A planet's current reset-cycle index is computed the same way `getCurrentSeason()` computes a season: hash `planetId` into a phase offset (so planets don't all reset in lockstep), then floor-divide elapsed time by the interval. **No new persisted field, no background job** — the same "always live, never cached, never stale" property `galaxy.md` already guarantees for the whole galaxy (deterministic regeneration from a seed) extends naturally to the resource layer once time becomes one more input to *that specific sub-roll*, not to tier/type/position, which stay on the original, permanent seed stream and never re-roll. **Already-gathered inventory is never retroactively affected** — a reset changes what a planet offers *going forward*; an item already in a player's inventory keeps whatever quality it had at the moment it was gathered, the same "no existing item mutates after creation" rule this design has held everywhere except Combat's deliberate, explicit exception.

- **Starting-planet tutorial guarantee: a deterministic clamp, not a reroll-until-it-works loop.** The starting planet must always be able to produce Igneous Ore, Autunite Crystal, and Hydrogen Gas (the MVP tutorial's gather → refine → craft chain: Radiant Alloy Bar, then Ion-Forged Hull Plate) with each one's **aggregate quality tier** (via the existing `computeAggregateTier()`, the same straight-average-to-tier formula ship/listing tier already reuse) landing in the **Grey or White band specifically** — not the planet's own overall rolled tier, which stays whatever it naturally rolls (per this session's earlier clarification). **Mechanism: if the normal roll for one of these 3 resources would land above 60** (White's own ceiling), **each of its quality dimensions is clamped to 60** rather than re-rolled — a direct, closed-form override, not a retry loop (this project has never used a retry-until-valid pattern anywhere; a clamp is consistent with how every other guardrail here works, from quality clamping itself to price floor/ceiling). If a resource isn't in the planet's naturally-rolled `producibleResourceIds` at all, it's added directly, bypassing the normal subset-selection draw for just these 3 slots. **Reapplied on every regeneration, including every reset cycle, not just the first** — idempotent, so a returning player's starting planet can never drift out of tutorial-viability after a reset. **Scoped to the starting planet only** (`galaxy.md`'s `startingPlanet`, not `secondaryDiscoveredPlanet`) — the tutorial only needs one guaranteed planet, and extending the override further would blunt the "planets genuinely differ" premise this whole design pass is trying to strengthen.

- **Interaction with refining/crafting thresholds, named honestly, not fully resolved here.** Ion-Forged Hull Plate's schematic-backed recipe checks Radiant Alloy Bar's *refined* durability against a 60 threshold — a Grey/White-band raw input, run through `refine()`'s own averaging and variance, may or may not comfortably clear that threshold depending on the exact tunable values in play at the time. This section guarantees the raw materials are *present and appropriately humble*; it does not re-derive or re-tune `refine()`/`craft()`'s own thresholds to guarantee a specific tutorial outcome — that's a balance/playtesting question for whoever implements this, flagged here rather than silently assumed to work.

**Section status: built.** `Planet.resourceQualities`, `getPlanetResourceCycleIndex()`, `generateResourcesForCycle()`, `getCurrentPlanetResources()`, and the starting-planet tutorial guarantee all implemented (`src/galaxy/planetResourceCycle.ts`, new; `src/galaxy/generatePlanet.ts`/`resourceSubset.ts`, amended), `GatherScene` reads through `getCurrentPlanetResources()` instead of rolling at click time, tested (`tests/galaxy/planetResourceCycle.test.ts`), full suite green with zero regressions. Contracts: `agent-01-amendment-planet-resource-generation-schema.md`, `agent-08-amendment-planet-resource-generation-core.md` — see `docs/functional-agents/planet.md` and `docs/functional-agents/mining.md` (renamed from `gathering.md`) for the consolidated contracts. This knowingly reopened Gathering's and Galaxy & Planet Generation's original "resolved" status, the same way Combat knowingly reopened two closed doors before it — recorded here explicitly rather than left implicit.

## Ship Crew Roles

**Status: active design pass — new territory, not a reopening.** Found while scoping what `docs/functional-agents/ship.md` should own. Confirmed by research before any of this was decided: `CrewMember` has **zero** connection to any `Ship` today — no `shipId`, no assignment table anywhere. Combat's own crew-unavailability mechanic deliberately draws from the player's *entire* roster, not a ship-specific one (`src/ships/README.md`'s own Combat-amendment section: "CrewMember.unavailableUntil is set here as a plain field mutation... nothing about attrition, hiring, or dismissal logic is read or written"). This section is genuinely new scope, not a correction to anything.

**A naming collision, resolved before anything else:** the requested role set (Pilot, Combat Engineer, Science Officer, Engineer, one of the crafting professions) puts a plain "Engineer" role right next to the **existing** tier-6/7 crafting profession `"Engineer"` (`TIER_6_7_PROFESSIONS`, `docs/profitable-alpha-content-roster.md` §5-adjacent, already shipped in content and already meaning specifically "crafts engine-category components"). **Chosen: the new ship-bridge role is named "Systems Engineer"**, not "Engineer" — cheaper to rename the not-yet-built concept than the one already live in content, seeded in `devSeed.ts`, and displayed in `CrewScene`. The crafting-profession `Engineer` is untouched.

**Decided:**

- **Architecture: extends the existing `CrewMember`/hire/wage/upkeep/attrition system — no second crew economy.** `CrewMember` gains two new fields: `shipRole: ShipCrewRole | null` and `assignedShipId: string | null`, where `ShipCrewRole = "Pilot" | "Combat Engineer" | "Science Officer" | "Systems Engineer" | "Crafter"`. A ship-role assignment is a **separate action from hiring** — a new `assignToShipRole(crewMember, ship, role)` function (mirrors `assignToCraft()`'s shape: takes an already-hired, idle `CrewMember`, doesn't touch the hiring/pool/wage machinery at all) — not a new candidate-pool roll, not a new cost table. **Reuses everything already built**: the assigned crew member still draws a wage (`CREW_WAGE_BY_TIER`), still needs `payUpkeep()`, still attritions on unpaid grace period, exactly like any other hired crew member — a ship-role assignment changes *what they do*, not *how they're owned*. The starting ship's 4 role-holders are simply pre-hired and pre-assigned at game start (`devSeed.ts`-equivalent for a real new game), not a mechanically distinct category of crew.
- **The `"Crafter"` role slot reuses the existing `profession` taxonomy directly — no new crafting-specialty concept.** A crew member can only be assigned `shipRole: "Crafter"` if `profession !== null` (i.e., only tier-6/7 crew) — their *specific* profession (`Weaponsmith`/`Engineer`/`Shield Technician`/`Cargo Specialist`/`Artisan`) is what determines the slot's effect (below), read directly off the field that already exists. This is the one slot explicitly named "one of the crafting professions" rather than a new role, and it's implemented as exactly that — zero new taxonomy for this slot.
- **Eligibility for the other 4 roles: any crew member, any tier, `profession` or not.** Pilot/Combat Engineer/Science Officer/Systems Engineer are a genuinely new dimension, independent of the tier-6/7-only profession concept — this gives tier 1-5 crew (currently cosmetically undifferentiated) a real way to specialize for the first time, without touching the existing hire-pool profession rolling at all.
- **Slot composition scales with the ship's own derived tier — reusing the tier-driven-effects pattern `SHIP_TIER_SPEED_MODIFIER`/`FUEL_CAPACITY_BY_TIER` already established, not a new component category.** A new `CREW_SLOTS_BY_TIER` table (originated default, tunable):

  | Tier | Pilot | Combat Eng. / Sci. Officer | Systems Eng. | Crafter | Total |
  |---|---|---|---|---|---|
  | Grey | 1 | 1 (either, not both) | 1 | 1 | 4 |
  | White | 1 | 1 (either) | 1 | 1 | 4 |
  | Green | 1 | 1 (either) | 1 | 2 | 5 |
  | Blue | 1 | 2 (**both** at once) | 1 | 2 | 6 |
  | Purple | 2 | 2 (both) | 1 | 2 | 7 |
  | Orange | 2 | 2 (both) | 2 | 2 | 8 |
  | Gold | 2 | 2 (both) | 2 | 3 | 9 |

  **Chosen over a 5th ship component ("crew quarters")** — Ships already closed "four categories, no more for now" at least three separate times in this document (most recently reaffirmed by Scanner's form-factor decision); introducing a component-driven crew-capacity stat would directly reopen that closed door for a feature that fits ship *tier* (an aggregate, whole-ship property, the same framing already used for fuel capacity) at least as well. **The Grey/White row matches the requested "starting ship" composition exactly** (1 Pilot, 1 either-or, 1 Systems Engineer, 1 Crafter) with no scaling until Green — a genuinely new ship doesn't outgrow the starting composition immediately. **Blue is where the either-or slot doubles into both-at-once** rather than a straight linear +1-per-tier climb, chosen so the Combat-Engineer/Science-Officer choice stays a real tradeoff through the early-mid game rather than becoming moot the moment a player upgrades once.

- **Role modifiers — recommendations, reusing an existing formula shape wherever one already fits (per the request to explore this "based upon the current design"):**

  - **Pilot → an additional travel-time multiplier, stacking with `SHIP_TIER_SPEED_MODIFIER`.** A small new tier-keyed table (originated default, e.g. Grey 1.0 down to Gold 0.9 — a modest secondary effect, ship tier stays the *primary* speed driver) applied to the Pilot's own crew tier, multiplied into `calculateTravelTime()`'s existing computation alongside the ship-tier modifier. **Alternative considered:** reducing `FUEL_COST_PER_DISTANCE_UNIT` instead (a fuel-efficiency angle) — also coherent, since Ship Fuel's own design deliberately kept fuel cost *ship*-tier-independent, leaving room for a *crew*-tier lever without contradicting that decision. Either is defensible; speed is the more immediately legible "pilot" association, so it's the primary recommendation, with fuel efficiency flagged as a strong alternative if travel speed ends up feeling over-stacked once Ship Fuel is also in play.
  - **Combat Engineer → mitigates the cost of a combat loss, not the odds of winning.** Reduces `COMBAT_COMPONENT_DURABILITY_DAMAGE_PERCENT` and/or `COMBAT_CREW_UNAVAILABLE_DURATION_HOURS` by a tier-scaled percentage when present for a combat resolution, reusing the same "tier scales a mitigation" shape `HAZARD_SHIP_TIER_MODIFIER` already established. **Chosen over boosting the attack roll itself** — the weapon component already owns offense (`resolveCombatChoice()`'s weapon-tier-vs-threat formula); giving Combat Engineer a defensive/mitigation job instead keeps "one job per system" intact rather than making weapon tier and Combat Engineer redundant levers on the same number.
  - **Science Officer → an additional scan-radius bonus, stacking with the scanner item's own `SCANNER_TIER_RADIUS_BONUS`.** Same shape, smaller magnitude, keyed off the Science Officer's own crew tier rather than the scanner item's tier — two independent levers on scan range (one item-driven, one crew-driven), consistent with how fuel now has both a ship-tier capacity lever and (per Pilot, above) a potential crew-tier efficiency lever.
  - **Systems Engineer → the first repair mechanic in the game, closing a real gap.** Today, combat-damaged component durability is **permanent** — nothing anywhere restores it short of crafting a full replacement, which sits oddly against Combat's own explicit design intent ("lightweight... a real but non-devastating consequence"). Recommended: while assigned, a Systems Engineer restores a small, tier-scaled amount of durability to damaged components over elapsed time (reusing the exact "derive from elapsed hours since a timestamp, capped, no background job" pattern `resolveBackgroundCrafting()` already established, via its own independent cap constant rather than reusing crew's `ELAPSED_TIME_CAP_HOURS`). This is the one recommendation that adds a genuinely new capability rather than an additional multiplier on an existing one — flagged as such, since it's the biggest single piece of new scope among the five. **Unconditional — applies regardless of whether the ship is docked or traveling**, the one repair source with no location gate; see the Crafter bullet below and the Citadels section for the other two, and `ship.md`'s `resolveComponentRepair()` for how the resulting 3-way combination was resolved on a later review pass.
  - **Crafter → lets the ship's onboard specialist repair their own matching component category while traveling, reusing the existing profession↔category mapping.** A `Weaponsmith` aboard repairs the weapon slot, `Engineer` the engine, `Shield Technician` the shield, `Cargo Specialist` the cargo hold (a natural, thematically-tidy pairing with `ship.md`'s own new Cargo Hold Capacity effect) — reusing `resolveComponentRepair()`'s exact shape (Systems Engineer, above), scoped to only the one matching category, stacking additively with Systems Engineer's any-category repair when both are assigned. **Note found on a later review pass:** `ship.md`'s own consolidated contract initially mis-summarized this as "a bonus to the matching component category," which read as a `craft()`-formula bonus rather than a repair mechanic — corrected there to match this entry exactly; this bullet's wording ("repair," not "bonus") is and was the actual decision.
  - **`Artisan` (the one profession not tied to a component category) — resolved on the same later review pass: a material-quantity discount on general (non-component) crafting, applied entirely upstream of `craft()`.** `CraftScene` reduces a matching general recipe's required input quantity when an assigned Artisan is aboard the active ship — `craft()` itself is never touched, no new parameter, no crew read anywhere in `src/simulation/craft.ts`. **Chosen over a `craft()`-formula bonus** (mirroring `crafterTier`/`schematicTier`'s ceiling-raise/variance-narrowing shape) specifically to avoid amending `craft()`'s signature or compromising `crafting.md`'s existing crew-agnostic contract — cheaper to make, never better/more-consistent quality, a genuinely distinct axis from the two formula-level bonuses that already exist. Originally left as an open magnitude/mechanism question; the mechanism is now decided, the exact discount percentage remains a tunable, same status as every other new numeric value in this document.

- **Must not create a 5th `ComponentCategory`** — crew slots scale by ship tier, never by a component, for the reason given above.
- **Must not let ship-role assignment bypass hiring, wages, or attrition** — `assignToShipRole()` operates on an already-hired `CrewMember` exactly like `assignToCraft()` does; it is not a second way to acquire crew.
- **Must not let a crew member hold two ship-role slots at once, on the same ship or different ships** — `assignedShipId`/`shipRole` together represent exactly one assignment; reassigning clears the previous one, mirroring how a `ShipComponent` can't occupy two slots at once.
- **Must not gate the 4 non-Crafter roles by tier or profession** — any hired crew member is eligible, by design, so tier 1-5 crew have a real use here for the first time.

**Section status: built.** `CrewMember.shipRole`/`assignedShipId`, `CREW_SLOTS_BY_TIER`, `getCrewSlotsForShip()`, and `assignToShipRole()` all implemented and tested. All 5 role effects are built: **Pilot** (`calculateTravelTime()`), **Combat Engineer** (`resolveCombatChoice()` mitigation), **Science Officer** (`performScan()` radius bonus), **Crafter/Artisan** (`CraftScene`'s material-quantity discount, `craft()` itself untouched), and **Systems Engineer** (`resolveComponentRepair()`, task #89 — unconditional repair regardless of docked/traveling, additively stacking with the Crafter role's own matching-category repair sub-effect and a Citadel Level 3's repair rate, wired into `ShipStatusScene`'s new `> Check Repair` action, 16 tests in `tests/ships/resolveComponentRepair.test.ts`). New `ShipStatusScene` shows role occupancy, a durability readout per component, and an assignment control (no `> Unassign` action yet — reassignment only); `CrewScene` shows a read-only `shipRole`/`assignedShipId` indicator. Exact modifier magnitudes (Pilot's tier table, Combat Engineer's mitigation %, Science Officer's radius bonus, Systems Engineer/Crafter/Citadel repair rates) were originated defaults, not locked here, and remain tunable. Contracts: `agent-01-amendment-ship-fuel-cargo-crew-roles-schema.md`, `agent-16-amendment-ship-crew-roles-core.md`, `agent-20-amendment-ship-fuel-cargo-crew-roles-core.md`, `agent-22-amendment-ship-fuel-cargo-crew-roles-presentation.md` — see `docs/functional-agents/ship.md` for the consolidated contract.

## Trading Counterparty (Instant Market Transactions)

**Status: active design pass — fixes a verified bug, not a reopening of anything intentionally built.** Found via `docs/profitable-tradewars-alignment.md`'s comparison against TradeWars 2000/2002's permanent-NPC-port model, confirmed by reading the real code: in single-player mode there is exactly one `playerId`, `purchaseListing()`'s self-trade check permanently blocks a player from buying their own listing, and nothing else can either — so every listing a solo player creates via `MarketScene`'s sell action is permanently unpurchasable. A one-time `SEED_MARKET_PLAYER_ID` seeds a few starter listings as a workaround, but nothing refreshes it; past `LISTING_EXPIRY_HOURS` (72h) or once those sell out, solo trading has no counterparty left, ever, with no error anywhere signaling it. This was never a deliberate design decision to reopen — `createListing()`/`purchaseListing()`'s own contracts never claimed to solve single-player viability, they just never got a mechanism that does.

**Decided:**

- **Fix: an instant "sell to market" action, not a synthetic NPC listing pool.** A new function, `sellToMarket(itemInstance, quantity, marketState, wallet, sellerPlayerId)`, credits the seller immediately at the planet's current live price — no `Listing` created, no counterparty needed, structurally impossible to deadlock the way listings can. **Chosen over extending `SEED_MARKET_PLAYER_ID` into a real periodically-refreshing NPC listing pool** (the shipyard/crew/scanner-pool pattern) — that would need synthesizing both buy *and* sell demand out of nothing, a second pricing signal alongside `PlanetMarketState`'s already-live one, for no benefit `sellToMarket()` doesn't already provide more simply. Listings are untouched and keep their existing purpose (player-to-player value once Multiplayer exists, the Phase 3 remote tier-6/7 sale mechanic).
- **Mechanically, this is almost entirely already-existing infrastructure — a genuinely small fix.** `applyDrift()` (`planetary-markets.md`) already has exactly the right shape: `TradeDirection = "sell" | "buy"` is defined **from the market's own perspective** ("`'sell'` = a player sold INTO this market (added supply), dropping the price" — `src/trading/drift.ts`'s own comment), so `sellToMarket()` is `applyDrift(marketState, quantity, "sell")` with no new drift logic at all. The fee model reuses `purchaseListing()`'s exact shape too: `totalValue = quantity * marketState.currentPrice`, `feeDeducted = totalValue * TRANSACTION_FEE_PERCENT`, `proceedsToSeller = totalValue - feeDeducted` — the same 5%-removed-from-the-economy rule every transaction already follows, applied symmetrically.
- **No new restriction beyond what already exists.** Planetary markets already allow tier 6-7 items (only the *global* listing ceiling restricts those); `sellToMarket()` inherits that as-is — no new tier check needed.
- **This does not change `purchaseListing()`, `createListing()`, or any existing listing behavior** — `sellToMarket()` is purely additive, a second way to dispose of inventory alongside (not instead of) creating a listing.
- **The global-market sibling gap, confirmed real (not just plausible) and now fixed the same way: `sellToGlobalMarket(itemInstance, quantity, marketStates, wallet, sellerPlayerId, now?)`.** Verified by reading `galactic-market.md`: it still routes every global sale through `createListing()`/`purchaseListing()`, the identical self-trade structure — a solo player can never buy their own global listing either, so global selling is the same permanent dead end once any seed listings are gone. **Reuses `getGlobalPrice(itemId, "sell", marketStates)` for pricing** (`galactic-market.md`) — no second pricing formula. **Deliberately drifts no `PlanetMarketState` at all**, unlike the planetary version: `getGlobalPrice()` is a *derived* value with no owned state of its own (`galactic-market.md`'s own "must not give global listings their own drift state" rule already forbids inventing one just for this). A global sale is priced off whichever planet currently has the best buy price, but doesn't feed back into that specific planet's `currentPrice` — treated as a genuinely separate transaction the same way a global purchase never touches planetary drift either. **Inherits the existing tier-6/7 ceiling** (`GLOBAL_LISTABLE_MAX_ITEM_TIER`) as a hard rejection, exactly like `createListing()`'s own enforcement — the instant-sell path must not become a second, unguarded route past a restriction the listing path already enforces.
- **Both `sellToMarket()` and `sellToGlobalMarket()` throw rather than return a typed rejection, mirroring `createListing()`'s posture, not `purchaseListing()`'s.** Clarified while adding the global sibling, since the original planetary entry never stated this explicitly. Reasoning: `purchaseListing()`'s rejections (self-trade, over-quantity) are normal outcomes of another player's independent action the caller must always handle gracefully; a sell-from-your-own-inventory action has no equivalent business-rejection surface — the only failure modes (tier 6-7 on the global path, "no planet currently trades this item" via `getGlobalPrice()`'s own existing throw) are contract violations a correctly-filtered UI should never trigger, the same class of error `createListing()`'s tier check already throws for.

**Section status: built.** `sellToMarket()`/`sellToGlobalMarket()` implemented (`src/trading/`), wired into `MarketScene`/`GlobalMarketScene` as additive `> Sell Now` actions, tested (`tests/trading/sellToMarket.test.ts`, `sellToGlobalMarket.test.ts`), full suite green with zero regressions. Contracts: `agent-11-amendment-trading-counterparty-core.md`, `agent-13-amendment-trading-counterparty-presentation.md` — see `docs/functional-agents/planetary-markets.md`/`galactic-market.md` for the consolidated contracts.

## Colonist-Driven Production

**Status: active design pass — new territory, deliberately reopens Planet Resource Generation's "always-on" gathering premise.** Found via the TradeWars alignment review: TW2002 planets produce nothing until colonists are transported there; Profitable's planets are gatherable the instant they're generated, with zero player investment. This section adds that investment layer without touching *what* a planet produces or the fixed-quality-per-resource mechanic this session already locked — only *whether* gathering is available at all.

**Decided:**

- **Colonists are a new, simple concept — not an extension of `CrewMember`.** A `Colonist` is unskilled population, transportable cargo in TW2002's own terms — mechanically closer to an inventory item than to a hired specialist. **Chosen over extending `CrewMember`** (adding `assignedPlanetId` alongside Ship Crew Roles' `assignedShipId`) specifically to avoid diluting what "crew" already means in this design: tiered, professioned, waged, attrition-subject, hired *specialists*. A colonist has none of that — no tier, no wage, no upkeep, no attrition, no profession. Blurring the two would make "crew" mean two structurally different things depending on context, the same kind of ambiguity this project has avoided everywhere else (e.g. keeping `Scanner` structurally separate from `ShipComponent` rather than reusing a similar-looking shape for a different job).
- **Mechanic: a new `Planet.colonistCount: number` field (default 0), and a new `COLONIST_TRANSPORT_COST` (credits per colonist, purchased at a planet with existing colonists — Terra-equivalent — or a Shipyard-adjacent action) and `MINIMUM_COLONISTS_TO_PRODUCE` threshold (originated defaults, tunable).** Transporting colonists to a planet is a new action (`transportColonists(ship, destinationPlanet, quantity, wallet)` or similar) — consistent with the existing "credits buy a real thing" pattern (`purchaseShip`, `purchaseScanner`, this session's `refuelShip`), not a resource/cargo simulation.
- **Production gate: binary, not graduated.** `getCurrentPlanetResources()` (`planet.md`) returns an empty `producibleResourceIds` (and no gathering is possible) when `planet.colonistCount < MINIMUM_COLONISTS_TO_PRODUCE`; once that threshold is met, the planet behaves exactly as `planet.md` already documents — same fixed quality, same reset cycle, same specialty rules. **Chosen over a graduated colonist-scales-quality/yield model** — the fixed-quality-per-resource mechanic was just locked this session specifically to make a planet's output a legible, comparable fact; layering a second, continuously-variable colonist-count modifier on top of it the very next design pass would undercut that legibility rather than build on it. A clean on/off gate adds the "where do I invest" decision TW2002 has without touching the quality model at all.
- **Both bootstrap planets are pre-colonized, not just the starting planet — revised from this bullet's original, narrower version.** A brand-new player has no ship-transport capability yet and no colonists to move; requiring colonization before the tutorial's own gather step would strand them before the game starts. `galaxy.md`'s `startingPlanet` **and `secondaryDiscoveredPlanet`** both get `colonistCount` set to (at least) `MINIMUM_COLONISTS_TO_PRODUCE` at generation, the same bootstrap-exception shape their `discovered: true` override and the Planet Resource Generation tutorial clamp already use. **Extended to the second planet specifically because it's the one `profitable-alpha-playtest-plan.md`'s A3/A4 scenarios already travel to** — leaving it colonist-gated would silently strand those scenarios the same way ungated gather-variance instructions already had to be fixed once this session; better to design around a known, already-load-bearing planet than discover the same class of break twice. No other planet gets this exception — everything beyond the two bootstrap planets requires real colonist investment.
- **Colonist count is permanent once transported — no attrition, no starvation, no reset-cycle interaction.** Simpler than TW2002 (which does model colonist growth/loss in some variants) and consistent with keeping this a one-time investment decision, not an ongoing maintenance burden layered on top of ship fuel and crew wages. `planet.md`'s periodic resource reset cycle re-rolls the resource *subset*/quality, never `colonistCount`.
- **Must not let colonization interact with `Voyage.cargo`/Cargo Hold Capacity** — colonists are transported via a dedicated action (`transportColonists()`), not modeled as `VoyageCargoItem`s subject to the cargo-hold capacity cap; that cap exists for the Phase 3 remote-sale mechanic specifically, and folding colonist transport into it would make an unrelated system's capacity number gate a completely different mechanic.
- **`colonistCount` (and Citadels' `citadelLevel`/`ownedByPlayerId`, below) must persist as a side-table, never as a direct field baked into the regenerated `Planet` object — a real gap found reviewing this section against `galaxy.md`'s own rule, not caught when this section was first written.** `galaxy.md`'s "must not persist the generated planet array itself" rule exists precisely because `Planet` objects are deterministically regenerated fresh from the galaxy seed on every load — which is exactly why `discoveredPlanetIds` is a separate persisted side-table rather than a field mutated on the planet object directly. `resourceQualities` (Planet Resource Generation) correctly avoids this trap by being a pure function of `(planetId, now)`, needing no persistence at all. `colonistCount`/`citadelLevel`/`ownedByPlayerId` have no such derivation — they're facts set by discrete player actions with nothing to re-derive them from — so without a side-table, every reload would silently reset every colonized/claimed planet back to defaults. **Fix: a new persisted structure (e.g. `profitable:planetOwnershipState`, a `Record<planetId, { colonistCount, citadelLevel, ownedByPlayerId }>`), read/written exactly like `discoveredPlanetIds` already is, merged onto a freshly-generated `Planet` at read time — never baked into `generatePlanet()`'s own deterministic output.**
- **`transportColonists()` requires the transporting ship be docked at the destination planet, and colonists have no separate origin/supply — found missing when this section's forward-looking contract (`planet-ownership.md`) was reviewed.** Without a docking check, the ship parameter the action takes would have no enforced purpose, undermining the "transported" framing entirely — every other credits-buy-a-real-thing action this project has (`purchaseShip`, `purchaseScanner`, `refuelShip`) already requires physically being at the right place, and this is no different. Colonists themselves are abstracted as "arranged via credits" once docked, not carried from a specific source planet or limited pool — modeling a real TW2002-style colonist supply chain is new scope well beyond this pass, stated explicitly here rather than left ambiguous.
- **The bootstrap exception (both planets pre-colonized) applies at the same moment `galaxy.md`'s `loadOrCreateGalaxy()` generates a genuinely new seed — not a vaguer "at first load" — and is a floor-set (`colonistCount = max(existing, MINIMUM_COLONISTS_TO_PRODUCE)`), never an overwrite.** Tightened on review: the original "at first load" phrasing didn't say whether that meant once-ever or every load; tying it to the fresh-seed branch (the same hook `universe.md`'s one-time Galaxy registry event uses) removes the ambiguity, and the floor-set framing means it's safe to reapply without clawing back colonists a player transported beyond the minimum.

**Section status: built.** `transportColonists()` (`src/planets/transportColonists.ts`), the `getCurrentPlanetResources()` colonist gate, the `planetOwnershipState` side-table and merge function, and the bootstrap floor-set all implemented and tested (`tests/planets/`, `tests/galaxy/planetResourceCycle.test.ts`), plus a minimal `GatherScene` presentation hook so the mechanic is actually playable. Full suite green (617 tests), zero regressions. `COLONIST_TRANSPORT_COST`/`MINIMUM_COLONISTS_TO_PRODUCE` remain tunables (originated defaults: 15cr/colonist, 5 minimum). Contracts: `agent-01-amendment-planet-ownership-schema.md`, `agent-37-planet-ownership-core.md`. Citadels (below) build directly on the ownership concept this section establishes, and share its persistence fix — also built, see that section's own status.

## Citadels

**Status: active design pass — depends on Colonist-Driven Production above; new territory.** TW2002's Citadels are a 6-level planetary upgrade path, primarily defensive. Profitable has no player-vs-player or NPC-invades-your-planet mechanic, and Multiplayer's own locked design is explicitly asynchronous with no shared real-time presence — so a defensive citadel would be building fortifications against a threat that structurally cannot exist yet. This section reshapes the concept around what actually has value in a single-player, async-multiplayer game today.

**Decided:**

- **Purpose: infrastructure benefits, not defense.** A Citadel provides real, immediately-useful single-player value: **ship repair** (accelerating or enabling the Systems Engineer repair mechanic recommended in Ship Crew Roles — a Citadel could repair combat-damaged components at a colonized planet even without a Systems Engineer aboard, or repair faster than the crew-only version alone — **resolved on a later review pass, together with the Crafter role's own repair effect, as a strict additive sum of whichever rates currently apply; see `ship.md`'s `resolveComponentRepair()` for the full 3-way contract**), **a refuel discount** (a percentage off `REFUEL_COST_PER_UNIT` at that specific planet), and **safe cargo storage** (a place `Voyage.cargo` can be held without occupying the ship's own cargo hold capacity while docked — a real use for a mechanic that otherwise has no UI-level use yet, per Cargo Hold Capacity's own "doesn't fix the never-wired-up UI gap" note). **Chosen over building defense/garrison mechanics now** — with no invasion threat model, a defensive citadel would be pure speculative scope against a system (real-time PvP or NPC planetary assault) that directly contradicts Multiplayer's own already-locked async design. If Multiplayer's shape ever changes to include direct player conflict, defense is a natural, well-scoped future addition to this same structure — not built preemptively.
- **Ownership prerequisite: a Citadel can only be built on a colonized planet the player has claimed.** Reuses Colonist-Driven Production's `colonistCount` gate as the entry point — a planet must already be productive before it's worth fortifying. "Claiming" is a new, minimal concept: the first player to build past `colonistCount >= MINIMUM_COLONISTS_TO_PRODUCE` and construct Citadel level 1 becomes that planet's owner (single-player-only concern for now; Multiplayer's eventual arrival would need its own decision about contested claims, explicitly not resolved here).
- **3 levels, not TW2002's 6** — matching this project's consistent minimal-depth pattern (4 ship components and no more, no 5th component, Cargo Hold Capacity's modest curve versus fuel's steeper one). A new `CITADEL_LEVEL_BENEFITS` table (originated default, tunable): **Level 1** — docking (a named place to be "at" when logged off, cosmetic/flavor parity with TW2002's level 1, no mechanical effect); **Level 2** — the refuel discount and cargo storage; **Level 3** — the repair benefit (the most valuable of the three, gated behind the deepest investment). Upgrading costs credits + a raw/refined material investment (reusing the existing "credits + materials" purchase pattern, not a new economy).
- **Must not add any garrison/fighter/defense field to `Planet` or `Citadel`** — explicitly out of scope per the purpose decision above; revisit only if Multiplayer's shape changes.
- **Must not let Citadel ownership interact with `getDiscoveredPlanets()`/discovery** — owning a citadel doesn't discover other planets or extend scan range; that's Scanner's job exclusively, unaffected by this section.
- **Must not require a Citadel to gather at all** — Colonist-Driven Production's binary gate (colonized → gatherable) is the *only* gathering prerequisite; a Citadel is a further, optional investment on top of an already-productive planet, never a second gate blocking basic gathering.
- **`citadelLevel`/`ownedByPlayerId` share Colonist-Driven Production's side-table persistence fix (above), not a separate mechanism.** Same reason: neither is derivable from the galaxy seed, so both belong in the same persisted `Record<planetId, {...}>` structure `colonistCount` uses, never as a direct field on the regenerated `Planet` object.
- **`claimPlanet()` and `buildCitadel()` both require the acting ship be docked at the target planet — found missing on the same review pass that added the docking requirement to `transportColonists()` above.** Claiming or building at a planet the player isn't at makes no more sense than colonizing one remotely; both actions follow the identical location-bound pattern.

## Engine/Systems Architecture

**Decided:**
- This is **not** meant to be a reusable engine/framework for other games or modes to plug into — it's a **specific implementation for one game**.
- **Data-driven design confirmed** — resources, recipes, and qualities will be defined in config files (JSON/CSV or similar) so content can be added/adjusted without code changes.
- **Persistence model: single-player for initial scope.** Multiplayer (some form of shared economy or otherwise) is a planned future evolution, not part of the initial build.
- **Development order:** galaxy generation → planet generation → resource generation → crafting recipes/schematics, **then** the trading loop, crafters (NPC crew), travel, and the galactic map.
- **MVP scope confirmed:** build the quality math end-to-end on one hardcoded planet before investing in procedural galaxy/planet generation:
  1. One hardcoded planet, 2-3 resource types (skip procedural galaxy gen for v1).
  2. Resource generation with random quality rolls (1-100 + 7-tier color mapping).
  3. One refining recipe end-to-end (Option A, refund chance, refiner tier).
  4. One crafting recipe + one schematic end-to-end (full unified crafting formula).
  5. Only after 1-4 are working and tunable — move to real galaxy/planet generation.
- **Tech stack: web stack now (TypeScript + Phaser), migrating to Unity later**, once the design has stabilized through iteration. Driven by wanting AI agents to do heavy lifting on development **for as long as possible** — a plain-text, framework-light web stack is far more agent-friendly (huge training data, automatable browser-based testing, no GUI-editor dependency) than Unity or Godot's editor-driven workflows. Unity was chosen as the eventual migration target over Godot, in part because Unity/C# is also comparatively agent-friendly (larger training data than Godot/GDScript), which helps keep agents effective even after the migration.
- **Renderer: Phaser, not PixiJS.** PixiJS is a rendering layer only (no scene management, input abstraction, tweening, or asset pipeline) — Phaser is a full 2D game framework built on similar rendering capability. Chosen because: (1) Phaser's `Scene` class maps directly onto the MVP's four screens (map/gather/refine/craft), giving every agent touching presentation code the same consistent pattern rather than inventing scene structure from scratch; (2) built-in tweening covers the "simple animated 2D screens" requirement natively; (3) built-in input handling (`setInteractive()`, pointer events) is the idiomatic way to satisfy the "no raw DOM input" architectural mandate; (4) larger, more game-specific training data (2D game tutorials/examples, not just rendering primitives), which matters given the agent-first development priority. PixiJS would win only if heavy custom rendering (particle systems, shaders, bespoke effects) were needed — not called for by the MVP's four straightforward screens, though Phaser doesn't preclude Pixi-style custom rendering later if needed (e.g., for the galactic trade map's visual polish).
- **Migration trigger: tied to the status of the initial (MVP) loop.** Once the hardcoded-planet, quality-roll, refining, and crafting vertical slice (see MVP scope below) is working and feels right, that's the signal to evaluate migrating to Unity — rather than a fixed calendar date or a specific unrelated technical wall. Exact "done" criteria for the initial loop still to be defined (see below).
- **Architectural mandate:** to keep the eventual Unity migration a *port* rather than a *rewrite*, the game must be built with a **hard separation between simulation and presentation** from day one. All core game logic (quality-roll formulas, refining/crafting math, market state, planet data) should live in plain, framework-agnostic TypeScript — pure functions/data structures with no Phaser objects touching them directly. Phaser code should only handle rendering, animation, input, and the map screen. Everything in the MVP scope above (quality rolls, refining formula, crafting formula) belongs in this framework-agnostic core.
- **Web-only capabilities: isolate, don't eliminate.** The goal isn't avoiding browser APIs entirely (some, like the canvas surface, are just what running in a browser means) — it's making sure they never leak into game logic:
  - **Avoid entirely:** DOM-based UI (HTML/CSS overlays for menus, market, inventory — render all UI inside the Phaser canvas instead), URL params/cookies/browser routing for game state, and raw DOM input event handling (use the engine's built-in input abstraction instead).
  - **Isolate behind a single swappable adapter each:** persistence (a `SaveSystem` interface wrapping localStorage, swapped for Unity's `PlayerPrefs`/file I/O at migration), audio playback (an `AudioManager` interface wrapping Web Audio, swapped for Unity's audio system later), and eventually networking (a thin interface over WebSockets, built even before multiplayer is in scope, so it costs nothing now and saves a rewrite later).
  - **Fine as-is:** the canvas rendering surface itself — not a migration risk, since Unity also renders to a surface conceptually similarly.
