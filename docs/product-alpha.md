# Profitable — Product Alpha Feature List

**Purpose:** the working checklist for alpha. Every item below traces back to a locked design decision in `profitable-design-questions.md` — nothing here is a new design question, only implementation, content, tuning, and packaging work against decisions already made. Detailed rationale for each section lives in its linked planning doc; this file is the trackable list itself.

**Explicitly not in this list:** Multiplayer backend implementation (design complete, deliberately deferred — see `profitable-design-questions.md`'s Multiplayer section), any Unity migration work, any new gameplay system — **with one named exception:** Section 6 below tracks seven newly-locked systems (Ship Fuel, Cargo Hold Capacity, Planet Resource Generation, Ship Crew Roles, Trading Counterparty, Colonist-Driven Production, Citadels) that genuinely are new gameplay systems, deliberately called out as in-scope for this alpha pass rather than deferred like Multiplayer. Reputation/alignment, haggling, and a StarDock-style hub were reviewed via the same TradeWars comparison and deliberately left out of scope, not overlooked.

**Sequence:** work top to bottom — later sections depend on earlier ones (tuning needs real content to tune against; UI/UX needs stable numbers/content to onboard into). Section 6 is the exception to strict sequencing — it was designed after Sections 1-5 were already underway and doesn't block or get blocked by any of them; treat it as parallel track, not a 6th sequential step.

## 3. Scale & Performance
*Detail: `profitable-alpha-scale-performance-plan.md`*

- [x] Fix galaxy generation at 50 planets — `PLANET_COUNT` raised from 5 to 50 (`src/presentation/galaxyState.ts`), the one line the plan doc's own rationale said this would be. Found and fixed one real downstream assumption this broke: `devSeed.ts`'s `seedDiscoveredPlanets()` discovered "every remaining planet" (`galaxy.planets.slice(2)`), which was only ever the low end of its own documented "4-6" target because the galaxy itself was too small to produce more — at 50 planets it would have discovered 48, defeating this section's own "meaningful subset, not all 50" premise for Test 1. Capped at `slice(2, 6)` (4 more, landing mid-range). Also re-verified (not assumed) that `devGalaxySeed.ts`'s hand-picked `KNOWN_GOOD_GALAXY_SEED` still produces its documented Grey/Gold+specialty/Orange+specialty pattern for planets 0-4 at 50-planet scale and against the current 60-resource roster (both had changed since that seed was last verified) — confirmed identical, since each planet's own seed (`${gameSeed}:${index}`) is independent of total planet count.
- [x] Confirm resource/Planet Type distribution is reasonable at 50 planets with the real content roster — plan doc's own "21-item roster" reference was stale (real roster is 60 resources, grown since this plan was written); checked against the actual current roster instead. `scripts/playtestHarness.ts` now prints both distributions for its existing 50-planet scale galaxy: tier `Green=7, Grey=19, Orange=4, Gold=5, White=8, Blue=5, Purple=2` (all 7 tiers present, Grey-heavy as expected — same 40-point-wide band as every other tier system in this project) and Planet Type `Neptunian=10, Terrestrial=11, GasGiant=12, SuperEarth=17` (all 4 types present, no type empty or dominant). Reasonable spread, confirmed empirically not assumed.
- [x] Test 1: full-galaxy map + travel layer rendering, discovered subset, check for overflow/legibility issues — verified via CDP against the real running dev build: 50-planet galaxy, a genuine mid-game discovered subset (6 planets — 2 bootstrap + 4 from the `seedDiscoveredPlanets()` fix above), TradeMapScene checked at unscrolled/mid-scroll/max-scroll. Clean at every position, no overflow, no overlap with the nav bar or the fixed status/scroll-hint text — the `ScrollableContent` work from earlier in Alpha already made this structurally scroll-bound rather than content-length-bound, and this confirms it holds at real Section 3 scale (60-resource price lists per planet, 5 real travel destinations with real 50-planet-scale distances, not just the smaller set it was originally fixed against).
- [x] Test 2: realistic player-state load (3-5 ships, full crew, 50-100 listings, 30+ days of price history) — `scripts/scaleTestHarness.ts` (`npm run scale-test`) builds 5 fully-componentized ships, a 6-member crew roster (one per tier), and 75 active listings (midpoint of 50-100) with their corresponding market states across the real 50-planet galaxy, then saves/loads through the real `createLocalStorageSaveSystem` adapter (byte-counted, not estimated). Result: save 0.28ms, load 0.45ms, 31.8KB total serialized — 0.62% of a real browser's ~5MB `localStorage` quota. No performance concern at this scale. **The "30+ days of price history" part of this item doesn't apply** — see Test 3's finding below; there is no price-history log to accumulate.
- [x] Test 3: `getGlobalPrice()` performance at 50 planets with real listing volume — same harness, 2000 calls against Test 2's 75 market states: 2.1μs/call average, no caching/indexing needed at this scale. **Finding: the plan doc's "price-history log... most likely to silently balloon" concern doesn't apply to the actual implemented design** — grep-confirmed no such log exists anywhere in the codebase; `PlanetMarketState` is a live snapshot only (`currentPrice`/`basePrice`, recomputed from elapsed time via drift/recovery), consistent with Trading's own locked "always query live, never cache" rule (Phase 3 GDD §2.7). Not a gap to fix — the plan doc's concern predated/didn't match Section 2's actual locked design.
- [x] Test 4: encounter/voyage history accumulation over an extended session (20-30 voyages) — **same finding as Test 3, from the other direction: no accumulating structure exists to test.** `resolveArrival()` calls `removeVoyage()` on every resolution (`TradeMapScene.ts`'s `onResolveArrival()`), deleting a `Voyage` — and whatever `encounters` it carries — the moment it resolves; nothing persists a voyage/encounter history log elsewhere. Confirmed via the harness anyway: 25 simulated voyage arrivals (at real per-route travel times, not an arbitrary duration — an earlier draft of this test back-dated departure by 10 years and produced ~17,000 encounters from 25 voyages, a bug in the test caught by the result looking obviously wrong, not a real finding) resolved in 1.68ms with 4 encounters rolled naturally. Resolution itself isn't slow at real distances/scale; there's nothing to accumulate.
- [x] Fix any issues found as bugs against the responsible existing agent/system — not new design scope — one real bug found and fixed (the `devSeed.ts` discovery-count assumption above, attributed to Alpha Section 4's own debug-seed work, not a new design decision). No other bugs found; the two "concerns that turned out not to apply" above are documentation corrections to this plan doc, not code changes.

## 4. UI/UX & Onboarding
*Detail: `profitable-alpha-uiux-onboarding-plan.md`*

- [x] Build debug/tuning panel exposing Section 2's tunables for live adjustment, gated behind a debug flag — `DebugPanelScene.ts`, reachable only via `?debug=1` (nav entry and scene registration both gated; scene code is dynamic-imported into its own chunk, verified absent from a production `npm run build` bundle and from a non-debug session's nav/registered-scenes). Every Section 2 scalar tunable across Trading/Crew/Ships & Travel/Scanner/Travel Encounters/Combat was promoted from `const` to `let` + a setter (data-file-only change, no formula/simulation code touched) and is live-adjustable via +/- steppers; per-tier tables (wage/cost/speed/weight curves) are exposed the same way. Includes a "Force Encounter" section (4 buttons: Trade Opportunity/Discovery/Hazard/Combat) that seeds a one-shot deterministic `RandomFn` into the next real `resolveArrival()` call rather than mocking an encounter — verified in-browser to produce a genuine, fully-resolvable `CombatEncounter` through the real `resolveEncounters()`/`initiateCombat()` path. Also includes "Reset all tuning to alpha defaults." Values are session-only — the `let` bindings live in memory only, are never written to `SaveSystem`, and reset to their alpha defaults on page reload, so a debug session can't leave a stray modified value active in a later non-debug session.
- [x] Build settings screen: audio on/off (via existing `AudioManager`), reset-onboarding option — `SettingsScene.ts`; `AudioManager` gained `setEnabled()`/`isEnabled()` (adapter-layer only), verified in-browser that toggling actually mutes/unmutes and persists via `SaveSystem`.
- [x] Build the 7-step skippable tooltip onboarding flow (gather → refine → craft → market → travel → shipyard → crew) — `onboardingOverlay.ts`, wired into all 7 scenes. Tracked per-step (not a strict linear pointer) since the nav bar already lets players visit scenes in any order; "Skip Tour" on any step's tooltip clears all 7 at once. Refine/Craft copy references "choose a recipe from the list" (recipe-selector-aware, not assuming a single hardcoded recipe).
- [x] Wire onboarding completion/skip state through the existing `SaveSystem` — `onboardingState.ts`; verified in-browser (dismiss/skip persist and survive scene changes; Settings' reset re-arms all 7 steps).
- [x] Run the tier-color legibility pass across all tier-driven UI (resource, refiner/crafter, planet, ship, schematic, scanner, crew) — audited via WCAG contrast ratio against the `#111111` canvas background plus a protanopia/deuteranopia/tritanopia simulation of all 21 tier-color pairs. One real failure found: Purple measured 2.99:1 (WCAG AA needs 4.5:1) — a legibility bug for all players, not just colorblind ones. Every other tier already cleared 4.5:1.
- [x] Add a minimal colorblind-safe treatment (e.g., tier-letter label alongside color) where feasible — audit found `TIER_COLOR_HEX` is only ever rendered as a real color fill in one place (`tierSelector.ts`), and that widget already draws the tier's full name as the colored text itself (never a bare swatch); every other tier display in the game shows the tier name as plain text regardless of color. This is already stronger than a letter code, so no separate abbreviation was added. Purple's color itself was corrected instead (0x9c27b0 → 0xba68c8, Material "Purple 300" — same palette family as the other 6, now 5.31:1 contrast) since that was the actual, concrete legibility gap the pass surfaced.

**Honest scope note:** this section improved functional completeness and accessibility — it did not add art, sound, or animation polish, which `profitable-alpha-plan.md` explicitly scoped out of alpha. The game's current text/shapes presentation is what alpha is intended to look like, not a placeholder awaiting replacement.

## Definition of Alpha-Ready

All five sections above complete, with:
- A player able to complete the full loop (gather → refine → craft → trade → travel → crew → ships → combat) using only the real content roster, with no numbers left at their initial "reasonable guess" state from `profitable-alpha-tuning-values.md`
- The 50-planet galaxy performance-verified per Section 3's four tests
- A new, unfamiliar player able to get through onboarding and reach the core loop unassisted
- A packaged, installable Windows/macOS build distributable to an external playtest group

**Section 6 is tracked separately, not required for Alpha-Ready.** It was locked after this definition's five sections were already the scope of "alpha-ready" — folding it in silently would move the goalposts. Whether Section 6 becomes a prerequisite for calling alpha done, or ships as a fast-follow after, is worth a deliberate call once Sections 1-5 are actually complete, not decided by default here.
